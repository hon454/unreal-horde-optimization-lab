# 측정 규약: 조건 고정, 캡처, 반복, 실패, 기록

측정을 설계할 때 연다. 예시 수치는 `SKILL.md` "예시 수치의 조건"에서 잰 참고값이다.

## 측정의 세 층

| 층 | 빌드 | 쓰는 곳 | 반복 |
| --- | --- | --- | --- |
| 개발 확인 | 에디터, Development | 동작 확인, 디버그 오버레이 화면. 수치를 비교에 쓰지 않는다 | 1회 |
| 작은 묶음 | Test 패키지 | 작업 하나의 설계 근거(이 기법을 넣을지, 이 값이 맞는지) | 조건마다 3회 |
| 최종 묶음 | Test 패키지 | 공개하거나 결정에 쓰는 모든 수치. 한 빌드에서 모든 조건을 함께 잰다 | 조건마다 3회, 끝에 A/A 3회 |

최종 묶음의 수치와 작은 묶음의 수치를 한 표에 섞지 않는다. 빌드나 시간대가 달라 같은 조건도 값이 다르다.

## 조건 고정

| 항목 | 값 | 왜 |
| --- | --- | --- |
| 빌드 | Test 구성 패키지. 패키지 커밋에 커밋되지 않은 변경이 있으면 재지 않는다 | Development는 `STATS`와 검사 코드가 있어 비용 구성이 다르다. 빌드 해시가 조건의 정의다 |
| 카메라 | 정해진 경로 하나. 비교하는 모든 조건이 같은 경로를 쓴다 | 화면 안 개체 수와 거리 분포가 같아야 렌더·GPU 비용을 견줄 수 있다 |
| 시간 | 워밍업 + 측정 창. 장면이 주기를 가지면 측정 창 = 한 주기, 워밍업 = 주기의 3분의 1 이상 | 측정 창이 주기의 일부면 창의 위치가 값을 바꾼다. 워밍업이 짧으면 첫 주기가 둘째 주기와 다르다 |
| 반복 | 조건마다 3회, 프로세스를 매번 새로 띄운다 | 한 번의 이상치를 거르고 범위로 차이를 판정한다 |
| 렌더 고정 | `r.VSync 0`, `t.MaxFPS 0`, 고정 창 해상도, `r.ScreenPercentage 100`, `r.DynamicRes.OperationMode 0`, 스케일러빌리티(`sg.*`) 고정, Lumen·VSM·TSR 상태 고정 | VSync와 프레임 상한은 프레임 시간을 자른다. 동적 해상도는 부하에 따라 일의 양을 바꾼다 |
| 엔진 기본값 | 모션 블러처럼 비교 대상이 아닌 엔진 기본값은 바꾸지 않고 그대로 기록한다 | 끄면 실제 게임과 다른 비용을 잰다 |
| 시드 | 고정. 초기 배치, 재생성 순서, 무작위 선택을 재현한다 | 조건 사이에서 같은 장면을 만든다 |
| 개체 수 | 측정 내내 유지한다. 유지되는지 실행마다 검사한다 | 개체 수가 줄면 일이 준다 |
| 재는 동안의 PC | 아래 "재는 동안의 PC" | 다른 프로세스가 CPU와 GPU를 나눠 쓴다 |
| CPU 클럭 | 실행마다 측정 창의 평균·최소 클럭과 시작 전 CPU 사용률을 남긴다 | 가끔 나오는 느린 실행이 게임 밖의 원인인지 가리려면 실행마다 값이 있어야 한다 |

**결정적 시나리오의 한계**: 시드가 같아도 궤적은 재현되지 않는다. 가변 프레임 시간이 매 프레임의 이동량을 바꾸고, 병렬 처리의 순서가 실행마다 다르다. 같은 것은 초기 상태와 규칙이고, 프레임 단위의 상태가 아니다.

## 캡처

CsvProfiler는 Test 구성에서 켜져 있다(`CSV_PROFILER` = 1). 워밍업은 캡처하지 않는다.

**압축을 끈다.** 기본값이면 `.csv.bin`(압축)으로 써질 수 있다. 분석 스크립트가 읽으려면 `.csv`여야 한다. `csv.CompressionMode`는 -1(기본), 0(끔), 1(켬)이다(`Engine/Source/Runtime/Core/Private/ProfilingDebugging/CsvProfiler.cpp`).

콘솔이나 명령줄로 할 때:

```text
csv.CompressionMode 0
csvprofile start
... 측정 창 ...
csvprofile stop
```

게임 코드로 할 때(워밍업이 끝나는 자리에서). 이름은 예시 이름이다.

```cpp
// 예시 이름: ABenchGameMode::BeginMeasure
void ABenchGameMode::BeginMeasure()
{
#if CSV_PROFILER
    // 렌더 고정은 워밍업 전에 이미 걸었다. 압축을 끄고 메타데이터를 남긴 뒤 캡처를 시작한다.
    IConsoleManager::Get().FindConsoleVariable(TEXT("csv.CompressionMode"))->Set(0);
    CSV_METADATA(TEXT("BuildCommit"), TEXT(BUILD_COMMIT_HASH));   // 빌드 해시(빌드 스크립트가 정의)
    CSV_METADATA(TEXT("FixedCVars"), *FixedCVarString());          // 적용한 렌더 고정 값
    CSV_METADATA(TEXT("Driver"), *FString::Printf(TEXT("%s %s"), *GRHIAdapterName, *GRHIAdapterUserDriverVersion));
    CSV_METADATA(TEXT("Window"), TEXT("60+180"));                  // 워밍업+측정(초)
    CSV_METADATA(TEXT("Techniques"), *TechniqueSwitchString());    // 켠 기법 스위치
    FCsvProfiler::Get()->BeginCapture(-1, FString(), RunLabel);    // 파일 이름 = 실행 이름
#endif
}

void ABenchGameMode::EndMeasure()
{
#if CSV_PROFILER
    CSV_METADATA(TEXT("Ok"), bRunValid ? TEXT("1") : TEXT("0"));   // 성공 표시. 실패 판정에 쓴다
    FCsvProfiler::Get()->EndCapture();
#endif
}
```

- 메타데이터는 CSV 끝에 `[키],값` 쌍으로 쓰인다. 키는 소문자로 바뀌어 나온다.
- 프레임마다 바뀌는 게임 값은 `CSV_CUSTOM_STAT`로 열을 만든다. 실행 하나의 합계는 `CSV_METADATA`로 남긴다.
- 엔진이 기본으로 쓰는 열은 `FrameTime`, `GameThreadTime`, `RenderThreadTime`, `GPUTime`, `RHIThreadTime`, `GameThreadTime_CriticalPath`, `RenderThreadTime_CriticalPath`다(`Engine/Source/Runtime/Launch/Private/LaunchEngineLoop.cpp`).

**셰이더와 PSO**: 셰이더는 쿡 때 컴파일된다. 실행 중 PSO 컴파일은 `r.PSOPrecaching 1`과 드라이버의 PSO 캐시가 맡는다. 묶음의 맨 첫 실행은 드라이버 캐시가 비어 있을 수 있어 버린다.

## 재는 동안의 PC

- 에디터, 빌드 도구, 쿡, 다른 게임 프로세스를 켜지 않는다. 같은 PC를 쓰는 다른 사람과 다른 에이전트 세션도 포함한다.
- 브라우저, 녹화 도구, 동영상 인코더를 닫는다. 브라우저의 주기적인 CPU 버스트가 7초 주기 스파이크를 만들어 프레임 p95를 흔든 적이 있다(참고값).
- 에디터를 켠 채로 잰 같은 조건의 실행들은 프로세스마다 수준이 달라 흩어졌다. 에디터 없이 다시 재면 범위가 몇 분의 일로 줄었다(참고값, 2만 개체).
- 게임 창이 앞 창이어야 한다. 뒤에 있던 실행은 게임 스레드 시간이 약 12% 길었다(참고값, 2만 개체). 측정 중에 앞 창을 주기적으로 검사하고 아니면 실패로 처리한다.
- 모니터를 켜 두고 화면 끄기와 절전을 끈다. 모니터가 꺼진 채 한 시간쯤 지난 뒤 모든 조건이 느려진 적이 있다(참고값).
- 시작 전 CPU 사용률이 높으면(예: 20% 초과) 내려갈 때까지 기다린다.
- 러너 스크립트가 있으면 시작 전에 빌드 도구, 에디터, 브라우저 프로세스를 찾아 시작을 거부하게 만든다.

## 반복과 순서

1. 조건마다 프로세스를 새로 띄워 3회 잰다.
2. 묶음의 맨 첫 실행 하나는 버린다(회차 0). 드라이버 PSO 캐시와 첫 실행 효과를 흡수한다.
3. 회차를 바깥 루프로 둔다. 조건 A·B·C를 회차 1에서 A, B, C로, 회차 2에서 C, B, A로, 회차 3에서 A, B, C로 돈다.
4. 묶음 끝에 기준 조건을 3회 다시 잰다(A/A). 판정은 `judging.md` "A/A"에 있다.
5. 0.5ms 아래의 차이를 주장해야 하면 두 조건을 5회씩 잰다.

순서를 뒤집는 까닭: 시간에 따른 표류(열, 클럭, 백그라운드)가 한 조건에만 몰리지 않고 조건마다 고르게 퍼진다. 그래도 실행 간 범위보다 작은 차이는 쓰지 않는다.

## 실패한 실행

아래 가운데 하나면 실패다. 실패한 실행의 수치는 요약에 쓰지 않는다.

- 측정 창의 프레임 수가 100 미만이다.
- 메타데이터가 조건의 기대값(빌드 해시, 기법 스위치, 개체 수, 측정 창)과 다르다.
- 개체 수가 측정 내내 유지되지 않았다.
- 측정 중에 앞 창이 게임이 아니었다.
- 게임이 남긴 성공 표시가 없거나 거짓이다. CSV가 없다.

규칙:

1. 프로세스 종료 코드만 믿지 않는다. Windows에서 게임의 비강제 종료는 종료 코드 0을 낸다(`troubleshooting.md`).
2. 실패한 실행은 새 회차 번호로 한 번 다시 잰다. 같은 실행 이름은 다시 쓰지 않는다.
3. 다시 잰 실행도 실패하면 더 재지 않고 기록한다.
4. 실행이 연달아 3회 실패하면 묶음을 멈추고 원인을 고친다.

## 기록과 측정 장치 동결

실행마다 남길 것:

| 항목 | 어디에 |
| --- | --- |
| 빌드 해시, 적용한 CVar, GPU 드라이버, 기법 스위치, 개체 수, 시드, 측정 창 | CSV 메타데이터 |
| 실행 이름(조건, 개체 수, 카메라, 회차) | CSV 파일 이름 |
| CPU 클럭과 시작 전 CPU 사용률 | 러너의 별도 표 |
| 측정 PC 사양, 엔진 버전 | 묶음 정보 파일 |

묶음마다 남길 것: 조건별 세 실행의 값, 중앙값과 범위, 판정, 버린 실행과 이유.

**측정 장치 동결**: 최종 묶음을 시작하기 직전의 커밋으로 아래를 동결한다. 하나라도 바꾸면 모든 조건을 새 묶음으로 다시 잰다. 지난 묶음의 값과 새 값을 한 표에 잇지 않는다.

- 개체 스포너, 시드
- 장면의 움직이는 대상(경로, 속도)
- 카메라 경로
- 러너와 검사 스크립트
- CSV 열과 메타데이터 키
- 조건 정의(조건마다 켜는 스위치)

이전 구성을 다시 재야 하면 옛 커밋을 체크아웃하지 않는다. 구현을 지우지 않고 실행 인자로 고르는 스위치로 남겨, 같은 빌드에서 그 구성을 다시 잰다.
