# 측정 규약

모든 마일스톤이 같은 시나리오, 같은 절차, 같은 지표로 잰다. 명령은 [commands.md](commands.md), 결정의 이유는 [ADR](../Decisions/README.md)에 있다. 값을 새로 확정하면 "확정값"에 적는다.

## 시나리오

- 평지 맵 반경 R. 중앙에 오브. 개체는 시작 시 디스크 전체에 정상 상태 분포(밀도 ∝ 1/r, 반지름당 개체 수 일정)로 N개가 놓이고 오브로 직진한다. 사망한 개체는 가장자리 링에서 다시 생성된다. N은 항상 유지된다.
- 오브: 반경 8m 피해 범위 안의 개체는 초당 100(가장자리)\~300(중심) 피해. 저격 간격마다 화면 안의 개체를 거리 구간별로 결정적 해시(스폰 일련번호 + 저격 틱)로 골라 피격 뒤 사망("확정값"의 저격). 사망은 사망 애니 뒤 제거(M5부터 재활용).
- 개체: Paragon 근접 미니언 1종(M3b부터 시즈 미니언 10% 추가. 일련번호 10의 배수가 대형, 초기 배치와 재생성 모두). 행동 규칙은 모든 마일스톤에서 같다. M3b부터 저격은 예약된 발(틱 4의 배수: 200m 밖 1발, 나머지 2: 80\~200m 1발)에서만 대형을 쏘고 나머지 발은 소형만 고른다. 대형 몫이 정확히 10%라 산 개체의 90 / 10 비율이 유지된다([plan.md](../plan.md) "M3b"). 1종에서는 예약 발이 소형으로 떨어져 규칙이 같다.
- 거리 밴드와 `LODMaxCount`는 M0에서 확정하고 바꾸지 않는다.

**프리셋 해석.** 대표 수치와 마일스톤 간 비교는 P1이다. P2는 모든 개체가 100m 넘게 떨어진 원거리 대조군이라, 거리·화면 크기로 동작하는 기법(URO, Budget 거리 단계, Representation LOD, Simulation LOD)에는 최선의 경우가 된다. 그래서 `budget`·`uro`는 P1에서만 잰다.

**하위 실험**(E1(b)\~(d), E2(b)\~(d), E3 계단 등)은 전수 매트릭스가 아니라 **앵커 조건 한 점 × P1 × 3회**로만 잰다. M3까지는 N=5k였다. M3b부터는 **N=20k**다. 5k는 GPU 병목(M3 5k P1 GPU 5.75ms)이라 Game Thread 변화가 프레임에 보이지 않는다(2026-11-09). 5k는 GPU가 주제인 실험에만 쓴다. **측정은 세 층이다**([ADR-0006](../Decisions/0006-three-measurement-tiers.md), 2026-11-10 사용자 결정). 개발 확인(N=20k P1 1\~3회, 비교에 쓰지 않는다), 마일스톤 묶음(새 단계의 대표 설정과 기준점만, N은 plan.md "측정 조건"), 총괄 묶음(전 단계 사다리와 글이 쓰는 모든 점, 글과 README의 수치). Mass 단계의 기본 점은 P1 N {10k, 20k, 30k}와 P2 N 20k, 액터 단계는 P1 N {500, 1k, 2k}다. 설정마다 60fps 경계의 위와 아래에 측정점이 하나씩 있어야 하고, 없으면 그 설정만 한 점을 더 잰다.

## 지표

프레임 시간은 ms로 적고 fps는 보조로만 쓴다. 중앙값(p50)과 p99는 60초 측정 창의 프레임 분포에서 구한다.

파생 지표 **`N@16.7ms`**(2026-11-09 사용자 결정 D안, M3b부터): 마일스톤·프리셋별로 **프레임 p95**가 16.7ms를 넘기 직전의 N(측정 N 사이를 로그 보간). 대표 그래프 "60fps를 지키는 최대 N"의 재료다. 옆에 **p50 기준 N**(Game/Render/GPU/프레임 p50 중 최댓값, M3까지의 정의)과 **병목 자원**(그 N에서 Game/Render/GPU p50 중 가장 긴 것의 이름. 프레임 시간은 항상 그 셋 이상이라 후보에서 뺀다, 2026-11-09)을 함께 적는다. 두 N의 간격은 그 단계의 꼬리 길이다. M0\~M3 값은 `Saved/Profiling/CSV/`의 원본으로 다시 요약해 태그 시점 값으로 구한다(재측정이 아니다). 본문 수치는 유효 숫자 둘("약 22,000")로 쓴다. 스레드별 시간은 p50만 쓴다. 병렬 실행의 스레드 시간에는 대기가 섞여 p95 해석이 어렵다. 이전 정의의 경위: Game Thread 시간은 워커 스레드를 기다린 시간을 빼서 워커가 병목인 경우를 놓치므로(E1 `massav` N=20k: Game 9.3ms, 프레임 57.7ms) 2026-11-08에 프레임 p50을 넣었고, 2026-11-09에 p50이 "절반은 느리다"는 뜻이라 p95를 대표로 올렸다.

## 차이 판정

- 중앙값의 변화가 두 구성의 범위(최댓값 − 최솟값) 중 큰 쪽보다 클 때만 차이가 있다고 적는다. 그보다 작으면 "구별되지 않았다"고 적고, 주장이 필요하면 두 구성을 5회로 다시 잰다.
- 같은 날 연달아 잰 묶음끼리만 비교한다. 지난 마일스톤과 비교해야 하면 같은 빌드에서 그 단계를 `-LabStage=`로 골라 같은 묶음에서 다시 잰다([ADR-0004](../Decisions/0004-stages-as-run-modes.md)).
- 바뀐 변수가 둘 이상인 비교는 "참고"로 적고 추이 그래프에 잇지 않는다.
- 실패한 실행(종료 코드 ≠ 0, N 유지 실패, 프레임 수 비정상)의 수치는 쓰지 않고 라벨을 바꿔 다시 잰다.

## 함정

- Development 빌드의 수치를 Test 패키지 수치와 섞지 않는다.
- 프리셋 밖에서 본 수치는 "관찰"로만 적는다.
- `csvprofile`은 `-csv.*` 인자와 CVar로 압축·버퍼를 조절한다. 측정 창 밖(워밍업)은 캡처하지 않는다.
- 저격 빈도와 사망·재생성 처리량은 같은 변수다. 피해 전달 비용만 보려면 비치명 피해를 쓴다(E1(d)).
- Game 스레드 시간은 기다린 시간을 포함하고, 기다림이 찍히는 자리에 따라 달라진다. M4 탑뷰 20k에서 Game p50이 +2.15ms였지만 프레임은 같았다(작업 대기가 LOD 프로세서 안으로 옮겨 갔다, Worklog/M4.md "표현 LOD 대기: 가르는 트레이스"). 스레드 지표의 차이는 프레임 시간과 병렬 트레이스로 확인한 뒤에 비용이라고 적는다.
