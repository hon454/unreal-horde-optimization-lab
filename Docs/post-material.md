# 글 재료: 질문과 답

작업 중 사용자가 묻고 답한 것을 글에 쓸 수 있게 모은다(2026-11-08 사용자 요청). 독자도 같은 곳에서 막힐 것이고, 배우는 과정을 보여 주는 재료다. 글을 쓸 때 "질문 → 처음 생각 → 확인한 것(수치·소스) → 결론" 순서로 풀고, 수치는 그 글의 `measurements.md`에 다시 잰 값으로 옮긴다.

**설명 강조**: 표시한 항목은 독자가 개념을 모르면 따라오지 못하므로 그림이나 비유와 함께 한 단락 이상 설명한다.

수치 출처는 따로 적지 않으면 Test 패키지 96f8202, P1, Game Thread p50이고 `Measurements/M0/`, `Measurements/M1/`에 있다.

## 01 액터 군중 기준선

### 왜 액터는 무엇을 덧대도 1천 개 근처에서 막히나

- 60fps를 지키는 최대 N(프레임 시간 포함 판정, 2026-11-08): full 813, budget·uro 1천 미만, pawn 1,128, static 1,196. Game Thread만 보면 874 / 1,019 / 1,197 / 1,278이었다. 판정 기준을 바꾼 이유는 02의 "Game Thread 시간과 프레임 시간" 항목.
- 1k에서 full 18.4ms의 내역(CSV `Exclusive/GameThread/*`): CharacterMovement 8.6, Animation 4.1, TickActors 3.0, 나머지(물리 동기화, 틱 대기열 등) 약 2.7.
- 결론: 한 변형은 한 비용만 뺀다. static은 Animation, pawn은 CharacterMovement를 빼지만 액터마다 도는 틱·컴포넌트 변환 갱신·틱 대기열은 남는다. 그래서 천장이 1.2\~1.5배밖에 오르지 않는다.

### URO는 왜 효과가 작았나

- uro N=1000: Animation 4.1 → 3.0ms(27% 감소), CharacterMovement 8.6 → 8.8, TickActors 3.0 → 2.9. 전체 18.4 → 17.5ms(5%).
- 결론: URO는 애니메이션 갱신 빈도만 줄인다. 애니메이션이 원래 전체의 22%라 그만큼만 줄어든다. 가장 큰 비용인 이동은 건드리지 못한다.
- 추정(확인 안 함): 애니메이션 절감이 27%에 그친 것은 포즈 계산 상당 부분이 원래 워커 스레드에서 돌기 때문으로 보인다. 글에 쓰기 전에 트레이스로 확인한다.

### 프레임 시간, fps, 16.7ms가 뭔가 **설명 강조**

- 사용자도 "프레임이 38ms"라는 표현에서 막혔다. 글 앞부분에서 먼저 정의한다.
- 게임은 화면을 한 장씩 새로 그리고, 한 장마다 "미니언 이동 → 애니메이션 → 그리기"를 한 바퀴 돈다. 이 한 바퀴가 프레임, 걸린 시간이 프레임 시간이다.
- 1초 = 1000ms. 16.7ms면 1초에 60장(60fps). 2,000명일 때 약 38ms(약 26fps), 5,000명일 때 약 150ms(약 7fps).
- 이 프로젝트의 "16.7ms 선"은 한 바퀴를 그 안에 끝내야 60fps라는 뜻이다.

### 비용이 N보다 빠르게 느는 이유: CharacterMovement의 하위 스텝 **설명 강조**

- 관찰: full 2k → 5k(2.5배)에서 Animation·TickActors는 2.8배, CharacterMovement만 17.7 → 96.4ms(5.4배).
- 원리: 매 프레임 "지난 프레임 이후 흐른 시간"만큼 움직인다. CharacterMovement는 한 번에 최대 50ms어치만 계산하고(`MaxSimulationTimeStep = 0.05`, `CharacterMovementComponent.cpp:698`), 더 길면 **한 프레임 안에서** 나눠 여러 번 계산한다(세 프레임에 나누는 것이 아니다). 매번 충돌·바닥 검사를 다시 해서 벽 통과나 바닥 판정 오류를 막는다.
  - 2k: 프레임 약 38ms라 한 번.
  - 5k: 약 150ms라 50ms씩 세 번. 미니언당 이동 비용 8.9µs → 19.3µs.
- 결과: 이미 느려진 상황에서 정확도를 지키려고 더 계산해서 더 느려지는 되먹임이다. 프레임이 50ms 안인 동안(이 시나리오에서 대략 2\~3천 개)은 없고, 넘는 순간 비용이 급히 뛴다.
- 상한: 최대 8번까지 나누고 8번째에 남은 시간을 몰아 쓴다(`MaxSimulationIterations = 8`, `GetSimulationTimeStep` `:8162-8186`). 무한히 느려지지는 않는다.
- 사용자가 스스로 낸 결론: "이미 느려진 상황에서 정확도 확보를 위해 더 느려지게 만들어 버려서 생기는 문제." 글에서 이 문장을 그대로 결론으로 쓸 만하다.

### 측정을 시작할 때 미니언이 오브 가까이 있어도 괜찮나

- 질문: 워밍업 동안 오브 범위에 못 들어오게 막아야 하지 않나?
- 답: 처음부터 정상 상태 분포(반지름당 개체 수 일정, 밀도 ∝ 1/r)로 놓아서 첫 프레임부터 "들어오는 수 = 죽는 수 = 재생성 수"가 평형이다. 막았다 풀면 한꺼번에 몰려와 측정 구간에 파도가 생긴다.
- 근거: 측정 60초의 재생성 수가 실행마다 거의 같다(첫 E0: full N=1000 세 실행 모두 504, N=5000 1,928 / 1,932 / 1,933).

## 02 Mass 코어

### M1에서 왜 거리 구분 없이 전부 ISM으로 그리나

- 질문: 하이드레이션을 할 거면 거리 구간마다 달리 그려야 하지 않나?
- 답: 한 단계에 변수 하나. M1은 컨테이너(액터 → Mass)만 바꾸고, 비교 상대인 M0 static(애니 없는 정적 메시 액터)과 표현을 같게 둔다. 거리 구간은 M2(Representation LOD), 근거리 액터 전환은 M3.

### 같은 로직을 Mass로 옮기기만 했는데 왜 17배인가 **설명 강조**

- 60fps 한계 N(프레임 시간 포함): M0 static 1,196 → M1 20,577(약 17배). 같은 N에서 Game Thread 1k 8.4배, 2k 13.8배, 5k 31.8배 가볍다.
- 정정(2026-11-09): 17배는 컨테이너 전환만의 값이 아니다. static 변형은 CharacterMovement 틱과 캡슐을 그대로 둔다(틱을 끄는 것은 pawn 변형뿐, `LabMinion.cpp:194`). 1k P1 Game Thread는 full 18.4 / pawn 13.3 / static 12.1ms라 CharacterMovement 몫이 약 5ms다. 컨테이너 전환만의 배수를 구하려면 "CharacterMovement 틱 끔 + 애니 없음" 변형이 필요하다(M3b 코드 결정 후보). 글에서는 "컨테이너와 이동 구현을 함께 바꾼 결과"로 쓴다.
- 이유: 액터마다 따로 도는 틱 대신, 프로세서가 같은 모양의 데이터(위치, 체력)를 메모리에 연달아 놓고 한꺼번에 처리한다. 액터당 틱·컴포넌트 고정비가 사라진다. 이 부분은 그림(액터 배열 vs 아키타입 청크)으로 보여 준다.
- 5k까지 거의 평평하다(1.4 → 3.1ms). 엔티티 수와 무관한 고정비(Mass 단계 처리, 오브, 화면 갱신)가 대부분이라서다. 그 뒤로 엔티티당 약 0.7µs씩 선형((32.9 − 12.4) ÷ 3만).
- 병목 이동: 20k에서 GPU 15.6ms가 Game 12.4ms보다 먼저 한계다. 모든 미니언을 거리와 무관하게 같은 메시로 그리기 때문이고, M2의 동기가 된다.

### Game Thread 시간과 프레임 시간 **설명 강조**

- 사용자도 처음에 "주방장이 일한 시간 vs 손님이 기다린 시간" 비유로 이해했다.
- CSV의 Game Thread 시간은 게임 스레드가 워커 스레드를 기다린 시간을 뺀다. 미니언끼리 비켜 가기를 켜면 이웃 찾기가 워커에서 길어져 Game 9.3ms인데 프레임 57.7ms가 된다(E1 (c), N=20k).
- 그래서 60fps 판정을 프레임 시간까지 넣어 다시 정했다. 숫자는 5\~8% 보수적으로 바뀌었고 배수(약 17배)는 같다.

### 병렬 처리는 왜 차이가 없었나

- E1 (b): `mass.FullyParallel`을 꺼도 프레임 p50이 5k 8.1 / 20k 16.1 / 50k 36.6ms로 켰을 때(8.0 / 16.0 / 39.2)와 같다.
- 정정(2026-11-09): "이득은 데이터 배치에서 왔다"는 이 데이터로 말할 수 없다. 20k P1은 GPU 15.6ms가 Game 12.4ms보다 커서 프레임 시간이 GPU에 묶여 있다. 병렬의 효과는 Game Thread로 봐야 하는데, 병렬 실행의 Game Thread 값(12.4ms)에는 다른 프로세서의 자원을 기다린 스핀 대기(`MassProcessingQueueTypes.h:776` `YieldThread`)가 들어 있어 직렬(12.8ms)과 바로 비교할 수 없다. 결론은 "구별되지 않았다"까지다. 프로세서별 시간은 M3b 묶음 1의 트레이스로 본다.

### 같은 문제에 대한 두 엔진 경로의 반대 선택 **설명 강조**

- CharacterMovement: 프레임이 길면 나눠서 여러 번 계산한다. 정확하지만 비용이 커진다(위 하위 스텝).
- Mass 이동: 나누지 않고 프레임 시간을 0.1초로 자른다(`MassMovementProcessors.cpp:41,100`). 비용은 일정하지만 프레임이 100ms를 넘으면 실제보다 덜 움직인다.
- 실제로 겪은 일: 개발 빌드(N=2000, 평균 64ms, 자주 100ms 초과)에서 M1의 범위 처치가 M0의 약 60%로 나왔다. 프레임이 빠른 N=300에서는 처치·재생성 수가 M0과 같았다. 처음에는 로직 버그로 의심했고, 엔티티 하나를 추적해 거리가 프레임마다 얼마씩 줄어드는지 찍어 원인을 찾았다.

### 움직이는 ISM과 Lumen **설명 강조**

- 관찰: M1 N=2000 시험에서 GPU 29ms. 미니언 ISM을 Lumen 장면에서 빼면 5ms, Lumen을 아예 끄면 4ms(시험 실행, `Saved/Profiling/CSV/trial/`).
- Lumen이 무엇인지 먼저 짧게 설명한다(실시간 간접광. 장면을 거리 필드와 표면 캐시로 단순화해 빛이 튀는 것을 계산한다).
- 원리: 소프트웨어 Lumen은 "동적 간접광에 영향"이 켜져 있고 거리 필드가 있는 메시만 장면에 넣는다(`PrimitiveSceneProxy.cpp:1701-1734`). 거리 필드는 정적 메시·Nanite·스플라인만 있다. 스켈레탈 메시 캐릭터는 원래 빠져 있다.
- 정적인 ISM(나무, 바위)이 Lumen에 들어가는 것은 흔하고 문제없다. 문제는 인스턴스 2,000개가 매 프레임 움직여 Lumen이 매번 장면을 다시 맞춰야 한 것이다(어느 패스가 시간을 쓰는지는 GPU 트레이스로 확인해 글에 넣는다).
- 질문: Lumen을 끄면 실제 게임과 멀어지지 않나? → 끄지 않고 미니언만 뺐다. 미니언은 여전히 Lumen GI를 받고 그림자를 그린다. 현업 근거: City Sample도 `r.RayTracing.Geometry.InstancedStaticMeshes=0`으로 ISM을 레이 트레이싱 장면에서 뺀다(`CitySample/Config/DefaultEngine.ini:122-123`).
- 같이 쓸 것: 엔진 Mass ISM은 기본으로 그림자를 그리지 않아(`bCastShadows = false`, `MassRepresentationTypes.h:105`) M0 액터와 맞추려고 켰다.

## 03 ISM + VAT

### 거리 단계 기준(30 / 80 / 200m)은 어디서 왔나

- City Sample에서 가져오지 않았다. 계획 초안 값을 M0에서 확정했다(measurement.md "확정값"). 근거: 미니언 키 1.76m가 30m에서 화면 높이 약 3%, 맵 반경 500m에서 모든 구간에 개체가 찬다(0\~30m 6%, 200m 밖 60%).

### 왜 M2에서는 모든 거리를 VAT로 그리나 **설명 강조**

- 질문: 원래 계획은 고품질 액터 / 저품질 액터 / ISM(VAT) / 안 그리기 같은 단계였는데, 왜 다 VAT인가? 극적인 비교를 위해서인가?
- 답: M2 동안만의 임시 상태다. 액터 표현은 M3에서 만들고, 한 마일스톤에 변수 하나만 더한다. 최종 모습(plan.md)은 0\~30m 액터, 30\~200m VAT 인스턴스, 200m 밖 안 그림.
- 200m 밖을 안 그리면 숫자가 크게 좋아지지만 VAT의 비용과 안 그린 이득이 한 숫자에 섞인다. 둘을 따로 재는 쪽이 오히려 덜 극적이다.
- 네 표현 종류(HighResSpawnedActor, LowResSpawnedActor, StaticMeshInstance, None)는 Mass `EMassRepresentationType` 그대로다.

### City Sample은 단계별로 무엇으로 그리나 **설명 강조**

- 엔진 군중 기본값(`Engine/Plugins/AI/MassCrowd/Source/MassCrowd/Private/MassCrowdVisualizationTrait.cpp:16-38`): High 고품질 액터 0\~5m 최대 10, Medium 저품질 액터 5\~10m 최대 20, Low ISM(VAT) 10\~50m 최대 500, Off 50m\~. 화면 안의 개체는 Medium 10m, Low 50m, Off 100m부터.
- City Sample `Config/DefaultMass.ini:15-23`은 Low 30m, Off 50m(화면 안 60m / 500m), 최대 High 10 / Medium 20으로 덮어쓴다. 군중 설정 에셋이 다시 덮어쓸 수 있어 최종값은 에디터에서 확인해야 한다.
- 전환: Medium ↔ Low에서 저품질 액터를 지우지 않고 꺼 둔 채 둔다(`bKeepLowResActors`, 스폰 비용 절약). 액터를 한 프레임 더 남겨 깜빡임을 가린다(`bKeepActorExtraFrame`).
- 우리와 다른 점: City Sample은 MetaHuman이 비싸 액터를 10\~20명, 수 m 안으로만 쓴다. 우리는 액터 500명(0\~30m)으로 넓다(E0 액터 천장 약 880명). 저품질 액터 단계는 plan.md에 없고 M3에서 넣을지 고를 수 있다.
- City Sample의 VAT ISM 프로세서(`MassCrowdUpdateISMVertexAnimationProcessor`)는 엔진 `UMassUpdateISMProcessor`를 상속해 위치와 애니 정보를 한 반복에서 쓰고, 엔진 것은 ini에서 끈다(`CitySample/Config/DefaultMass.ini:131-138`).

### VAT의 비용은 어디서 나왔나 **설명 강조**

- 예상: 셰이더가 텍스처를 읽어 정점을 옮기니 GPU가 늘 것이다.
- 관찰(Test 패키지 c867446, 프레임·Game·GPU p50): P1에서 GPU는 50k 29.4 → 29.1ms로 그대로, Game Thread는 20k 12.0 → 14.5, 50k 29.8 → 34.7ms. P2(탑뷰)에서는 GPU도 20k 8.4 → 9.8, 50k 14.2 → 17.8ms.
- 원리: Mass ISM은 매 프레임 보이는 개체의 위치 목록을 다시 쌓아 GPU로 보낸다. VAT는 개체마다 "지금 몇 번째 프레임인지" 숫자를 같이 쌓아야 하고(`AddBatchedCustomData`), 그 쓰기가 게임 스레드에서 돈다(`UMassUpdateISMProcessor`는 `bRequiresGameThreadExecution`).
- P1에서 GPU 차이가 안 보인 것은 Lumen·그림자 같은 다른 GPU 비용이 커서 묻힌 것으로 본다(추정). 글에 쓰기 전에 GPU 트레이스로 확인한다.

### 화면 밖만 지우면 왜 얻는 게 없었나

- 5k P1 프레임: 그대로 7.5, 거리만으로 200m 밖 지우기 6.4, 화면 밖일 때만 200m 밖 지우기 7.7.
- 엔진 ISM 갱신은 보이는 개체가 있는 청크만 돈다(`MassUpdateISMProcessor.cpp` `AreAnyEntitiesVisibleInChunk`). 화면 밖 개체는 원래도 갱신하지 않아, 지워도 줄일 일이 없었다.

### 실험 설계가 틀렸던 사례: 사망 0 / 초당 1천 **설명 강조**

- 처음 설계: "사망 0"을 만들려고 범위 피해와 저격을 껐다. 아무도 죽지 않으니 5천 명이 오브 주위에 쌓여 GPU가 14.1ms로 튀었다. 사망 비용이 아니라 밀집을 쟀다.
- 단서: 사망이 없는 쪽(14.5ms)이 초당 1천 명이 죽는 쪽(6.7ms)보다 두 배 느렸다. 원리와 맞지 않는 결과는 설계를 의심한다(00의 "환경이 수치를 흔든 사례"와 같은 교훈).
- 고친 설계: 평소 시나리오(초당 약 30명 재생성) 위에 초당 1천 명을 더했다. 5k P1 Render Thread 4.12 → 4.56ms, Game Thread는 구별 안 됨. 프레임은 7.49 → 6.52ms로 오히려 줄었는데, 60%가 피격·죽기로 멈춰 GPU 일이 줄어서다. 인스턴스 추가·제거 자체는 초당 1천 건에서도 싸다.

### 죽는 VAT 인스턴스의 칼날 그림자가 바닥에 남았다 **설명 강조**

- 사용자 관찰(2026-11-08): 화면 어디서나 죽기 애니 중 칼날 끝 그림자가 바닥에 남고, 인스턴스가 지워지면 사라진다. 측정을 멈추고 먼저 고쳤다.
- 갈라 보기: 번호를 붙인 같은 조건의 창(N=1000, 60초)을 차례로 띄워 사용자가 판단했다. M3 안 보임 / M3 그림자 캐시 끔 안 보임 / M2 보임 / M2 + `ShadowCacheInvalidationBehavior=Always` 보임 / M2 캐시 끔 안 보임 → 그림자 캐시가 원인이지만 "모르는 움직임" 문제는 아니다.
- 원인: Virtual Shadow Map은 물체 바운드 안쪽만 무효화한다. AnimToTexture는 Bone 모드에서 바운드를 뼈 위치 범위로만 넓혀(`AnimToTextureBPLibrary.cpp:290`), 칼날 끝이 상자 밖으로 나갔다. Y 음수 쪽이 204cm 모자랐다.
- 고친 것: Vertex 굽기가 계산한 모든 프레임의 정점 범위로 Bone 메시 바운드를 넓혔다(`Scripts/bake-vat.py`). `Always`는 비용 때문에 되돌렸다.
- 교훈: "그림자가 남는다 → 캐시를 끈다"로 끝내지 않고, 캐시가 무엇을 기준으로 지우는지(바운드)를 따라가면 근본 원인이 나온다. 셰이더로 정점을 움직이는 기법(VAT, WPO)은 바운드를 직접 챙겨야 한다.
- 전후 기록: [Measurements/M3/shots/vat-shadow/README.md](../Measurements/M3/shots/vat-shadow/README.md).

### 전환 팝핑은 어디서 생기고 어떻게 줄였나 **설명 강조**

- 사용자 관찰(2026-11-08, 개발 빌드 N=5000 P1): 30m에서 VAT 인스턴스가 액터로 바뀔 때 팝핑이 보인다. 시작 시각을 맞춘 뒤였다.
- 원인 후보(가능성 순, 추정): (1) 액터가 붙는 첫 프레임에는 애니메이션이 아직 계산되지 않아 기본 자세나 풀에 들어가기 전 자세가 한 프레임 보인다. (2) 액터 → VAT로 돌아갈 때 액터가 먼저 사라지고 인스턴스가 다음 프레임에 나타나 한 프레임이 빈다. (3) 30m 근처를 오가며 전환이 반복된다(엔진 기본 히스테리시스 10%, `MassRepresentationFragments.h:309`). (4) VAT는 본 영향 4개 근사라 실제 스킨과 미세하게 다르다.
- 엔진에서 확인한 함정: 엔진 풀은 액터를 꺼내자마자 보이게 하고(`MassActorSpawnerSubsystem.cpp:252`, 새로 스폰한 액터는 `:328`), "준비될 때까지 기다림"(`SetActorEnabled`)은 틱과 충돌만 켜고 끈다(`MassRepresentationActorManagement.cpp:30-45`). 기다리는 동안에도 액터가 보일 수 있다.
- 한 일(현업 정석, 2026-11-08 사용자 결정 A): (1) `bWaitForActorVisualReadiness`를 켜서 액터가 준비됐다고 알릴 때까지 엔진이 VAT 인스턴스를 떼지 않게 했다. 준비 신호는 우리 액터 관리 클래스(`ULabActorManagement::IsActorReadyForRepresentation`)가 "애니를 시작 시각으로 맞추고 메시가 두 번 틱함"으로 돌려준다. 그동안 액터는 숨기고, VAT 프로세서는 기다리는 엔티티도 계속 갱신한다. (2) `bKeepActorExtraFrame`으로 액터 → VAT 때 액터를 한 프레임 더 남긴다(엔진 군중 기본값도 켠다, `MassCrowdVisualizationTrait.cpp:22`).
- 버린 대안: 디더 크로스페이드(가장 부드럽지만 마스크 머티리얼로 모든 미니언의 그리기 비용이 는다), 전환 거리 늘리기(액터 수가 늘고 시나리오 변경).
- 그래도 "깜빡이는 느낌"이 남았다(사용자). 논리 진단(그려지지 않는 엔티티 수, 둘 다 그려지는 엔티티 수)은 0이었다. 그래서 화면을 프레임 단위로 봤다: 개발 빌드에 연속 캡처(`-LabShotBurst=N`)와 전환 사건 로그(프레임 번호, 화면 좌표)를 넣고, 사건 위치를 앞뒤 3프레임씩 잘라 나란히 놓았다.
- 찾은 원인: 액터가 보이기 시작하는 프레임에 미니언이 반투명하게 번진 덩어리로 그려졌다. 모션 블러를 끄면 사라졌다(`-dpcvars=r.MotionBlurQuality=0`). 액터를 숨긴(`SetActorHiddenInGame`) 동안 렌더 프록시가 장면에서 빠져서, 다시 보일 때 지난번 보였던 위치·뼈 변환이 "이전 프레임"으로 쓰여 큰 속도가 생긴 것이다. 보이는 프레임에 `ResetSceneVelocity`·`ClearMotionVector`를 불러도 프록시가 그 프레임 끝에야 다시 만들어져 소용없었다.
- 고친 것: 기다리는 액터를 숨기지 않고 메인 패스·깊이 패스·그림자에서만 뺐다(`SetRenderInMainPass(false)` 등). 프록시가 장면에 남아 위치와 뼈가 매 프레임 렌더러에 가므로 보이는 첫 프레임의 속도가 맞다. 같은 캡처에서 번짐이 사라졌다(전후 비교 이미지: 대책 전 `a46bf9c` 이전, 후 `a46bf9c`). 함께 찾은 것: 죽은 채 풀에 들어간 액터의 진홍색이 다음에 쓰일 때 한 프레임 남았다. 풀에 넣을 때 지운다.
- 그래도 깜빡였다(사용자). 앞의 캡처는 캡처 비용 때문에 프레임이 약 150ms 간격이라 실제와 달랐다. `-benchmark -fps=60`(고정 시간 간격)으로 다시 찍자, 액터가 보인 다음 두 프레임 동안 미니언이 세로 줄무늬로 번졌다. 원인: 엔진은 액터를 붙일 때와 준비가 끝날 때 엔티티 변환(발밑, z=0)으로 액터를 옮긴다(`MassRepresentationProcessor.cpp:272, 428`, 지연 명령이라 우리 동기화 뒤에 실행된다). 우리 액터의 원점은 캡슐 중심이라 그 프레임에 88cm 가라앉았다가 다음 프레임에 올라왔고, 그 수직 이동을 모션 블러가 그렸다. 액터 관리 클래스의 `TeleportActor`에서 같은 높이를 더해 고쳤다(60fps 캡처에서 사라짐).
- 교훈: "논리상 구멍 0"이어도 화면은 다를 수 있다. 캡처도 실제 프레임 간격이어야 보인다. 렌더러의 시간 축(이전 프레임 데이터, 모션 블러, TSR)까지 봐야 한다.
- 글에 넣을 것: 문제 크기 순 기록 [Measurements/M3/shots/transition/README.md](../Measurements/M3/shots/transition/README.md)(사용자 요청, 2026-11-09). 처음 기록은 원인을 찾은 순서였다. "가장 문제가 되던 것부터 적용하며 기록해야 한다"는 지적으로, 대책마다 끌 수 있게 하고(`-LabHydrateFixMask`) 전환 사건마다 화면 튐을 숫자로 쟀다(`Scripts/transition-score.py`). 다 켠 상태에서 하나씩 빼면 튐 평균이 2.6에서 높이 보정 8.8, 준비 대기 7.6, 시작 시각 6.3, 패스 숨김 4.9로 오른다(진홍 지우기는 잡음 안). 큰 순서로 쌓으면 9.0 → 9.1 → 7.5 → 5.5 → 2.2, 눈에 띈 전환 21% → 0%.
- 글에서 강조할 것: 가장 큰 문제(높이)를 먼저 고쳐도 첫 단계는 줄지 않았고, 하나씩만 켜면 어느 대책도 거의 효과가 없었다. 한 전환에 문제가 여럿 겹쳐 있으면 "하나 고치고 재기"가 효과를 못 보여 준다. 그래서 크기는 "다 고친 상태에서 하나만 되돌리기"로 쟀다. 영상 녹화는 사용자 승인 뒤.

### 액터의 비용은 어디서 나오고 무엇이 줄였나 **설명 강조**

- E3 (1)(20k P1, Test, 3회): 30m 안 액터 495개가 Game Thread를 7.1 → 14.4ms로 두 배 만들었다. N@16.7ms는 M2 + Off 35,763 → 22,046.
- 정정(2026-11-09): "38% 감소"는 액터 수가 아니라 상한이 정한 값이다. 20k와 50k 모두 액터가 495\~500개(상한 500)라 액터가 더한 Game Thread는 N과 무관하게 약 7.3ms(병렬)이고 액터당 약 14.8µs(직렬 5.76ms 기준 11.6µs)다. 글에서는 액터당 µs와 "고정비가 Mass 비용 위에 얹힌다"로 쓴다. 상한을 바꾸면 감소율도 바뀐다(E3 (7)에서 50m도 상한에 걸려 30m와 같았다).
- 순위를 직렬 Mass(`mass.FullyParallel=0`)에서 다시 쟀다. 병렬일 때 VAT ISM 프로세서에 더해진 2ms는 게임 스레드가 다른 프로세서가 쥔 자원을 실제로 기다린 시간이다(`WaitForQueryResources`, `MassProcessingQueueTypes.cpp:678` → `WaitForChange`의 `YieldThread` 스핀, `MassProcessingQueueTypes.h:776`). 착시가 아니라 게임 스레드가 쓴 시간이다. 경합의 원인 일부는 우리 쿼리 선언이다: VAT 프로세서가 `FLabMinionFragment`를 읽고(`LabVatProcessor.cpp:39`), Lab 로직 프로세서들이 같은 프래그먼트를 쓴다(저격은 쿼리 밖에서 `GetFragmentDataChecked`로, `LabMassProcessors.cpp:234`). M3b에서 선언을 고치고 전후를 잰다. 직렬은 원인을 가르는 수단이지 비용을 없애지 않는다. 직렬에서 액터가 더한 5.8ms: 애니메이션 2.5, 동기화 1.6(그중 이동 1.2), 나머지 메시 틱 등 1.7.
- 1위 애니메이션: Budget Allocator(`USkeletalMeshComponentBudgeted`, 예산 2ms)가 20k에서 1.4\~1.5ms를 줄였다. 5k(액터 263개, 애니메이션 1.55ms)에서는 줄지 않았다. 예산보다 적게 쓰면 할 일이 없다. URO는 0.3\~0.5ms, 저품질 액터 단계(15\~30m)는 0.5ms.
- 2위 이동: 캡슐 콜리전이 프레임 1.55ms다(콜리전 끔 15.78 → 14.23). 오버랩·물리 볼륨만 끄면 0.14ms, QueryOnly는 더 줄지 않는다. 피직스 씬에 바디가 있고 매 프레임 옮기는 것 자체가 비용이다.
- 글에서 강조할 것: 프로파일러의 프로세서 시간이 그 프로세서의 "일"이라는 보장이 없다. 병렬 실행에서는 기다린 시간도 잡히고, 그 대기도 게임 스레드의 실제 비용이다. 직렬로 다시 재서 일과 대기를 갈랐다. 또 기법의 효과는 조건을 탄다(Budget은 예산을 넘을 때만).

### 검이나 총의 정밀 판정은 프래그먼트로 되나 **설명 강조**

- 사용자 질문(2026-11-09): 실제 게임에서 검이나 총을 쓰면 근거리 액터에 더 정밀한 바디가 필요하고, 그건 프래그먼트만으로 안 되지 않나? 답: 맞다. 프래그먼트에는 위치·반경 정도만 있고, 부위 모양은 그 프레임의 뼈 자세가 있어야 안다.
- 흔한 구성은 거리별로 판정을 나눈다. 가까운 액터는 스켈레탈 메시의 피직스 애셋 바디(뼈마다 캡슐, QueryOnly)에 트레이스·스윕을 하고, 결과(부위, 위치, 피해)를 액터가 가진 엔티티 핸들로 Mass에 사건으로 넘긴다. 체력·상태는 Mass에 남는다(퍼핏 + 섞기 갈래). 먼 VAT 인스턴스는 CPU에 뼈가 없어 Mass 공간 질의로 구·캡슐 근사 판정을 하고, 정밀함이 필요하면 맞은 개체를 액터로 바꾼다(사건 기반 하이드레이션).
- 비용: 뼈마다 바디가 있으면 캡슐 하나보다 비싸다. E3 (6)의 1.55ms(20k, 액터 495개)는 캡슐 하나 기준이다. 판정용으로 뼈 수를 줄인 피직스 애셋을 따로 두고 근거리 액터에만 켜는 경우가 많다. Paragon 미니언 피직스 애셋은 바디가 Simulated라 그대로 켜면 래그돌이 된다(engine-notes.md 9절).
- 이 프로젝트는 무기 전투가 비목표라 구현하지 않는다.

### 사망 래그돌과 피직스 바디는 늘 켜야 하나

- 사용자 질문(2026-11-09): 실제 게임이면 사망 때 래그돌이 나와야 하나? 현실감 위주 게임이면 액터의 피직스 바디가 완전히 켜져 있어야 하나?
- 래그돌: 흔하지만 필수는 아니다. 호드 게임은 근거리 액터만, 동시 개수 상한을 두고 넘치면 오래된 것부터 멈추거나 치운다. 나머지 사망은 애니메이션(우리 VAT 사망처럼 싸고 예측 가능). 애니에서 물리로 블렌드해 시작하고, 멈추면(sleep) 시뮬레이션을 끄고 정지 포즈로 굳히거나 지운다. Mass 하이브리드에서는 래그돌 시체가 액터를 붙잡아 액터 상한(500) 안에서 살아 있는 개체와 자리를 다툰다.
- 바디: 살아 있는 동안은 Kinematic(애니를 따라가고 트레이스만 받음)이 보통이다. 시뮬레이션은 피격 반응(맞은 부위만 잠깐, Physical Animation·부분 래그돌)과 사망 때만 켠다. 늘 시뮬레이션하면 비싸고 불안정하다(걷기 유지가 어렵고 겹치면 튄다). Kinematic도 비용이 있다(E3 (6): 캡슐 하나 x 495개에 1.55ms). 현실감 있는 게임일수록 근거리 액터 상한을 낮게 잡게 되고, 하이드레이션 거리·상한을 정하는 근거가 판정·물리 비용으로 옮겨 간다.
- 이어진 질문(2026-11-09): Kinematic은 다른 바디를 밀어내는데, 미니언은 자기 몸이 밀릴 이유가 없어서 Kinematic인가? 답: 핵심은 위치의 주인이 Mass·애니메이션이라는 것이다. Kinematic은 힘을 받지 않고 코드·애니가 정한 곳으로 옮겨질 뿐이라 로직과 물리가 싸우지 않고 판정 모양은 정확하다. 밀어내기는 부수 효과다. 언리얼은 물리 타입(Kinematic / Simulated, 누가 움직이나)과 콜리전(QueryOnly / QueryAndPhysics, 무엇과 부딪히나)을 따로 고른다. 미니언 판정 바디는 보통 Kinematic + QueryOnly(판정 전용 채널)로 트레이스만 받고 아무것도 밀지 않는다. 시체·잔해를 밀게 하고 싶을 때만 QueryAndPhysics를 켜고 피직스 씬 비용을 더 낸다.
- 원거리 사망은 보통 래그돌을 만들지 않는다. 화면에서 작아 애니와 차이가 거의 안 보이고, 우리 구조에서는 원거리가 VAT 인스턴스라 뼈·피직스가 없어 래그돌을 쓰려면 액터를 붙여야 한다(상한·스폰 비용). 사망 애니 몇 가지를 섞어 단조로움을 줄이고, 폭발로 날아가는 장면처럼 물리처럼 보여야 하면 미리 돌린 래그돌 시뮬레이션을 VAT 클립으로 구워 재생하는 방법을 많이 쓴다.
- 이 프로젝트는 구현하지 않는다.

### 보스 같은 고수준 AI 적도 Mass로 만드나

- 사용자 질문(2026-11-08). 답: 보통 아니다. Mass의 이득은 같은 데이터를 수천 개 한꺼번에 처리하는 데서 나온다(M1 E1 (a) 약 17배). 보스 1\~수 마리에는 그 이득이 거의 없고, 보스가 쓰는 Behavior Tree·StateTree·GAS·몽타주·IK·복제는 액터·컴포넌트 기준이다.
- 흔한 구성: 졸개는 Mass(멀리는 인스턴스, 가까이는 하이드레이션 액터), 엘리트는 이번 M3 같은 하이브리드(City Sample의 사람들), 보스는 처음부터 액터. 보스와 졸개가 상호작용하면 `UMassAgentComponent`로 보스 액터를 Mass 쪽에 등록해 졸개가 장애물·목표로 인식하게 한다(로직은 액터에 남는다).
- 이 프로젝트: 보스는 범위 밖. M3b의 큰 미니언(시즈 10%)은 엘리트에 가깝고 같은 Mass 엔티티로 중요도만 다르게 둔다. 글 마무리(08 총괄)에서 "어디까지 Mass로 만드나"로 다룰 만하다.

### 하이브리드에서 로직은 누가 갖나: 퍼핏(Mass-driven) vs 액터 구동(actor-driven) **설명 강조**

- 사용자 질문(2026-11-08): 우리는 로직을 전부 Mass가 갖고 액터는 표현만 하는데, 하이브리드는 액터화되는 순간부터 로직을 액터에 맡기나?
- 용어: "퍼핏(puppet)"은 엔진 용어다. `UMassAgentComponent` 상태 `PuppetPendingInitialization` 등, 주석 "Actor driven by Mass (puppet)"(`MassActors/Public/MassAgentComponent.h:23`). 반대로 액터가 자기를 대표하는 엔티티를 만드는 경우는 `EntityPendingCreation`/`EntityCreated`로 구분한다. 처음 채팅에서 쓴 "넘겨주기"는 설명용으로 붙인 이름이라 쓰지 않는다(사용자 질문으로 확인, 2026-11-08).
- 갈래 셋: (1) 퍼핏(Mass-driven, 우리): 로직은 늘 Mass, 데이터는 Mass → 액터 한 방향. 진실이 한 곳이라 전환 때 어긋남이 없다. (2) 액터 구동(actor-driven): 액터가 붙으면 액터가 자기 AI·CharacterMovement·물리로 움직이고 엔티티가 액터를 따라간다(액터 → Mass), 떨어질 때 상태를 돌려준다. 엔진의 변환기(translator) 프로세서가 태그로 방향을 정한다(`MassActors/Public/Translators/MassSceneComponentLocationTranslator.h`의 `FMassSceneComponentLocationCopyToMassTag` / `CopyToActorTag`, `MassCharacterMovementTranslators.h`). 경계에서 상태 어긋남 버그가 나기 쉽고 가까운 개체의 로직이 액터 비용이 된다. (3) 섞기: 핵심 상태는 Mass, 액터는 IK·피격 물리·래그돌 같은 근거리 기능만 더하고 결과를 사건으로 Mass에 알린다.
- 우리가 (1)을 고른 이유: 이 프로젝트는 단계마다 로직이 같아야 표현 비용을 비교할 수 있고, E0에서 액터 비용의 가장 큰 몫이 CharacterMovement(1k에서 8.6ms)라 (2)는 그 비용을 다시 산다.

### Mass에서 AI는 어떻게 짜나: StateTree, BT, 태그 **설명 강조**

- 사용자 질문(2026-11-08): BT나 StateTree를 쓸 수 있나?
- StateTree: MassAI 플러그인에 Mass용이 있다. `MassAIBehavior/Public/MassStateTreeTrait.h`(엔티티에 붙임), `MassStateTreeProcessors.h`(실행), `MassStateTreeSchema.h`. Mass용 태스크(`Tasks/`: NavMesh 경로 따라가기, 스마트 오브젝트 찾기·사용, 바라보기). Mass Signal로 필요한 엔티티만 깨워 판단 비용을 줄인다. City Sample 보행자가 StateTree + ZoneGraph + 스마트 오브젝트 조합이다(구성은 City Sample 설정·에셋으로 다시 확인할 것).
- Behavior Tree: AI 컨트롤러·폰 전제라 엔티티에 바로 못 붙인다. BT 변환기(`MassTranslator_BehaviorTree`)는 액터 BT와 엔티티를 잇는 오래된 다리이고 City Sample은 꺼 둔다(`CitySample/Config/DefaultMass.ini`). BT를 쓰려면 하이브리드의 액터 구동(actor-driven) 방식으로, 액터가 됐을 때만 돌린다.
- 태그 + 프로세서(이 프로젝트 M1\~): 상태가 몇 개면 가장 싸고 단순하다. plan.md M4b(선택)가 태그 vs StateTree + Signal 비교다.

### 액터화 거리는 어떻게 정하나

- 사용자 질문(2026-11-08): 실제 게임이라면 액터화가 더 이른 시점(먼 거리)에서 되어야 하나. 현업 기준은 (1) 상호작용 반경 + 생성 지연 여유(액터 스폰은 시간 분할, `MassSimulationSettings` `DesiredActorSpawningTimeSlicePerTick` 1.5ms), (2) VAT와 액터의 차이가 보이기 시작하는 화면 크기, (3) 동시 액터 상한(`LODMaxCount` 500). 우리 시나리오는 상호작용이 피해 범위 8m뿐이라 15m면 충분하고 30m는 여유가 크다. 저격(30\~200m)은 VAT로 피격·죽기를 재생하는데, 실제 게임은 "맞힌 적은 거리와 상관없이 액터로" 같은 사건 기반 액터화도 흔하다(backlog 후보).
- 잰 결과(E3 (7), 2026-11-09, Test 3회, 프레임 p50, 괄호는 액터 수): 5k 15m 6.31(64) / 30m 6.21(263) / 50m 8.66(476), 20k 15m 12.27(270) / 30m 15.62(495) / 50m 15.48(493). 20k에서 30m와 50m가 같은 것은 액터 상한 500에 걸려서다. 상한이 걸리면 거리가 아니라 상한이 비용을 정한다. 5k는 GPU 병목이라 15m에서도 프레임이 줄지 않았다(Game Thread만 5.64 → 3.10). 전환 대책을 다 켠 상태에서는 세 거리 모두 눈에 띈 전환이 0이었다(튐 평균 2.89 / 2.60 / 0.78). 대책이 갖춰지면 거리는 화질보다 비용과 상한으로 정하게 된다.

### 액터와 VAT 인스턴스의 머티리얼을 왜 맞췄나

- 원본 Paragon 머티리얼(마스크·발광·금속 광택)과 VAT용 단순 머티리얼이 다르면 30m에서 전환될 때 색과 광택이 툭 바뀐다. 액터도 같은 단순 머티리얼을 써서 전환 때는 자세만 이어지면 되게 했다. 죽기 진홍색도 같은 값으로 그린다.

## 06 Simulation LOD

### Simulation LOD는 무엇이고 Representation LOD와 어떻게 다른가 **설명 강조**

- 사용자 요청(2026-11-09): 개념 설명을 글에 넣고 싶다. Representation LOD(M1\~M3)는 거리별로 "어떻게 그릴지"(액터 / VAT / 안 그림), Simulation LOD(M4)는 거리별로 "로직을 얼마나 자주 돌릴지"다. 한 줄로: 덜 그리기에 덜 생각하기를 더한다.
- 동작: `UMassSimulationLODTrait`이 거리 밴드로 High / Medium / Low / Off를 매기고 `FMassSimulationVariableTickParameters::TickRates`에 단계별 간격을 둔다. 같은 단계 개체가 같은 청크에 모이고, `TMassLODTickRateController`가 이번 프레임에 돌릴 청크만 고른다(`MassLOD/Public/MassSimulationLOD.h`, `MassLODTickRateController.h`).
- 정정(2026-11-09, 소스 확인 뒤): 누적 델타는 맞다(`MassLODTickRateController.h`, `Time − LastTickedTime`). 단 그 델타를 읽고 청크 필터를 건 프로세서만 건너뛴다. 엔진 이동·조향은 매 프레임 프레임 델타로 돌고 `TickRates`를 읽지 않는다. 회피가 High만 처리하는 것도 맞지만 LOD 태그가 있어야 한다(`bSetLODTags` 또는 가변 틱, 기본 둘 다 꺼짐). 기본 상한(100/200/300)이면 20k 중 약 19,400이 Off고, Off 개체는 `MoveTarget.Center`로 스냅된다(`MassNavigationProcessors.cpp:61`). 그래서 M4는 "엔진이 다 해 준다"가 아니라 "엔진이 등급·태그·누적 델타를 주고 우리 프로세서가 그 틀로 건너뛴다"로 다시 썼다(plan.md M4, engine-notes.md 5절).
- 글에서 강조할 것: City Sample도 같은 구조다. 자기 프로세서가 청크 LOD를 읽어 갱신 간격을 정한다(`MassZoneGraphAnnotationFragments.cpp:34-48`). "Simulation LOD를 켰다"는 문장은 어느 프로세서가 그 틀을 쓰는지까지 말해야 뜻이 있다.
- 얻는 것: 먼 개체만큼 Mass 로직의 Game Thread 비용이 준다. 회피 프로세서는 High만 처리해 먼 개체의 회피가 자동으로 빠진다(E4 (c)에서 가까운 개체만 비켜 가기).
- 잃는 것: 먼 개체가 간격마다 한 번에 움직여 끊겨 보인다(E4 (b)). 표현은 매 프레임 갱신되므로 보간을 넣을지가 쟁점이다.

### 로직 밴드와 표현 밴드의 경계는 왜 다른가 **설명 강조**

- 사용자 요청(2026-11-10): 독자도 궁금할 부분이다. 표현은 0\~30m 액터 / 30\~200m VAT 인스턴스 / 200m 밖 그리지 않음이고, 로직은 0\~80m 매 프레임 / 80\~200m Medium 간격 / 200m 밖 Low 간격이다.
- 다른 점 둘. (1) 로직 High(80m)가 액터 밴드(30m)보다 넓다. 접근과 범위 피해가 늦는 것이 화면 가까이의 VAT 인스턴스(30\~80m)에서 보이지 않게 80m까지 매 프레임 돌린다. (2) 표현은 200m 밖을 그리지 않지만 로직에는 Off가 없다. 그리지 않는 개체도 오브로 걸어와야 하고, 엔진의 Off는 위치를 이동 목표로 순간이동시킨다(`MassNavigationProcessors.cpp:61`).
- 80m와 200m는 저격 거리 구간의 경계와 같다. 표현 LOD는 화면 안팎을 가리지만 로직 LOD는 카메라 거리만 본다(`MassLODLogic.h:29-54`).

### 틱 간격을 0.5초로 적어도 0.2초마다 돈다 **설명 강조**

- 설정은 Medium 0.5초 / Low 1.0초인데 실제 주기는 낮은 카메라, 개체 20,000에서 약 0.20 / 0.31초였다(Development 빌드 값이고 2026-11-10 실행 순서 수정 전이다. Test 값은 M4 묶음에서 다시 나온다. Worklog/M4.md).
- 원인: 엔진 가변 틱은 엔티티가 드나든 청크를 간격과 무관하게 다음 프레임에 돌린다(`MassLODTickRateController.h:153`). 계속 죽고 다시 생기며 안쪽으로 흐르는 호드에서는 청크가 계속 수정된다. 설정 간격은 상한일 뿐이다.
- 글에서는 설정 간격과 실제 주기를 함께 적는다(2026-11-10 사용자 결정). 실제 주기 = 평균 프레임 시간 × 밴드 전체 개체 수 ÷ 그 프레임에 돈 개체 수.

### 틱을 줄일 것과 줄이지 않을 것 **설명 강조**

- 줄이는 것: 걷는 개체가 스스로 하는 갱신(이동 목표, 범위 피해). 줄이지 않는 것: 다른 주체의 질의(저격 대상 선택)와 사건으로 시작된 짧은 상태(피격·사망 타이머).
- 사례: 타이머까지 간격으로 돌렸더니 80m 밖에서 저격당한 개체가 피격 마지막 자세로 0.383초 서 있었다. 피격 클립은 0.667초에 끝나는데 틱은 저격 뒤 0.53초와 1.05초에 왔다(1.05 − 0.667 = 0.383). 타이머를 매 프레임 돌리자 최대 한 프레임(0.017초)이 됐다(Development, 낮은 카메라, 개체 20,000, Worklog/M4.md "사망 전환 지연").
- 필터를 읽는 프로세서는 그 값을 쓰는 엔진 LOD 프로세서 뒤에 돈다고 적어야 한다. 적지 않았더니 가끔 틱 한 번을 통째로 놓쳤다(0.9초, 1.35초).

### 출시 게임은 간격이 아니라 예산을 지킨다

- 2026-11-10 조사(검색 요약 수준이다. 발표 원문은 열어 보지 않았으므로 글에 쓰기 전에 원문을 확인한다). 공개 자료는 틱 간격 스케줄러보다 "개체 수 상한이 있는 단계 구분"과 "먼 무리를 묶어 단순하게 돌리기"를 말한다.
- 엔진에도 개체 수 예산 도구 `UE::Mass::FExecutionLimiter`가 있다(engine-notes.md 5절). 실험은 하지 않았다.

### 대형 미니언의 색과 죽기 클립

- 색 값은 선형 RGB다. 대형이 죽으면 소형 진홍 × 0.22다. 화면(sRGB)에서 밝기가 절반이 되는 선형 값이다(0.5^2.2 = 0.22, 계산값. measurement.md "2종").
- 대형은 죽은 뒤 마지막 자세로 멈춰 있다. 죽기 클립은 두 종류 모두 `Death_A`이고 로직의 사망 길이는 한 값을 같이 쓴다. 그대로 두기로 했다(2026-11-10 사용자 결정, Worklog/M4.md).

### Simulation LOD를 켰는데 프레임이 그대로다 **설명 강조**

- M4 묶음(Test 패키지 7ff3fce, 2종, 낮은 카메라): `m4mass` − `m3mass` 프레임 p50이 개체 10,000 / 20,000 / 30,000에서 −0.05 / +0.30 / −0.21ms다. A/A 잡음(p50 0.06, p95 0.27ms)과 3회 범위 안이다.

### 탑뷰에서 Game 스레드가 2ms 늘었는데 프레임은 같다 **설명 강조**

- 탑뷰 카메라, 개체 20,000: Game p50 4.79 → 6.93ms(+2.15), 프레임 p50 10.34 → 10.38ms(GPU 병목).
- 병렬 트레이스로 본 것: Game 스레드의 작업 대기(`WaitForTasks`)가 2.73 → 0.80ms로 줄고, 표현 LOD 프로세서가 0.14 → 2.10ms로 늘었다. 프레임 `Tick`은 10.31 / 10.38ms로 같다. Game 스레드가 쉬던 자리가 프로세서 안으로 옮겨 갔다. 간격을 0으로 둔 `m4off`에서는 수집기가 대신 기다린다(1.56ms). 기다림은 작업자 스레드의 이동 프로세서가 끝나는 시각에 풀린다(중앙값 차 0.00\~0.01ms).
- 추정으로 남은 것: 기전이 위치 프래그먼트 청크의 읽기·쓰기 충돌이라는 해석. 청크 단위 대기를 보여 주는 엔진 타이머가 없다.
- 틀린 가설 하나도 재료다. VAT 인스턴스 프로세서가 먼저 도는 순서가 원인이라 보고 순서를 고쳤더니 순서는 고쳐졌는데(961/961 프레임) 대기는 그대로였다(2.16 → 2.05ms). 되돌렸다(d80d390).
- 교훈: 스레드 시간 지표는 "일한 시간"이 아니라 "그 스레드가 그 구간에 머문 시간"이다. 기다림이 어디에 찍히는지에 따라 Game 스레드 수치가 달라진다. 프레임 시간과 함께 본다.

## 07 ISKM vs VAT

### ISKM은 무엇이고 VAT와 어떻게 다른가 **설명 강조**

- 사용자 요청(2026-11-09): 개념 설명을 글에 넣고 싶다. ISKM(Instanced Skinned Mesh, `UInstancedSkinnedMeshComponent`)은 엔진의 인스턴스 스켈레탈 메시다. MetaHuman Crowd Sample이 쓴다.
- VAT: 애니메이션을 텍스처로 굽고 머티리얼이 정점을 옮기는 정적 메시. 어디서나 돌고 싸지만 굽기가 필요하고, Bone 모드는 본 영향 4개 근사라 실제 스킨과 조금 다르며 클립 블렌딩은 직접 만든다(M2).
- ISKM: 실제 스켈레탈 메시를 GPU에서 스키닝한다. 애니메이션은 AnimSequence의 뼈 변환을 뽑은 데이터(`AnimSequenceTransformProviderData`)로 재생하고 블렌드 시간 크로스페이드·BlendSpace 트랙이 있다. AnimBP는 없다(`InstancedSkinnedMeshComponent.h`). 액터와 같은 메시·스킨이라 전환 때 모양 차이가 줄 수 있다.
- Mass 연결: `FMassSkinnedMeshInstanceVisualizationMeshDesc`로 등록, `UMassConsumeInstancedSkinnedMeshAnimationProcessor`가 엔티티 상태를 재생 데이터로 넘긴다. 5.8.4에도 동적 엔티티의 트랙 풀이 해제되지 않아 사망 때 엔티티를 재활용한다(engine-notes.md).
- M5에서 볼 것: 같은 원거리 개체 수에서 GPU·Game Thread·메모리 비용과 화질(전환 튐 점수 포함).

### ISKM 미니언 일부가 한 프레임씩 세로로 번진다 **설명 강조**

- 사용자 관찰(2026-11-11): 개발 빌드 20k P1에서 "미니언 전체가 가끔 번쩍인다". 진단해 보니 모션 블러가 일부 ISKM 인스턴스의 잘못된 세로 모션 벡터를 그린 것이었다. 몸 전체가 같은 속도를 받으므로 애니메이션 자세가 아니라 인스턴스의 이전 변환이 틀린 것이다. Lab이 넘기는 `PrevTransform`은 정상이었고, 엔진 경로는 확인하지 못했다(Worklog/M5.md "미니언 깜빡임 진단").
- 글에서 설명할 것: 모션 벡터가 무엇이고 모션 블러·TSR이 왜 그것을 읽는지, 인스턴스마다 이전 변환을 따로 넘겨야 하는 이유. 원인은 "미확정"으로 쓴다.
- 처리: 모션 블러는 엔진 기본(켬) 그대로 두고 측정했다([ADR-0007](Decisions/0007-keep-default-motion-blur.md)). 줄무늬를 줄이려고 촬영에서 모션 블러를 끈 영상이 있으면 캡션에 적는다.

## 00 시나리오와 측정 방법

### 호드는 도시 군중과 무엇이 다른가 **설명 강조**

- 사용자 요청(2026-11-09): 글감으로 다룬다. City Sample·MetaHuman Crowd는 흩어져 돌아다니는 군중 사이를 플레이어가 걷는다. 호드는 한 점(플레이어)으로 수렴한다. 그래서 같은 Mass 기법이라도 어디에 힘을 줘야 하는지가 달라진다.
- 밀도가 플레이어 주변에서 가장 높다. 근거리 액터 상한이 늘 꽉 찬다(E3 (7): 20k에서 30m와 50m가 같은 이유, 상한 500). 근거리 비용은 "거리"가 아니라 "상한과 우선순위"가 정한다. 우선순위는 거리 + 화면 안 + 접근 중이고, M3b의 대형 우선 중요도가 첫걸음이다.
- 플레이어가 자주 돌아본다. 뒤의 개체가 한꺼번에 화면에 들어온다. 화면 밖 Base 거리를 0으로 두면 돌아볼 때마다 수백 개가 동시에 액터가 되고 스폰 시간 분할(1.5ms/틱, `MassSimulationSettings.h:23`)에 걸려 몇 프레임에 걸쳐 나타난다. MetaHuman Crowd는 Base를 Visible의 절반쯤에 둔다(`MetaHumanMassCrowdVisualizationTrait.cpp:34-42`). P1은 1rpm 회전이라 이 상황을 늘 만든다. E3b (8)에서 Base 0 / 15m를 잰다.
- 사망·재생성 처리량이 크다. 도시 군중은 죽지 않는다. 우리는 초당 수십 개가 죽고 다시 생긴다(E2 (d)). M5의 엔티티 재활용은 호드에서 선택이 아니라 기본이다.
- 경로는 목표가 하나라 플로우 필드가 정석이다(추정, 일반 지식. Shabel 31:39의 ISM 11만 개 플로우 필드 데모가 현업 근거). 개체마다 NavMesh 경로 탐색을 하지 않는다. 장애물은 M5 뒤 "장애물 + 플로우 필드" 마일스톤에서.
- 근접 공격 판정이 있다. 우리는 오브 범위 피해로 대신하고 캡슐 콜리전을 껐다(E3 (6) 20k 1.55ms). 실제 게임은 여기서 판정 바디 비용이 더해진다.
- 히스테리시스(`MassLODCalculator.h:864-888`): 멀어질 때는 바로 낮은 LOD, 가까워질 때는 밴드 폭의 10%(샘플은 20%)만큼 더 들어와야 높은 LOD. 호드는 모두 가까워지기만 하므로 이 유예가 늘 작동한다. 30m 경계가 실제로는 27m에서 바뀐다.

### 원거리 공격(저격) 대상은 어떻게 고르나

- 처음: 80m 밖 전체에서 해시로 5명. 대부분 화면 밖(300\~450m)이라 보이지 않았다. 하늘에서 떨어지는 번개도 시험했지만 같은 이유로 안 보였다.
- 바꾼 것: 화면(카메라 시야) 안의 산 미니언만, 거리 구간 30\~80m 1 / 80\~200m 2 / 200m 밖 2. 30m 안은 곧 피해 범위에 들어오므로 쏘지 않는다(사용자 의견). 카메라 경로가 시간으로만 정해져 결정성이 유지되고, M0과 M1이 같은 대상을 쏜다.

### 환경이 수치를 흔든 사례 **설명 강조**

- 밤 E0: 모니터를 끄고 PC를 비워 둔 지 약 1시간 뒤부터 모든 조건이 느려졌다(static N=2000 P1 33.7ms). 아침에 같은 조건을 다시 재니 25.0ms로 첫 측정(24.6ms)과 같았다.
- 단서: 세 실행끼리는 같았지만, full(먼저 잰 것)은 그대로이고 뒤쪽만 나빠졌고, uro가 full보다 느려지는 설명 안 되는 결과가 나왔다.
- 처리: 오염된 14조건을 따로 빼고(`Saved/Profiling/CSV/invalid-idle/`) 다시 쟀다. 측정 규약에 "모니터 켜 둠, 화면 끄기 안 함, 측정 중 PC 사용 안 함"을 추가했다. 원인(유휴 유지 관리 또는 전원 상태)은 추정이다.
- 교훈: "세 실행이 일치한다"만으로는 부족하고, 결과가 원리와 맞는지(uro가 full보다 느릴 수 있나?) 보고 같은 조건을 다시 재서 확인한다.
