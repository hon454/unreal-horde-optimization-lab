# M1 작업 기록

## 2026-11-07 Mass 코어 구현 (-LabStage=M1)

- EntityConfig를 실행 시 C++로 만든다(ADR-0005). 에셋용 `UMassEntityConfigAsset::AddTrait(TSubclassOf)`는 에디터 전용이라 Test 패키지 빌드가 실패했고, `FMassEntityConfig::AddTrait(Trait&)`로 바꿨다.
- 첫 실행에서 로직은 돌았지만 아무것도 그려지지 않았다. LOD 수집·표현 LOD·표현 프로세서가 엔진 기본값으로 꺼져 있어 `Config/DefaultMass.ini`로 켰다. 다음 실행은 회색이었다. 바탕 머티리얼에 ISM 사용 플래그가 없어서였고 `Scripts/make-static-minion.py`가 켠다.
- 개발 빌드(N=2000)에서 범위 처치가 M0의 약 60%였다. 엔티티 하나를 추적해 프레임이 100ms를 넘는 동안 이동이 느려지는 것을 찾았다. 엔진 Mass 이동이 프레임 시간을 0.1초로 자른다(engine-notes.md 11절). N=300에서는 처치·재생성 수가 M0과 같았다.
- Test 패키지 시험에서 GPU 29ms. 움직이는 ISM 2,000개가 Lumen 장면에 들어가서였다. 모든 단계에서 미니언 표현을 Lumen 장면에서 뺐다(사용자 결정, M0 static 포함).

## 2026-11-08 E1 측정 (M1-mass-*, M1-massst-*, M1-massav-*, M1-massdir*-*, M1-massevt*-*)

- (a) 컨테이너 전환: N@16.7ms 1,196(M0 static) → 20,577. (b) 병렬 처리 끔은 차이 없음. (c) 비켜 가기는 20k 프레임 57.7ms라 M2\~M5는 끈다(사용자 결정, plan.md 수정). (d) 바로 깎기와 이벤트 엔티티는 구별되지 않음.
- (d) 첫 구현은 피해를 한 건도 넣지 못했다. 섞지 않은 `HashCombineFast`가 작은 입력에서 고르게 퍼지지 않아 확률 선택이 늘 실패했고 `MurmurFinalize32`로 섞었다.
- Game Thread 시간이 워커 대기를 빼서 `massav`의 비용을 놓쳤다. N@16.7ms 판정에 프레임 시간을 넣었다(사용자 결정). 모든 값이 5\~8% 보수적으로 바뀌었다.
