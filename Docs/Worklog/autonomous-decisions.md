사용자가 자리를 비운 동안 코디네이터가 [plan.md](../plan.md) "품질 계획"의 Q2 나머지\~Q6을 묻지 않고 진행하며 내린 결정을 적는다. ADR 초안은 쓰지 않았다. 사용자가 이 보고서를 검토한 뒤에 쓴다.

2026-11-12 덧붙임: 사용자 지시로 ADR 초안 넷을 "제안됨"으로 썼다. [ADR-0010](../Decisions/0010-final-representation-bands.md)(D11, D12, D15, D18), [ADR-0011](../Decisions/0011-entity-driven-crowd-particles.md)(D1\~D4, D6, D17), [ADR-0012](../Decisions/0012-ablation-switches-and-quality-metrics.md)(D9, D10, D13), [ADR-0013](../Decisions/0013-full-batch-runner-and-condition-table.md)(D8, D16, D19). ## 결정

항목마다 같은 순서로 적는다: 결정, 왜 그때 필요했는가, 고른 안과 근거, 버린 대안, 바꾸면 다시 할 일, 확인하지 못한 것.

### D1. Niagara 입자 수를 호드 총수 N에 묶는다

- **결정.** 배경 무리의 입자 수를 고정하지 않고 N에 비례하게 둔다. N 1만이면 스폰율이 초당 60개, 살아 있는 입자가 약 16,000개다(계산값, 식은 [Q2.md](Q2.md)).
- **왜 그때.** Q2 코드 연결에서 사용자 변수(`SmallRate`, `LargeRate`)에 넣을 값을 정해야 했다. 자율 진행 전에는 추천안으로 잠정이었다.
- **근거.** 200m 경계를 지나는 실제 미니언의 흐름(초당 마리 수)과 입자의 흐름을 같게 맞추면 경계에서 밀도가 끊기지 않는다. 실제 미니언의 흐름이 N에 비례하므로 입자도 N에 비례해야 한다.
- **버린 대안.** 고정 입자 수(예: 16,000). 보조 묶음(5k, 2만, 3만)에서 배경만 같은 밀도로 남아 경계가 눈에 띈다. 대신 단계 7의 비용이 N과 무관해 표가 단순해진다.
- **바꾸면.** `ALabGameMode`의 사용자 변수 계산 한 곳. 단계 7·8과 빼 보기 "Niagara" 행, 보조 묶음의 단계 7·8을 다시 잰다.
- **확인하지 못한 것.** 3만에서의 입자 비용(Q2 코드 단위와 Full1에서 본다).

### D2. Niagara 입자는 그림자를 드리우지 않는다

- **결정.** 메시 렌더러의 그림자를 끈다.
- **왜 그때.** Q2 1단위에서 시스템 초안을 만들 때 정했고 사용자가 바꾸지 않았다.
- **근거.** 200m 밖 입자는 화면 높이의 1% 미만이다([Q2.md](Q2.md) 계산). 그림자 패스에 16,000 인스턴스를 더하는 비용에 비해 화면 이점이 없다. 실제 미니언의 그림자는 켠 채로다(measurement.md 확정값).
- **버린 대안.** 그림자 켬. 경계 바로 밖에서 그림자 유무가 달라 보일 수 있는 것을 없앤다. 비용은 재지 않았다.
- **바꾸면.** `NS_LabCrowd`의 렌더러 속성 하나(에디터 작업). 단계 7·8과 빼 보기 "Niagara" 행을 다시 잰다.
- **확인하지 못한 것.** 200m 경계에서 그림자 유무 차이가 눈에 띄는지(Q2 코드 단위의 움직이는 화면에서 본다).

### D3. `-LabCrowdFx`의 기본값은 0이고, 켜는 것은 변형 이름으로 한다

- **결정.** 인자 기본값은 끔이다. 사다리 7·8단계와 빼 보기 표의 최종 구성은 변형 이름(`q2crowd`에서 출발, Q5에서 사다리 이름으로 정리)이 켠다.
- **왜 그때.** Q2 코드 연결에서 인자의 기본값을 넣어야 했다.
- **근거.** 단계는 한 빌드 안의 실행 모드이고(ADR-0004) 기존 단계 1\~6의 동작이 바뀌면 안 된다. 기본값이 끔이면 옛 변형 이름이 옛 동작 그대로다. `run-bench.ps1`은 고칠 수 없어서 변형 이름으로 켤 수 있어야 한다.
- **버린 대안.** 기본값 켬(최종 구성이 기본). 인자 없이 실행한 화면이 완성본이 되지만 단계 1\~6의 변형이 모두 끔을 명시해야 하고 빠뜨리면 사다리가 오염된다.
- **바꾸면.** `FLabConfig`의 기본값 한 줄과 변형 표. 측정값은 변형이 같은 값을 명시하는 한 다시 잴 필요가 없다.
- **확인하지 못한 것.** 없음.

### D4. 200m 경계는 페이드 없이 둔다(움직이는 화면을 보고 다시 판단)

- **결정.** 입자는 200m에서 그대로 사라진다. Q2 3단위의 경계 화면에서 튀어 보이면 그때 고친다(결과는 아래 "D4 뒤").
- **왜 그때.** 사용자에게 움직이는 화면을 본 뒤 묻기로 했던 항목이고, 자율 진행에서는 코디네이터가 화면을 보고 정해야 한다.
- **근거.** 200m에서 미니언은 화면 높이 약 8px이다([Q2.md](Q2.md) "장면 수치", 계산값). 사라지는 입자 수와 나타나는 미니언 수는 초당 같다(D1).
- **버린 대안.** 마지막 수 m에서 크기 줄이기(에셋 수정, 에디터 작업 필요), 디더 페이드(새 머티리얼과 셰이더 비용), 5m 겹치기(경계 밀도 두 배).
- **바꾸면.** `NS_LabCrowd`에 Scale Mesh Size 모듈 하나(Unreal MCP 세션). 단계 7·8과 빼 보기 "Niagara" 행을 다시 잰다.
- **확인하지 못한 것.** 3단위 결과를 기다린다.

### D4 뒤. 입자가 사라지는 자리를 오브에서 172.8m로 옮긴다

- **결정.** 페이드는 넣지 않고, 입자의 안쪽 반경 기본값을 200m에서 172.8m(계산식)로 바꾼 3단위의 수정을 받아들인다. 바깥 반경 1,000m(사용자 확정)는 그대로다.
- **왜 그때.** Q2 3단위(72ad2e6)에서 실제 미니언과 함께 본 화면에 경계가 약하게 보였다. 사다리 7단계의 화면이 이 값에 달려 있어 Q3 전에 정해야 했다.
- **근거.** 실제 미니언은 카메라에서 188m에 나타난다(Off→Low 히스테리시스, `MassLODCalculator.h:864-886`, 그리는 끝은 카메라 기준 거리다). P1 카메라가 오브 뒤 15m라 화면 정면에서는 오브로부터 약 173m다. 입자를 오브 200m에서 지우면 정면에 약 27m의 빈 띠가 생긴다. 스크린샷 [u3-boundary-native.jpg](../../Measurements/Q2/shots/u3-boundary-native.jpg)(위부터 200m, 173m, 끔)와 4배 확대 `u3-boundary-zoom-inner200.jpg`·`u3-boundary-zoom-inner173.jpg`에서 173m 쪽은 밀도가 이어진다. 코디네이터가 1:1 비교 시트를 직접 봤다: 켬과 끔의 차이(수평선까지 차는가)는 분명하고, 200m와 173m의 차이는 1:1에서는 미세하다.
- **버린 대안.** 200m 그대로(빈 띠가 남는다). 크기 줄이기·디더 페이드(에셋 수정이 필요하고 빈 띠의 원인인 거리 기준 차이를 고치지 못한다).
- **바꾸면.** `-LabCrowdFxInnerM=200`으로 되돌려 볼 수 있다(개발용 인자). 기본값은 `LabConfig`의 계산 함수 한 줄. 입자 수가 3.4% 달라지므로(1만에서 16,000 ↔ 16,544, 로그 실측 16,547) 단계 7·8과 빼 보기 "Niagara" 행을 다시 잰다.
- **확인하지 못한 것.** 식이 P1 카메라의 오프셋 15m에 맞춘 것이라 다른 카메라에서는 방향마다 어긋난다(P2는 입자가 화면에 없다). 사람이 움직이는 화면으로 본 판단. 카메라가 도는 중 입자가 번져 보이는 원인(모션 벡터로 추정, 확인하지 않음).

### D6. 입자와 실제 미니언의 톤 차이는 고치지 않고 남긴다 (사용자 판단 필요)

- **결정.** 입자가 실제 미니언보다 약간 밝고 푸르게 보이는 것을 그대로 둔다.
- **왜 그때.** 3단위의 경계 화면에서 밀도 단차를 없앤 뒤 남은 차이다.
- **근거.** 원인은 입자에 그림자가 없고(D2) 머티리얼 인스턴스가 다른 것으로 추정한다(확인하지 않음). 고치려면 에디터 작업(머티리얼 또는 그림자)이 필요하고, 그림자를 켜면 비용이 달라져 D2와 함께 정해야 한다. 1:1 화면에서 경계선으로 읽히지는 않는다.
- **버린 대안.** 입자 그림자 켬(비용 미측정). 입자 머티리얼의 색을 맞추는 보정(근거 없는 값이 하나 는다).
- **바꾸면.** `NS_LabCrowd` 또는 `MI_LabCrowd*`(Unreal MCP 세션). 단계 7·8과 빼 보기 "Niagara" 행을 다시 잰다.
- **확인하지 못한 것.** 원인.

### D7. Niagara 에셋 워밍업(268초)은 그대로 둔다

- **결정.** 안쪽 반경이 줄어 입자 수명이 275.7초가 됐지만 에셋의 워밍업 268초를 올리지 않는다.
- **왜 그때.** 3단위가 보고했다. 올리려면 에디터를 다시 띄워야 한다.
- **근거.** 모자란 7.7초 동안 가장 안쪽 약 23m가 덜 차 있고, 측정 워밍업 15초 안에 다 찬다(measurement.md 벤치마크 절차). 측정과 촬영에 영향이 없다.
- **버린 대안.** 워밍업 280초 이상. 에디터 작업 한 번과 활성화 스파이크가 조금 는다.
- **바꾸면.** `NS_LabCrowd` 시스템 속성 하나. 다시 잴 것은 없다.
- **확인하지 못한 것.** 활성화 때 워밍업 스파이크의 크기(Full1의 `spikes.py`로 본다).

### D8. `run-bench.ps1`의 변형 목록에 `q2crowd`를 더하지 않는다

- **결정.** `run-bench.ps1`은 고치지 않는다(사용자 지시). 총괄 묶음 러너는 변형 이름 대신 `-ExtraArgs`로 스위치를 넘기거나 `run-bench.ps1`을 거치지 않는 새 러너를 쓴다(Q5에서 정한다).

- **버린 대안.** ValidateSet에 한 단어 추가. 가장 간단하지만 금지된 파일이다.
- **바꾸면.** 사용자가 허락하면 ValidateSet에 더하고 러너의 우회를 걷어낸다.

### D5. 세션 시작이 거부되어 작업 단위를 서브에이전트로 돌린다

- **결정.** Q2 3단위부터 작업 단위를 코디네이터 안의 서브에이전트(같은 모델과 추론 수준)로 진행한다. 세션 시작이 다시 되면 세션으로 돌아간다.
- **왜 그때.** 2026-11-12 Q2 3단위 세션 시작이 "자동 이벤트로 시작된 턴에서는 세션을 시작할 수 없다"는 이유로 거부됐다. 사용자가 미리 정해 둔 대체 경로다.

- **버린 대안.** 제안 카드로 남기고 기다리기. 사용자가 없어 진행이 멈춘다.
- **바꾸면.** 없음. 서브에이전트는 단계 메시지를 보낼 수 없어 진행은 Worklog 절의 "진행" 줄로만 남는다.

### D9. 빼 보기 아홉 행은 "변형 + 인자 하나"로 고르고, 새 인자는 끄는 방향으로만 듣는다

- **바꾸면.** `LabConfig.cpp`의 스위치 해석과 `ablation-check.py`의 기대값 표. 빼 보기 표 해당 행을 다시 잰다.
- **확인하지 못한 것.** Test 패키지에서의 동작. Development 참고(1만 P1, 1회)로는 엔티티 풀(−0.11ms)·전환 대책(−0.11ms)·배경 무리(−0.06ms, GPU는 약 4ms 차이)·하이드레이션(−1.73ms, 빼면 빨라진다) 행이 프레임 이점을 보이지 않는다. 이 넷의 이점은 프레임이 아니라 전환 점수, 화면, 스파이크로 보여야 한다.

### D14. Test에서 본 배경 무리의 비용

### D15. 하이드레이션 액터의 캡슐 콜리전 기본을 끈다(사용자 결정이 코드에 빠져 있었다)

- **결정.** Mass 하이드레이션 액터(사다리 4\~8단계, 빼 보기 표, 하위 실험)의 캡슐 콜리전 기본을 끈다. 하위 실험은 "켬"(`S8-col` = `q4final -LabActorCollision=1`)이다. M0 액터 기준선(단계 1)은 지금 동작 그대로 둔다. 바꾼 뒤 다시 패키징한다.

- **영향.** M3b 이후의 묶음(M3b, M4, M5, Q4)은 모두 콜리전을 켠 액터로 잰 값이다. 공개 수치는 Full1에서만 만들므로 고칠 표는 없다. Q4의 최종 구성 선택(D11)은 콜리전을 켠 값으로 했다. 끄면 프레임이 줄어드는 방향이라(2만 P1에서 15.58 → 14.12ms, plan.md M3b) 13.3ms 조건은 그대로 지켜지고, 전환 거리는 이미 밴드 끝 79m라 더 올릴 곳이 없다. 1b단위에서 1만 P1 참고값(끔, 켬 1회씩)을 잰다.

### D16. 총괄 묶음 러너는 `run-bench.ps1`을 거치지 않는 새 스크립트다

- **결정.** `Scripts/run-full.ps1`이 패키지 exe를 직접 부르고 `run-bench.ps1`의 절차(앞 창 검사, r0 버리기, 같은 라벨 거부)를 옮겨 쓴다. 조건과 기대 메타데이터는 `Scripts/full-conditions.json` 하나에 둔다. 회차를 바깥 루프로 돈다(r1 전 조건 → r2 → r3).
- **왜 그때.** Q5의 러너 설계. D8에서 미룬 선택이다.
- **근거.** `run-bench.ps1`은 고칠 수 없고 새 변형 이름(`q2crowd`, `q4final`)과 plan.md의 라벨 형식(`Full1-<단계>-<변형>-N<수>-<프리셋>-r<회차>`)을 받지 못한다. 회차를 바깥에 두면 몇 시간짜리 묶음의 표류가 조건마다 고르게 퍼진다.
- **버린 대안.** `run-bench.ps1 -ExtraArgs`로 감싸기(라벨이 plan.md 형식과 달라지고 변형 이름이 `m5bounds`로 남는다).
- **바꾸면.** 러너만. 측정값에는 영향이 없다(절차가 같다는 것을 예행 묶음에서 Q4 값과 견줘 본다).
- **확인하지 못한 것.** 옮긴 절차가 `run-bench.ps1`과 같은 값을 내는지(예행 묶음).

### D17. 배경 무리 입자를 실제 엔티티 위치에 그린다(사용자 승인, 2026-11-12)

- **결정.** 사용자가 돌아와 경계에서 개체가 사라지고 생기는 것이 눈에 띈다고 했고, 추천안을 승인했다: 그려지지 않는 엔티티의 위치를 매 프레임 Niagara에 배열로 넘겨 그 자리에 입자를 그리고, 톤 차이(D6)도 맞춘다. `Full1` 전에 넣는다. D4("페이드 없이 둔다")와 D2("입자 그림자 끔")는 이 결정으로 바뀐다.
- **코디네이터가 고른 세부.** (1) 엔티티는 맵 반경 500m 안에만 있으므로 500\~1,000m는 독립 이미터를 안쪽 반경 500m로 남긴다. 바깥 반경 1,000m는 사용자 확정값이라 유지한다. 500m에서 개체는 화면 높이 약 3.7px다. (2) 위치는 매 프레임 모은다(1Hz는 카메라가 물러날 때 최대 한 주기 겹침이나 빔이 생긴다). (3) 그림자는 엔티티 구동 이미터만 켠다. 실제 미니언 쪽을 바꾸면 사다리 앞 단계의 조건이 바뀐다. (4) 옛 방식은 `-LabCrowdFxEntity=0`으로 재현한다(가능하면).
- **근거.** 원인은 입자와 미니언이 대응하지 않는 것이다(입자는 오브 172.8m에서 사라지고, 미니언은 카메라 188m에서 다른 자리에 나타난다). 200m 밖 엔티티는 3m/s 직선 이동이라(`ULabOffMoveProcessor`, `LabMassProcessors.cpp:255-274`) 마지막 갱신 위치와 시각에서 외삽한 값이 정확하다. Array DI는 GPU 이미터에서 읽을 수 있다(`NiagaraDataInterfaceArray.h:106`).
- **버린 대안.** 겹쳐서 디더 페이드(개체가 대응하지 않아 어른거림이 남는다). 톤만 맞추기(위치 불일치가 남는다). 500m 밖 비우기(사용자 확정값 1,000m와 어긋난다).
- **Niagara의 값어치를 재는 조건을 더한다(사용자 승인).** 같은 200m 밖 엔티티를 VAT로 그리는 `q4final` + `-LabFarCull=0 -LabCrowdFx=0`을 부속 실험으로 넣어 같은 묶음에서 비교한다. 지금까지의 근거는 간접이다: M3 묶음에서 200m 밖을 지우자 60fps 최대 총수가 약 2만에서 35,763이 됐고, Q4 묶음에서 입자 16,544개는 프레임 p50 +0.87ms, GPU p50 +3.9ms였다. 조사에서 GPU 쪽은 Niagara가 싸다는 근거가 없었다.
- **바꾸면.** `q2crowd`·`q4final`의 뜻이 바뀌므로 Q2\~Q4 묶음의 배경 무리 수치는 `Full1`과 견줄 수 없다. 에셋 `NS_LabCrowd`, `Scripts/create-crowd-fx.md`, 조건 표.
- **확인하지 못한 것.** 엔티티 구동 방식의 실제 비용, 걷기 위상이 실제 미니언과 맞는지, 그림자를 켠 비용. 구현 뒤 채운다.

### D18. 표현 LOD 네 칸을 재편한다(사용자 승인, 2026-11-12)

- **결정.** 최종 구성(`q4final`)의 화면 안 표현을 액터 0\~40m, ISKM 40\~80m(그림자 켬), ISKM 80\~200m(그림자 끔), 200m 밖 엔티티 구동 입자로 바꾼다. `Full1` 전에 반영한다. 사용자가 곁가지 세션에서 재편안을 승인했고, 이 세션에서 "반영해"로 다시 확인했다. D11(전환 거리 79m)은 이 결정으로 바뀐다.

- **버린 대안.** 저품질 액터를 40\~80m에(M3 E3 (5)에서 이득 약 0.45ms, URO로 끊긴다), 80\~200m를 VAT로(고정 바운드 뒤 ISKM이 프레임 p50 0.36ms 낮았다), 79m 유지.
- **바꾸면.** 사용자 확정값 둘이 바뀐다: 미니언 그림자(80m 밖에서 끔), 최종 구성의 액터 구간(40m). 부속 실험 이웃 점은 30m·50m로 옮기고 옛 값 79m를 비교 조건으로 둔다. 사다리 4\~7단계(30m)는 그대로다.
- **확인하지 못한 것.** 40m 건너뜀 수치는 액터 콜리전을 끄기 전 묶음의 값이고 소형 액터는 잰 적이 없다. 그림자 끄기의 비용과 구현 방식은 코드 단위(Q4b)에서 채운다. 이점이 보이지 않으면 그대로 보고한다.

### D19. 조건 표는 최종 구성의 단계별 기술과 성능 변화만 잰다(사용자 결정, 2026-11-12)

- **근거.** 79m는 "80m 밴드를 넘지 않는 최댓값"이라는 탐색의 흔적이라 표에 나오면 따로 설명이 필요하다. 40m의 근거는 사다리 7단계(30m)와 8단계(40m)의 애니 건너뜀 비율로 `Full1` 안에서 보인다. Niagara 대 ISKM은 `L8` 대 빼 보기 `A8-farcull`로 읽는다(Q2b 뒤로 `A8-farcull`은 200m 밖 엔티티를 입자 대신 ISKM으로 그리는 조건이다).
- **함께 정한 것.** 엔티티 구동 입자의 그림자는 원거리 그림자 스위치(`-LabFarShadow`)를 따른다(Q2c). 최종 구성은 80m 밖 ISKM과 입자 모두 그림자 끔이다. D17의 "(3) 그림자는 엔티티 구동 이미터만 켠다"는 이 결정으로 바뀐다. 그림자 켠 비교 조건(2×2)은 넣지 않는다.
- **바꾸면.** 조건 표와 plan.md "측정 목록". `-LabCrowdFxOuter` 인자는 코드에 남는다.
- **확인하지 못한 것.** `A8-farcull`에서 엔티티 입자가 0개인지(Q2c 세션이 확인 중). 틀리면 `S8-fariskm`을 남긴다.

### D21. 참고 묶음 `Ref1`은 창 해상도 1280×720으로 잰다(2026-11-13)

- **결정.** 참고 묶음은 `run-full.ps1 -Batch Ref1 -Only ablation,aa -ExeArgsPrefix "-ResX=1280 -ResY=720"`로 잰다. 조건은 빼 보기 열 행과 `L8`이다(34회).
- **근거.** `Full2`의 `L8` 1만 P1은 Game p50 7.65ms, GPU p50 5.72ms로 이미 게임 스레드가 병목이다. 그래도 GPU에 막힌 행이 남는다(`A8-hydrate`: Game 3.80 < GPU 5.76, `A8-iskm`: GPU 6.95). 측정 세션의 짧은 시험에서 1280×720은 GPU 3.04ms, Game 7.62ms였다. 이 값이면 모든 행에서 게임 스레드가 병목이 된다. 창 해상도 인자는 코드 변경과 재패키징이 없다.
- **버린 대안.** `r.ScreenPercentage`(게임이 시작 때 100으로 고정해 코드 변경과 재패키징이 필요하다. 같은 패키지 조건이 깨진다). 1920×1080(GPU 4.09ms라 `A8-hydrate`가 여전히 GPU에 막힌다). 참고 묶음을 건너뛰기(사용자가 재기로 정한 묶음이고 약 1시간이면 된다).
- **한계.** `-ExeArgsPrefix`는 러너 시험용 인자였고 측정에 쓰는 것은 처음이다. `L8`이 묶음 끝에 몰려 시간 순서가 조건과 섞인다. 이 묶음은 그 안에서만 비교한다.
- **바꾸려면.** 다른 해상도나 방법으로 새 묶음 이름(`Ref2`)을 써서 다시 잰다.

### D22. ISKM의 이점은 GPU 시간과 기능으로 적는다(2026-11-13)

- **결정.** README와 글은 ISKM의 이점을 "프레임 시간이 줄었다"로 쓰지 않는다. "GPU 시간이 줄고, 굽기 단계가 없고, 원본 메시의 LOD를 쓰며, 블렌딩을 쓸 수 있다"로 쓴다. 이 프로젝트가 블렌딩을 쓰지 않는다는 것도 적는다. 사용자가 2026-11-13 채팅에서 이 서술에 동의했다.
- **근거.** `Full2`에서 ISKM을 VAT로 바꾸면(`A8-iskm`) GPU p50이 +1.23ms, Game p50이 −0.33ms, 프레임 p50이 −0.21ms다. 병목이 게임 스레드라 GPU 이점이 프레임 시간에 보이지 않는다. 블렌딩은 engine-notes.md "ISKM 블렌딩" 행이 근거다.
- **버린 대안.** 프레임 시간으로 계속 적기(`Full2`에서 거짓이 된다). 최종 구성의 40\~200m를 VAT로 되돌리기(승인된 ADR-0010의 결정이고, 0.21ms는 차이 판정의 경계에 가깝다. 되돌리면 전 조건을 다시 재야 한다).
- **사용자가 볼 것.** 프레임 시간만 보면 40\~200m는 VAT가 0.2ms 빠르다. ISKM을 유지하는 근거가 GPU 여유와 기능이라는 점에 동의하지 않으면 ADR-0010을 대체하는 ADR이 필요하다.

### D23. 참고 묶음과 80m 밖 그림자의 다루는 법(2026-11-13)

- **결정.** 참고 묶음 `Ref1`은 README 그림에 넣지 않는다. 글 08·09에서 하이드레이션 액터의 게임 스레드 비용을 말할 때만 조건을 풀어 쓴다. 80m 밖 그림자 끔은 그대로 둔다. 문서는 "GPU 시간 0.39ms, 프레임 시간은 구별되지 않는다"로 고친다.
- **근거.** `Ref1`은 `A8-hydrate` 한 행(−3.73ms)을 빼면 `Full2`와 0.2ms 안에서 같다. 그림자 끔은 ADR-0010의 승인된 결정이고, `Full1`의 +1.40ms라는 근거는 `Full2`에서 +0.39ms(GPU)로 줄었을 뿐 방향은 같다.
- **버린 대안.** README에 참고 묶음 그림 추가(값이 거의 같아 독자가 얻는 것이 적다). 80m 밖 그림자 다시 켜기(품질은 오르지만 승인된 결정을 바꾸고 다시 재야 한다).
- **사용자가 볼 것.** GPU에 3ms쯤 여유가 생겼다. 80m 밖 그림자를 켜도 프레임 시간이 구별되지 않으니, 품질을 위해 켜는 선택이 가능하다. 켜려면 새 ADR과 재측정이 필요하다.

### D24. 화면은 7·8단계만 다시 찍는다(2026-11-13)

- **결정.** 촬영 묶음 `Pre6`은 7·8단계만 찍는다. 1\~6단계 화면은 `Pre5`의 것을 둔다.
- **근거.** 패키지에서 바뀐 것은 200m 밖 입자 메시뿐이다. 1\~6단계에는 입자가 없다. 1\~6단계의 프레임 값은 0.1\~0.6ms 달라졌지만 녹화 부하 때문에 HUD 값은 원래 측정값과 다르다.
- **버린 대안.** 여덟 단계를 모두 다시 찍기(약 10분 더 걸리고 LFS에 약 50MB가 더 쌓인다).
