### 설계 선택과 이유

- **컴포넌트를 0개로 두었다.** 루트 컴포넌트를 두면 위치를 컴포넌트에도 써야 하고, 그 비용은 "데이터를 든 곳과 순회 방식"이 아니다. 위치는 액터 멤버 `Transform`이다.
- **순회는 한 번이다.** 개체마다 접근 → 조향 → 힘 → 이동 → 회전 → 범위 피해 → 저격 후보 → 상태 타이머 → 30m 집계 → ISM 쓰기를 차례로 한다. 2단계는 프로세서마다 청크를 따로 순회한다.
- **프레임 안의 순서는 2단계와 같게 맞췄다.** 2단계의 태그는 플러시에서 바뀐다. 그래서 매니저도 순회 시작 때의 상태로 갈래를 고른다. 이 프레임에 죽거나 저격당한 개체의 타이머는 다음 프레임부터 준다.
- **이동은 엔진 프로세서의 식을 옮겼다.** 조향(Move 갈래), 힘 적용, 이동, 회전이다. 파라미터는 엔진 구조체의 기본값을 읽는다. 회전 함수는 엔진 헤더(`MassNavigationUtils.h`)의 것을 그대로 부른다. 줄 번호는 engine-notes.md 31절에 있다.
- **멈춘 개체도 조향·힘·회전을 계산한다.** 엔진의 세 프로세서가 코드 구동 태그를 요구하지 않기 때문이다. 위치만 옮기지 않는다.
- **그리기는 같은 설정의 ISM에 같은 호출을 한다.** 2단계는 전 개체가 `CanBeSeen`이라 엔진이 매 프레임 개체마다 `UpdateInstanceTransformById`와 `SetPreviousTransformById`를 부른다. 매니저가 같은 두 호출을 한다. 컴포넌트 설정은 엔진이 만드는 줄을 그대로 따랐다(그림자 켬, Movable, 콜리전 없음, 컬 거리 0\~1,000,000, Lumen 장면 제외).
- **죽은 개체는 액터를 지우고 새로 만든다.** 2단계가 엔티티를 파괴하고 새로 만드는 것과 같은 길이다.
- **이펙트와 사망 수는 오브가 맡는다.** 모든 단계가 같은 이펙트 코드를 쓴다.

### 2단계와 남은 차이

바꾸려던 변수(데이터를 든 곳, 순회 방식)에 딸려 온 것과 그렇지 않은 것을 나눠 적는다.

| 차이 | 2단계 | `manager` | 변수에 딸린 것인가 |
| --- | --- | --- | --- |
| 스레드 | 로직 프로세서가 워커에서 병렬로 돈다(`mass.FullyParallel=1`). ISM 갱신만 게임 스레드다 | 전부 게임 스레드 한 곳이다 | 순회 방식에 딸린다. 병렬 몫만 가르려면 2단계를 `-LabFullyParallel=0`으로도 잰다 |
| Mass의 LOD·표현 프로세서 | LOD 수집, 표현 LOD 계산, 표현 프로세서가 전 개체를 돈다 | 없다. 프로세서는 등록돼 있지만 엔티티가 없어 빈 순회다(1단계와 같다) | Mass의 몫이다 |
| 인스턴스 ID 찾기 | 엔티티 → 인스턴스 ID 해시 맵을 개체마다 찾는다 | 액터 멤버에 ID를 든다 | 데이터를 든 곳에 딸린다 |
| ISM에 쓰는 시점 | 로직은 PrePhysics, ISM 쓰기는 PostPhysics 단계 끝(`EndVisualChanges`) | 매니저 틱(TG_PrePhysics) 안에서 바로 쓴다 | 순회 방식에 딸린다. 그리는 프레임은 같다 |
| 새 개체의 첫 지난 변환 | `FMassRepresentationFragment::PrevTransform` 기본값(항등)이다 | 스폰 변환과 같다 | 아니다. 새 개체의 첫 프레임 모션 벡터만 다르다(초당 약 14개) |
| 새 개체가 그려지는 프레임 | 표현 프로세서가 표현을 정한 뒤 인스턴스가 붙는다 | 스폰한 프레임에 붙는다 | 아니다. 한두 프레임 차이다 |
| UObject 수 | 엔티티는 UObject가 아니다 | 액터 N개가 GC 대상이다 | 데이터를 든 곳에 딸린다 |
| 번개 대상 | 청크 병렬 결과를 잠금으로 모은다 | 순회 안에서 고른다 | 순회 방식에 딸린다. 고르는 규칙은 같다 |

## 트레이스: MgrT1

### Game 차이의 출처

게임 스레드에서 `manager`가 2단계보다 짧은 시간(프레임당 ms, 트레이스 한 회):

| 타이머 | 1만 | 2만 |
| --- | --- | --- |
| `Tick_Engine` | −1.30 | −2.90 |
| `UWorld_Tick` | −1.28 | −2.74 |
| `LabCrowdManager Tick` − (`PrePhysics` + `PostPhysics`) | −1.23 (4.00 − 5.23) | −2.64 (8.40 − 11.04) |
| `Tick_Engine` 차이 가운데 위 항으로 설명되지 않는 몫 | −0.07 | −0.26 |
| `CalcBoundsImpl` (`manager`가 더 큼) | +0.13 | +0.26 |

- 사실: 차이는 대부분 Mass 처리 단계 둘의 합(2만 11.04ms)이 매니저 틱 하나(8.40ms)로 대체된 데서 나온다. 2만 −2.64ms가 `Tick_Engine` 차이 −2.90ms의 91%다.
- 2단계의 11.04ms는 두 덩어리다. 게임 스레드에서 도는 표현 쪽 프로세서(LOD 2.57 + `MassUpdateISMProcessor` 1.66 + LOD 수집 0.64 + 표현 0.59 = 5.46ms)와 ISM 갱신 `EndVisualChanges`(5.44ms)다.
- `manager`는 LOD·표현 프로세서가 없다. 2만에서 LOD 계산 쪽 세 프로세서(2.57 + 0.64 + 0.59 = 3.80ms)가 통째로 없다.
- `manager`는 로직도 게임 스레드에서 돈다. 병렬 2단계가 워커로 보내는 로직(2만 11.01ms)은 게임 스레드 표에 올라오지 않는다.
- 추측: `manager`의 틱 8.40ms = 로직 + ISM 쓰기라면, 로직이 직렬 2단계와 같은 3.59ms일 때 ISM 쓰기는 약 4.8ms다. 2단계의 ISM 갱신 경로(`MassUpdateISMProcessor` + `EndVisualChanges` = 7.10ms, 직렬은 6.43ms)보다 작다. 이 4.8ms는 틱 안을 나누지 못해 계산한 값이고 확인하지 못했다.
- 직렬 2단계(2만 `Tick_Engine` 13.27ms)와 병렬 2단계(13.14ms)는 0.13ms 차이다. 이 트레이스에서 병렬 처리는 게임 스레드를 줄이지 못했다. 병렬은 게임 스레드가 표현 쪽 프로세서를 돌고 로직은 워커가 돌며, 직렬은 게임 스레드가 로직까지 돈다. 두 합이 거의 같다.
- 설명하지 못한 나머지: `Tick_Engine` 차이 2만 −2.90ms 가운데 −0.26ms(1만 −0.07ms)다. `CalcBoundsImpl`(+0.26)은 반대 방향이라 그만큼 다른 곳에서 더 줄었다. 다른 곳을 가르지 않았다.
- `Mgr1`의 Game p50 차이(1만 0.95ms, 2만 2.29ms)는 트레이스 한 회의 `Tick_Engine` 차이(1.30ms, 2.90ms)보다 작다. 트레이스를 켠 한 회의 값이라 같은 크기가 아니다. 차이가 어디서 나는지의 구성만 쓴다.
- `FEngineLoop::Tick`은 2만에서 `manager` 14.38, 2단계 14.73ms로 0.35ms 차이다. 게임 스레드가 줄인 시간(2.90ms)은 `Sync_RenderingThread` 대기가 늘어난 시간(3.74 − 1.12 = 2.62ms)으로 거의 메워진다. 프레임 시간이 렌더 쪽에 묶여 있다는 `Mgr1`의 결과와 같다.

### Render 차이의 출처

렌더 스레드(`RenderThread 0`)에서 `manager` 대 2단계(프레임당 ms, Excl, 트레이스 한 회):

| 타이머 | 1만 | 2만 |

- 사실: 렌더 스레드 Excl 합에서 `WaitForTasks`를 뺀 시간은 2만에서 `manager`가 3.07ms 짧다. `PrepareDistanceFieldScene`이 그 가운데 2.10ms(68%)다. 1만은 합 0.71ms인데 이 타이머 하나가 0.81ms라 다른 타이머가 0.10ms 늘었다.

- 추측: `PrepareDistanceFieldScene` 차이는 거리 필드 오브젝트 갱신량이나 갱신 시점이 두 변형에서 다른 데서 올 수 있다. `manager`가 ISM 쓰기를 `PrePhysics`(TG_PrePhysics 틱)에서, 2단계가 `PostPhysics` 끝에서 한다. 이 가설은 확인하지 않았다.

### 확인하지 못한 것

- 트레이스는 조건마다 한 번이다. 위 차이의 크기가 세 실행 범위 안인지 알 수 없다. `Mgr1`의 차이와 방향은 같고 크기는 다르다.
- `LabCrowdManager Tick` 안쪽(로직, 접근, 이동, ISM 쓰기, 스폰)을 나눈 타이머가 없다. 구간 타이머를 소스에 더하려면 `Source/` 변경과 재패키징이 필요하다.
- `PrepareDistanceFieldScene` 차이의 원인, 렌더 스레드의 `WaitForVisibilityTasks`가 `manager`에서 긴 원인, 병렬 2단계 워커 Excl 합의 설명되지 않는 약 8.8ms.
- GPU 타이머는 보지 않았다. 병목이 GPU라는 `Mgr1`의 결과는 그대로다.
- `Measurements/Reh4/`(예행 3회의 진행 로그와 실패 목록)는 커밋하지 않았고 지우지 않았다. 예행 산출물이라 커밋하지 않고, 예행의 근거라 지우지도 않았다. 코디네이터가 정한다.
