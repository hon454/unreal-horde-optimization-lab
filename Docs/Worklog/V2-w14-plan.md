## 0. 용어

이 문서 안에서만 쓰는 줄임말이다. 처음 나오기 전에 정의한다.

- 프레임 p50: 한 실행의 측정 창(180초)에서 프레임 시간의 중앙값이다. 공개 글에서는 "프레임 시간 중앙값"으로 쓴다.
- 프레임 p95: 같은 창에서 프레임 시간의 95번째 백분위수다. 느린 쪽 5%의 경계다. 공개 글에서는 "느린 쪽 5% 경계"로 쓴다.
- 표의 값: 같은 조건 세 실행의 중앙값이다. 출처는 `Measurements/Full4/summary.csv`이고 따로 적지 않으면 호드 총수 1만, 오브 시점 카메라(P1)다.
- 이동: 오브가 반지름 57.3m 원을 2m/s로 도는 장면이다(라벨 `V0-`). 정지: 오브가 원점에 서 있는 장면이다(라벨 `V1-`).
- 기법별 기여: 최종 구성(단계 8)에서 기법 하나를 끄고 잰 조건과 단계 8의 차이다. 옛 문서와 조건 표는 같은 것을 "빼 보기"(`ablation`, `a8*`)라고 부른다. 이 계획안은 사용자가 정한 새 이름 "기법별 기여"를 쓴다(7.2절).
- 최대 N: 프레임 p95가 16.7ms를 넘기 직전의 호드 총수다. 잰 총수 사이를 로그 보간한다. 기능 미달(`UNMET`) 점은 보간에서 뺀다([measurement.md](../Guides/measurement.md) "실패 등급").
- 구별되지 않음: 중앙값의 차이가 두 조건의 범위 중 큰 쪽보다 작거나, 0.5ms 아래다. `Full4`에는 5회 묶음이 없어 0.5ms 아래 차이는 범위를 넘어도 이렇게 쓴다([measurement.md](../Guides/measurement.md) "차이 판정").
- 버는 단계, 품질 단계: 조건 표의 성격이다. 버는 단계는 2, 3, 5, 8이고 품질 단계는 4, 6, 7이다([v2-plan.md](../v2-plan.md) "사다리").
- 계획안의 작업 단위 이름은 `W14-<번호>`다(12절).

## 1. 결론 먼저

- 글 열 편 가운데 주장이 그대로 서는 것은 00과 06뿐이다. 02, 03, 05, 08, 09는 `v2`에서 주장이 맞지 않거나 반대다. 01, 04, 07은 주장의 일부만 선다(3절).

- 그림 스크립트 셋(`plot-readme.py`, `build-site.py`, 글마다의 `make-figures.py`)은 `v1` 조건 이름(`L1`\~`L8`, `A8-*`)과 `Full3`을 읽는다. 셋 다 `v2` 이름으로 옮겨야 한다(9절).
- 작업은 22개 단위다. 사용자 결정이 먼저이고, 그림 장치와 단계 화면과 표현 색 코드가 그다음, 글, README, 사이트, 병합 순이다(12절).

## 2. 사용자가 W14 전에 정할 것

### 결정 1. 최대 N을 어떻게 적나

- 지금 상태: `Docs/figures/full4/full-n-at-60fps.csv`의 프레임 p95 기준 값은 단계 3 12,147, 단계 4·5 "≥12,500", 단계 6 12,185, 단계 7 11,619, 단계 8 12,026이다. 2만 점은 여섯 단계 모두 기능 미달이라 뺐다. 그래서 단계 4·5는 16.7ms를 사이에 두는 두 점이 없다.
- 추천: 본문 문장은 최종 구성 하나로 "약 1만 2천"이라 쓴다. 그림에는 단계마다 값을 그리고, 단계 4·5는 "1만 2,500 이상"으로 막대 끝을 열어 그린다. 그림 아래 한 문장에 "2만에서는 겹침 방지가 기능 미달이라 뺐다"를 적는다.
  - 득: 주 지표가 목표 총수의 프레임 시간이라는 사양([v2-spec.md](../v2-spec.md) 1절)과 맞는다. 유효 숫자 둘 규칙(measurement.md "지표")에 맞는다.
  - 실: 단계 3\~8의 차이(약 500)가 문장에서 안 보인다. 그림이 대신 보인다.
- 대안 A: 범위 "약 1만 1천 6백\~1만 2천 5백 이상"으로 쓴다. 득: 정직하다. 실: 숫자가 셋이라 한 문장 숫자 둘 규칙(posting.md)을 어긴다.
- 대안 B: 처음 목표를 지킨 단계 3의 12,147을 머리 숫자로 쓴다. 득: "단계 3에서 이미 지켰다"는 이야기와 맞는다. 실: 최종 구성의 값이 아니라 독자가 오해한다.

### 결정 2. 잡음 안의 기법별 기여 행을 어떻게 보이나

- 추천: 모든 행을 그리되 열 행은 회색 막대와 "구별되지 않음" 글자로 그린다. 값 대신 세 실행 범위를 가는 선으로 보인다. 프레임 시간에 안 보이는 이점(GPU, 왕복 전환 수, ISKM 트랙 수)은 그 행 옆에 한 줄로 적는다.
  - 득: 사양의 "모든 기법은 이점이 보여야 한다"(v2-spec 1절)를 행마다 확인할 수 있다. 이점이 안 보인 것도 적는다는 README의 약속과 맞다.

- 대안 A: 구별되는 여덟 행만 그리고 나머지는 산문 한 문단으로 묶는다. 득: 그림이 짧다. 실: 독자가 빠진 행의 값을 찾으려면 측정 기록으로 가야 한다.

### 결정 3. 단계 화면을 어디에, 어떤 크기로 싣나

- 추천:

  - 득: 새로 더하는 LFS 양이 약 51MB에서 약 16MB 아래로 준다(추정). 사용자가 큰 움직이는 파일을 꺼린다(메모리의 42MB GIF 사례).

- 대안 A: 지금 크기(7MB대) 그대로 8개를 싣는다. 득: 일이 적다. 실: LFS에 약 60MB가 더 쌓인다.

### 결정 6. `v1`에만 있는 두 그림(엔티티 풀 16분, 전환 점수)을 어떻게 하나

- 지금 상태: README "엔티티 풀" 절과 글 05는 `v1` 묶음 `Pool1`(16분 2회)에, "전환이 티 나는 정도"는 `Full1`의 Development 참고값에 기댄다. `v2`에는 둘 다 없다(리뷰 R5). `run-pool.ps1`과 `run-transition.ps1`은 `v1` 전용이다.
- 추천: 두 절을 빼고 `v2`에서 잰 값으로 바꾼다.
  - 엔티티 풀: `Full4` 240초 실행 끝의 ISKM 트랙 수가 풀 켬 20,215, 풀 끔 30,797이다(`summary.csv` `iskm_tracks_last`, `V0-s8`, `V0-a8pool`). 누수가 4분 안에도 보인다. 프레임 시간은 구별되지 않는다(+0.01ms). 긴 실행의 프레임 영향은 "`v2`에서 다시 재지 않았다"고 측정 기록에 적는다.
  - 전환: 최소 유지 시간을 끄면 왕복 전환이 초당 4.34건, 켜면 0건이다(`summary.csv` `sw_round_all`, `V0-a8hold`, `V0-s8`). 이것으로 전환 절을 대신한다.
  - 득: 공개 수치가 모두 한 묶음에서 나온다. 러너를 옮기지 않는다.
  - 실: "16분 동안 메모리가 1.75GB 는다" 같은 눈에 띄는 결과가 사라진다.
- 대안 A: `run-pool.ps1`을 `v2`로 옮겨 같은 패키지 de0e21b로 16분 × 2회를 잰다(참고 묶음, 약 0.6시간 + 러너 작업). 득: 풀 그림이 산다. 실: 코드와 측정 작업 단위가 하나 는다.
- 대안 B: `v1` 값을 "이전 판의 참고값"으로 둔다. 실: 다른 묶음의 값이 공개 문서에 섞인다(AGENTS.md "비교는 같은 묶음에서").

**00 목표와 재는 법**(부분 재작성)

- 시나리오 절: 맵 중앙 고정 오브 → 반지름 57.3m, 높이 6m 원 궤도를 2m/s로 도는 오브(한 바퀴 180초), 오브를 따라가는 카메라. 재생성은 맵 밖 무리의 기록에서다(ADR-0020). 시나리오 카드 세 문장이 바뀐다(posting.md의 카드 문장도 함께, W14-7).
- 새 절 "모든 단계가 하는 일 넷": 오브 쫓기, 겹치지 않기, 가까운 개체의 캡슐, 피해와 사망(v2-spec 3절). 그 확인 방법인 동등성 검사(초당 사망 ±1%, 30m 안 ±1%, 겹친 쌍 0.5\~2배, 캡슐 빗나감, 왕복 전환)를 한 문단으로.
- 측정 방법 절: 워밍업 15초 + 60초 → 60초 + 180초(이동), 15초 + 180초(정지). 묶음 끝 같은 조건 다시 재기(차이 +0.08ms, 한계 0.5ms, `batch-check.py` 출력), 느린 실행 재측정, CPU 클럭 기록. 차이 판정의 0.5ms 규칙. 목표 판정식(단계 8 p95 14.23 + 0.6 = 14.83ms ≤ 16.7ms).
- "최대 개체 수" 절: 기능 미달 점을 빼는 규칙을 한 문장 더한다.
- "여덟 단계의 지도": 단계 이름과 성격(버는 단계 2, 3, 5, 8, 품질 단계 4, 6, 7)이 바뀐다. 표현 구조 그림(결정 11)의 작은 판.

- 주장 반대: `v1`은 남은 예산으로 액터를 84개 늘려 1.02ms를 썼다. `v2` 단계 8은 80m 밖 그림자를 끄고 액터 메시에 고정 바운드를 써서 시간을 번다. 단계 8 대 7: p50 −0.79ms, p95 −0.94ms, 게임 스레드 −0.81ms.

- 액터 상한 1,000과 35m는 단계 2부터 같다(ADR-0021). 그래서 "액터를 늘렸다"는 절은 빠진다. 40m에서 35m로 낮춘 경위는 수치 없이 방향만.
- 목표 판정 14.83ms ≤ 16.7ms. 최대 N 12,026. 2만은 기능 미달.
- 표현 구조 그림(결정 11)과 "80m를 넘는 개체의 애니메이션 트랙" 절은 둔다.

**09 요약**(다시 쓴다)

- 주장: "60fps는 단계 3에서 처음 지켰고, 단계 4\~7은 거리별 품질을 더하며 p95를 약 1ms 늘렸고, 단계 8이 그만큼 되돌렸다." 수치: 단계 3 14.15, 단계 7 15.17, 단계 8 14.23ms(p95).

### 12.3 main 병합(사용자 승인 뒤, W14-22)

1. 사용자가 공개 자료 전체를 승인한다(W14-21). 승인 문장을 autonomous-decisions.md에 남긴다.
2. 코디네이터가 `v2`의 작업 트리가 깨끗한지 본다(`git status --porcelain`).
3. main에 `v2`를 병합한다. 강제 푸시는 하지 않는다. main의 오탈자 커밋이 `v2`에 이미 병합됐는지 먼저 본다(AGENTS.md "진행 방식").
4. main에서 `py -3 -I Scripts/build-site.py`를 다시 돌리고 바뀐 `Site/`를 커밋한다.
5. `git push origin main`.
6. `gh-pages`를 main의 `Site/`로 갱신해 올린다. 공개 게시라 사용자 승인 범위 안에서 한다.
7. 결정 10이 "올린다"이면 de0e21b 패키지를 Releases에 올리고 README 링크를 확인한다. 공개 게시라 사용자의 명시적 승인이 필요하다.
8. 사이트 주소를 열어 단계 여덟과 그림이 보이는지 본다.
9. STATUS.md를 갱신하고 W14를 닫는다.
