그리는 끝(200m) 밖을 실제 미니언과 연결되지 않은 Niagara GPU 입자 + VAT 메시로 채운다([plan.md](../plan.md) "품질 계획" Q2, [ADR-0009](../Decisions/0009-flat-scenario-quality-by-distance.md)). 첫 작업 단위는 조사, 설계안, Niagara 시스템 초안까지다. 런타임 코드 연결과 빌드는 다음 단위다.

- 커밋 끝: 푸시하지 않음.

## 조사

### 지금 VAT 에셋과 프레임 지정

- 메시·텍스처·머티리얼은 `Scripts/bake-vat.py`가 `/Game/Lab/VAT/Baked/`(gitignore)에 굽는다. 대표는 Bone 모드다: `SM_LabMinionVAT_Bone`·`SM_LabMinionLargeVAT_Bone`, 텍스처 `T_*_BonePosition/BoneRotation/BoneWeight`, 머티리얼 `M_*VAT_Bone`(Diffuse·Normal → `MF_BoneAnimation`)과 인스턴스 `MI_*VAT_Bone`.
- 클립 프레임(데이터 에셋 `Animations`, 30fps, MCP로 읽음): 소형 걷기 0..61, 피격 62..82, 죽기 83..147(148프레임). 대형 걷기 0..40, 피격 41..65, 죽기 66..85(86프레임).
- 프레임 지정: 굽기 데이터 에셋은 `auto_play=False`이고, `ULabVatProcessor`가 프레임을 계산해 `FLabVatFrameData`(Frame, PrevFrame)를 ISM 인스턴스 커스텀 데이터 0·1번에 넣는다(`LabVatProcessor.cpp:147-165`). 우리 머티리얼은 커스텀 데이터 0번을 한 번 더 읽어 죽기 클립 진행도로 색을 붉게 바꾼다(`bake-vat.py` `make_material`).
- `MF_BoneAnimation` 안의 `GetFrameSwitch`(엔진 에셋 `/AnimToTexture/Materials/MaterialFunctions/GetFrameSwitch`, MCP로 노드를 읽음)에 정적 스위치가 둘 있다. `AutoPlay`와 `UseDynamicParameters`(기본 false)다.
  - AutoPlay 끔 + 동적 파라미터 끔: 커스텀 데이터 0 = Frame, 1 = PrevFrame(지금 ISM 경로).
  - AutoPlay 끔 + 동적 파라미터 켬: Dynamic Parameter 0번(이름 Frame, PrevFrame).
  - AutoPlay 켬 + 동적 파라미터 끔: 커스텀 데이터 0 TimeOffset, 1 Playrate, 2 StartFrame, 3 EndFrame.
  - AutoPlay 켬 + 동적 파라미터 켬: Dynamic Parameter 1번(이름 TimeOffset, Playrate, StartFrame, EndFrame).
  - 자동 재생 프레임은 `GetAutoPlayFrame`이 `StartFrame + fmod((Time + TimeOffset) × Playrate × SampleRate, EndFrame − StartFrame + c)`로 계산한다(`Time`은 머티리얼 Time 노드, 일시정지 따름). 상수 c와 Max 하한값은 MCP가 읽지 못했다.
- **Niagara 메시 렌더러에서는 인스턴스 커스텀 데이터를 쓸 수 없다.** GPU Scene 경로에서 Niagara는 인스턴스당 커스텀 데이터 float 하나를 잡고 그 0번에 입자 인덱스(`asfloat(ParticleIndex)`)를 쓴다. 그래서 같은 머티리얼을 커스텀 데이터 경로로 쓰면 프레임 자리에 입자 인덱스의 비트가 들어간다. 프레임은 Dynamic Material Parameter로 넘겨야 하고, 엔진 VAT 함수가 그 경로(`UseDynamicParameters`)를 이미 갖고 있다. 근거는 engine-notes.md 17절.
- 우리 머티리얼의 죽기 색은 커스텀 데이터 0번을 그대로 읽는다. Niagara에서는 입자 인덱스의 비트(작은 정수를 float로 읽으면 0에 가까운 비정규 수)가 들어가 진행도가 saturate로 0이 되므로 색이 바뀌지 않는다(계산으로 판단했고, 스크린샷에서 붉은 개체가 없다).

### 방향, 바운드, 그림자, 워밍업

- 방향: 메시 렌더러 `FacingMode = Velocity`는 메시 X축을 속도 방향에 맞춘다. 미니언 메시는 진행 방향이 −90도 돌아 있어(`LabCrowdSubsystem.cpp:84-85`, `LabMinion.cpp:34`) 렌더러 메시 항목에 `Rotation` yaw −90을 넣었다. 스크린샷에서 입자가 중앙을 보고 걷는다.
- 바운드: GPU 입자는 바운드를 계산하지 않으므로 이미터 `CalculateBoundsMode = Fixed`(±1,050m × z −1\~10m)와 시스템 `bFixedBounds`를 같은 상자로 두었다. 개체별 컬링은 엔진이 GPU Scene 경로에서 강제한다(`bForceInstanceCulling = true`, engine-notes.md 17절).
- 그림자: 메시 렌더러 `bCastShadows` 기본값이 true다. 200m 밖 미니언(화면 높이 약 8px)의 그림자는 보이지 않을 만큼 작고 비용만 든다고 보고 렌더러와 시스템(`bOverrideCastShadow`, `bCastShadow` false) 둘 다 껐다. 실제 미니언은 그림자를 켠다(measurement.md "확정값"). 200m 경계에서 그림자 유무가 눈에 띄는지는 움직이는 화면으로 본다.
- 워밍업: 입자가 1,000m에서 200m까지 걷는 데 267초가 걸려, 켤 때 비어 있지 않으려면 정상 상태로 미리 돌려야 한다. 시스템 `WarmupTime` 268초, `WarmupTickDelta` 0.125초(이미터 최대 틱 델타 `MaxDeltaTimePerTick` 기본 0.125, 넘으면 에디터 경고)로 두어 활성화 때 2,144틱을 한꺼번에 돈다. GPU 이미터도 워밍업 틱을 큐에 넣어 다음 렌더에서 모두 처리한다. 에디터에서 배치 직후 화면이 채워진 것으로 확인했다. 이 한 번의 비용(활성화 프레임 스파이크)은 재지 않았다.

### 장면 수치(목표 총수 1만)

계산값이다. 시나리오는 measurement.md "확정값"(반경 R 500m, 밀도 ∝ 1/r, 3m/s, 소형 90% / 대형 10%).

- 반지름당 개체 수는 N/R = 10,000 / 500 = 20명/m로 일정하다. 200\~500m 고리에는 20 × 300 = 6,000명(60%)이 있고 모두 그리지 않은 채 로직만 돈다.
- 면밀도 σ(r) = N / (2πRr) = 3.18/r 명/m². 200m에서 0.0159명/m²(63m²에 한 명, 평균 간격 약 8m), 500m에서 0.0064명/m²(157m²에 한 명, 약 12.5m).
- 입자가 실제 미니언과 같은 밀도로 이어지려면 같은 흐름을 만들면 된다. 바깥 고리에서 초당 (N/R) × v = 20 × 3 = 60개를 만들어 중앙으로 3m/s로 걸리면, 정상 상태 밀도가 반지름에 관계없이 20개/m가 되어 위 σ(r)와 같다. 바깥 반경을 Rout이라 하면 입자 수는 20 × (Rout − 200)이다.
- 어디까지 채울지: P1 카메라(높이 9m, 수평 시야 90도, 16:9이면 수직 시야 58.7도, 1080p에서 도당 18.4px)에서 지평선 아래 각도는 atan(9/d)다. 200\~500m 띠가 1.55도(약 28px), 500\~1,000m가 0.51도(약 9px)를 차지한다. 미니언 키 1.76m는 200m에서 약 8px, 500m에서 약 3.7px, 1,000m에서 약 1.9px이고 그 너머는 2px 아래라 개체로 읽히지 않는다. 그래서 Rout 1,000m를 추천한다. 입자 수는 16,000개(소형 14,400 + 대형 1,600)다.
- 바닥은 정사각형이고 한 변의 절반이 520m다(`Scripts/create-bench-map.py`, 맵 반경 + 20m). 520m(모서리는 735m) 밖의 입자는 바닥 없는 곳을 걷는다. P1에서는 지평선 띠에 묻혀 구별되지 않았다(아래 스크린샷).

## 설계안

추천안으로 초안을 만들었다. "확정 필요"는 사용자 확정 전까지 초안 값이다.

### (가) 입자가 덮는 구간

추천: **200m부터 Rout(1,000m)까지 전부를 입자로 덮는다.** 실제 미니언이 로직만 도는 200\~500m도 입자가 대신 보여 준다. 화면에서는 200m 안쪽이 실제 미니언, 밖이 입자로 나뉘어 겹치지 않는다. 200\~500m 띠가 P1 지평선 아래 28px로 가장 넓어 비워 두면 가장 눈에 띈다.

- 다른 안 1: 맵 끝(500m) 밖만 입자로 덮는다. 입자가 6,000개 줄지만 200\~500m가 빈 띠로 남아 "빈 수평선"이 그대로다.
- 다른 안 2: 실제 미니언을 500m까지 그리고 그 밖만 입자로 덮는다. 200m 밖 지우기(사다리 3단계, 2026-11-08 사용자 결정)를 되돌리는 것이라 비용이 크다(E2 (c) 5k P1에서 200m 밖 지우기가 프레임 7.5 → 6.4ms).

### (나) 입자의 생애와 200m 경계

추천: **Rout 고리에서 생겨 3m/s로 중앙을 향해 직진하고, 수명 (Rout − 200m) / 3m/s가 끝나는 200m에서 사라진다. 페이드는 두지 않는다.** 실제 미니언과 같은 흐름이라 경계에서 사라지는 입자 수(초당 60)와 경계를 넘어 나타나는 실제 미니언 수가 통계적으로 같다. 둘의 각도는 서로 무관하지만 200m에서 미니언이 약 8px이라 어긋남이 개별로 보일 가능성은 낮다고 본다. 확인은 움직이는 화면으로 한다(다음 단위, 확정 필요).

- 다른 안 1: 마지막 수 m 동안 크기를 0으로 줄인다(Scale Mesh Size 모듈 하나). 튀는 느낌은 줄지만 경계에 작아지는 미니언 띠가 생길 수 있다.
- 다른 안 2: 디더 페이드. 머티리얼을 Masked로 바꿔야 해서 새 머티리얼과 셰이더 비용이 든다.
- 다른 안 3: 입자를 195m까지 겹쳐 둔다. 경계 5m가 두 배 밀도가 된다.
- 실제 미니언은 200m 밖에서도 저격으로 죽는다(measurement.md "확정값" 저격). 입자는 죽지 않는다. 200m 밖 저격은 화면 높이 약 8px 이하의 개체라 입자에 같은 연출을 넣지 않는다.

### (다) 입자 수, 2종 비율, 걷기 위상

추천: **이미터 둘(소형, 대형)을 두고 스폰율을 N에서 계산한다.** 소형 = 0.9 × N/R × v, 대형 = 0.1 × N/R × v(N=1만에서 54, 6개/초). 단계와 N이 바뀌어도 밀도가 실제 미니언과 맞는다. 1종 실행(`-LabTypes=1`)에서는 대형 0이다. 걷기 위상은 입자마다 TimeOffset을 [0, 클립 길이)에서 고르게 고르고(소형 62/30초, 대형 41/30초), Playrate 1, StartFrame 0, EndFrame 61(대형 40)을 Dynamic Material Parameter 1번으로 넘긴다. 3m/s는 걷기 클립에 맞춘 속도라 Playrate는 1이다(measurement.md "이동 속도").

- 다른 안 1: 입자 수를 N과 무관하게 고정한다. 보조 묶음(N 5k\~3만)에서 경계 밀도가 어긋난다.
- 다른 안 2: 한 이미터에 메시 둘을 넣고 MeshIndex로 고른다. 이미터 하나로 줄지만 2종 비율을 정확히 맞추려면 별도 표현식이 필요하다.
- 확정 필요: Rout(1,000m)과 입자 수를 N에 묶을지.

### (라) 비용과 화면 이점을 재는 법

추천: **빼 보기 표의 "Niagara 배경 무리 → 빈 수평선" 행을 같은 빌드의 인자 하나(`-LabCrowdFx=0/1`)로 켜고 끈다.** 최종 구성 1만 P1 3회씩 두 조건의 프레임·GPU p50/p95 차이가 비용이다. 화면 이점은 같은 시점의 켬·끔 스크린샷 쌍(이 단위의 `p1-crowd`·`p1-empty`)과 촬영 실행 GIF로 보인다. 입자 수는 CSV 메타데이터에 계산값으로 남긴다(`LabCrowdFxParticles`, 20 × (Rout − 200) × N / 1만). P2는 화면에 입자가 없으므로(`p2-crowd`) GPU 시뮬레이션 비용만 남는다. P2도 한 번 재서 "보이지 않을 때의 비용"으로 적을 수 있다.

- 다른 안: `stat gpu`의 Niagara 항목으로만 적는다. 프레임 시간에 미치는 영향은 켬·끔 비교가 직접적이다.
- 활성화 때 워밍업 2,144틱의 스파이크는 15초 워밍업 안에 들어가지만 `spikes.py`로 한 번 확인한다.

### (마) 런타임에 켜고 끄는 방식(다음 단위의 코드 범위)

추천:

- `FLabConfig`에 `-LabCrowdFx=` 인자(0/1). 기본값은 사다리 7단계부터 1, 그 앞 단계는 0(확정 필요: 단계와 기본값의 연결은 Q3·Q5의 단계 이름과 함께 정한다).
- `ALabGameMode`가 켬일 때 오브 위치에 `UNiagaraComponent`를 하나 붙인다. 시스템 경로는 코드에 박지 않고 `Config/DefaultGame.ini` `[Lab] CrowdFxSystem`에서 읽는다(바닥 띠 머티리얼 `BandFloorMaterial`과 같은 방식, `LabGameMode.cpp:152-156`).
- 사용자 변수 `User.SmallRate`·`User.LargeRate`(N과 종류 수에서 계산), `User.OuterRadius`, `User.Lifetime`, `User.Speed`를 컴포넌트에 넣은 뒤 활성화한다. 워밍업은 활성화 때 돈다.
- CSV 메타데이터에 `LabCrowdFx`, `LabCrowdFxParticles`, lab_build 로그에 같은 값.
- 쿡: 시스템이 ini의 문자열 경로로만 참조되면 쿡에서 빠진다. `/Game/Lab/FX`를 `DirectoriesToAlwaysCook`에 넣거나 기존 방식(바닥 띠 머티리얼이 어떻게 쿡되는지)을 따른다. 다음 단위에서 확인한다.
- 굽기 머티리얼 `M_LabMinionVAT_Bone`·`M_LabMinionLargeVAT_Bone`에 `bUsedWithNiagaraMeshParticles`를 켜고 저장했다. 이 에셋은 `bake-vat.py`가 다시 만들면 플래그가 사라진다. `bake-vat.py`의 `make_material`에 `MATUSAGE_NIAGARA_MESH_PARTICLES`를 더해야 한다(측정 세션 소유 파일이라 이 단위에서는 고치지 않았다). 플래그가 없으면 쿡된 빌드에서 입자가 기본 머티리얼로 그려진다.

### 확정 필요 목록

1. Rout(입자 바깥 반경): 추천 1,000m(입자 16,000개 @ N 1만). 다른 안 520m(바닥 끝, 아래 참고)·1,500m(26,000개, 1,000m 너머는 개체가 2px 아래).
2. 입자 수를 N에 묶을지: 추천 묶는다(초당 0.006 × N).
3. 200m 경계 처리: 추천 페이드 없음. 움직이는 화면을 본 뒤 크기 줄이기로 바꿀지 정한다.
4. 입자 그림자: 추천 끔.
5. `-LabCrowdFx` 기본값과 단계 연결: Q3·Q5에서 단계 이름과 함께.

1번의 520m 안은 입자 6,400개(20 × 320)이고 바닥 밖을 걷는 입자가 없다. P1에서 지평선 아래 2.58\~0.99도(200\~520m, 약 29px)를 채우고 그 위 약 18px(0.99도)는 빈 바닥으로 남는다(계산값, 위 "장면 수치"의 시야).

1·2단위의 에셋(`NS_LabCrowd`, 바닥 1,020m)을 런타임에 붙인다. 코디네이터 결정(2026-11-12, 사용자 부재): 입자 바깥 반경 1,000m, 입자 수는 N에 묶는다(초당 0.006 × N, 소형 0.9·대형 0.1, 1종 실행은 대형 0), 그림자 끔, 200m 경계는 페이드 없음. 에디터는 닫혀 있고 에셋은 고치지 않는다.

### 진행

- 조사 끝(2026-11-12): 변형은 `FLabConfig::Get()`이 `-LabVariant=` 문자열을 `ELabVariant`로 바꾸고 기본값(풀링, Budget)을 변형과 단계에서 정한다. `run-dev.ps1`·`run-bench.ps1`은 `-Variant`를 `ValidateSet`으로 막고 `-LabVariant=`로 넘긴다. 시스템 경로는 `[Lab] BandFloorMaterial`과 같은 `GConfig` 읽기, 쿡은 `DirectoriesToAlwaysCook`의 `/Game/Lab`이 `/Game/Lab/FX`를 이미 덮는다. 실제 미니언이 나타나는 거리는 카메라 기준이고 히스테리시스 때문에 200m가 아니라 188m다(아래 "200m 경계의 위치").
- 구현 끝: `FLabConfig`에 `-LabCrowdFx=`(기본 0, 변형 `q2crowd`만 1)와 개발용 `-LabCrowdFxInnerM=`, 스폰율·수명·입자 수 계산 함수. `ALabGameMode::SetupCrowdFx`, ini 키 `[Lab] CrowdFxSystem`, CSV 메타데이터 `LabCrowdFx`·`LabCrowdFxParticles`·`LabCrowdFxActive`, `lab_build`·`lab_config` 로그, 개발 빌드의 실제 입자 수 로그 `lab_crowdfx_count`(5초마다). `run-dev.ps1`의 `ValidateSet`에 `q2crowd`.
- 빌드 끝: `Scripts/build.ps1` 성공(경고는 기존 Mass 폐기 API 경고뿐).
- 작은 실행 끝: `run-dev.ps1 -Small -Stage M5 -Variant q2crowd`(켬)·`-Variant m5bounds`(끔), `-Stage M0`\~`M4`, `-Stage M5 -Variant m4offpool` 모두 종료 코드 0, 모두 `kills=8 respawns=43 snipes=39`(Q1b와 같다). 켬 실행의 `lab_crowdfx_count`가 5·10·15초에 `Small=144 Large=16`(계산 160과 같다). 끔 실행은 `crowdfx=0 crowdfx_particles=0`이고 `lab_crowdfx` 줄이 없다.
- 실행 끝: 1만 P1(2종, M5) 켬·끔 스크린샷, 경계 확대와 연속 프레임(카메라 회전·정지), 안쪽 반경 200m·173m 비교, 시즈 사망 확인 로그, 켬·끔 프레임 시간. 이 결과로 입자의 안쪽 반경 기본값을 그리는 끝(200m)에서 실제 미니언이 나타나는 자리(172.8m)로 바꾸고 다시 빌드했다.
- 최종 빌드·작은 실행 끝: 안쪽 반경 기본값 변경과 Q1b 확인 로그를 넣고 `Scripts/build.ps1` 성공. `-Small`로 `q2crowd`(입자 계산 165, 5초 실측 163), `m5bounds`, `m5bounds -Extra "-LabCrowdFx=1 -LabTypes=1 -LabFarM=300"`(대형 0, 소형 0.60/초, 안쪽 262.85m, 수명 245.72초, 147개), `-Stage M0`\~`M4`, `-Stage M5 -Variant m4offpool` 모두 종료 코드 0, 모두 `kills=8 respawns=43 snipes=39`.
- 커밋 끝: 푸시하지 않음. 게임·에디터 프로세스 없음.

### 켜고 끄는 인자와 변형

- `-LabCrowdFx=0/1`, 기본 0. 변형 `q2crowd`(`m5bounds` + 배경 무리)만 기본 1이고 인자를 주면 그 값이 이긴다(`FLabConfig::Get`, 풀링·Budget 기본값과 같은 방식). `q2crowd`는 표현·풀링·Budget·고정 바운드가 `m5bounds`와 같다(`IskmParams`에서 `bFixedBounds`). 단계 인자는 `M5`를 따로 준다(다른 변형과 같다).
- `run-bench.ps1`은 `-Variant`를 `ValidateSet`으로 막아 `q2crowd`를 받지 못한다(이 단위는 고치지 않는다). 그때까지 같은 구성은 `run-bench.ps1 -Milestone Q2 -Stage M5 -Variant m5bounds -ExtraArgs "-LabCrowdFx=1" -Tag crowd`처럼 고른다(`-Milestone Q2`만 주면 `-LabStage=Q2`가 되어 종료 코드 2). 이때 라벨과 CSV `LabVariant`는 `m5bounds`이고 켬 여부는 메타데이터 `LabCrowdFx`로 가른다. Q5에서 `ValidateSet`에 `q2crowd` 한 단어를 더하면 변형 이름만으로 켜진다. 버린 대안: 코드에서 단계 이름으로 기본값을 정하기(단계 이름은 Q3·Q5에서 정한다, (마) 확정 필요 5번).
- `run-dev.ps1`의 `ValidateSet`에는 `q2crowd`를 더했다.
- 개발용 `-LabCrowdFxInnerM=<미터>`(Test 빌드에서는 읽지 않는다): 입자가 사라지는 안쪽 반경을 덮어쓴다. 아래 비교 촬영에 썼다.

### 런타임 연결

- `ALabGameMode::SetupCrowdFx`(켬일 때 `StartPlay`에서 스포너보다 먼저): `[Lab] CrowdFxSystem=/Game/Lab/FX/NS_LabCrowd.NS_LabCrowd`를 `LoadObject`로 읽고 `UNiagaraFunctionLibrary::SpawnSystemAtLocation`(자동 활성화 끔, 자동 파괴 끔, `bPreCullCheck` 끔)으로 오브 위치에 놓는다. 오브에 붙이지 않은 것은 로컬 공간 시스템이 부모 회전을 따라가지 않게 하려는 것이다(오브는 움직이지 않는다). 사용자 변수 다섯 개를 넣은 뒤 `Activate`한다. 활성화 전에 넣은 값은 `OverrideParameters`에 들어가 워밍업이 그 값으로 돈다(engine-notes 17절).
- 값: 총 스폰율 = N / 맵 반경 × 이동 속도(N 1만이면 60/초), 소형 = 총 × 0.9, 대형 = 총 × 0.1(1종이면 대형 0이고 소형이 총 전부). `OuterRadius` 100,000cm, `Speed` 300cm/s, `Lifetime` = (바깥 반경 − 안쪽 반경) / 속도. 안쪽 반경은 `-LabFarM`을 따라간다(아래 "200m 경계의 위치").
- 실패하면(ini 키 없음, 에셋 없음, 안쪽 반경 ≥ 바깥 반경) `lab_crowdfx on=0 reason=…`을 남기고 배경 무리 없이 돈다. CSV `LabCrowdFxActive`가 실제로 활성화됐는지 남긴다.
- 기록: `lab_config`에 켬일 때만 `crowdfx=1 crowdfx_particles=… crowdfx_inner=…`, `lab_build`에 항상 `crowdfx=0/1 crowdfx_particles=…`, CSV 메타데이터 `LabCrowdFx`·`LabCrowdFxParticles`(정상 상태 계산값 = 총 스폰율 × 수명)·`LabCrowdFxActive`. 개발 빌드는 5초마다 `lab_crowdfx_count`(이미터별 실제 입자 수).

### 쿡

`Config/DefaultGame.ini`의 `DirectoriesToAlwaysCook`에 이미 `/Game/Lab`이 있어 `/Game/Lab/FX`(시스템, `MI_LabCrowd*`)와 그 부모가 있는 `/Game/Lab/VAT/Baked/`가 함께 쿡된다. 오브의 `NS_LabBolt`(같은 `/Game/Lab/FX`)도 문자열 경로만으로 지금까지 패키지에 들어왔다. 그래서 설정을 바꾸지 않았다. 패키징은 하지 않았다(Q5).

### 200m 경계의 위치

실제 미니언은 오브가 아니라 카메라 기준 3D 거리로 그려지고, Off에서 Low로 들어올 때 히스테리시스가 붙어 카메라에서 188m(= 80 + 0.9 × (200 − 80))에서 나타난다(`MassLODCalculator.h:864-886`, engine-notes 17절). P1 카메라는 오브 뒤 15m, 높이 9m라 화면 정면에서 실제 미니언은 오브에서 약 173m에 나타난다. 입자를 오브 200m에서 지우면 정면에 173\~200m(약 27m) 띠가 빈다. 계산상 이 띠는 QHD 화면에서 지평선 아래 2.40\~2.74도, 약 6\~8px 높이다.

연속 프레임은 기존 `-LabShotBurst`(창 해상도 2560×1440, 프레임마다 한 장)로 찍었다. QHD 캡처가 프레임을 약 0.4초로 늘려 프레임 간격이 그만큼 벌어졌다. 10fps 제한(`-ini:Engine:[ConsoleVariables]:t.MaxFPS=10`)은 인자가 쉼표로 한 덩어리가 되어 걸리지 않았다. 대표 프레임은 경계가 잘 보이는 영역과 카메라가 멈춘 구간을 골랐고, 버스트 원본은 저장소 밖 스크래치에만 두었다.

본 것:

- **켬·끔**: 끔은 실제 미니언 너머 지평선까지 빈 바닥이고, 켬은 지평선까지 소형(흰색)과 시즈(짙은 회색)가 실제와 같은 비율로 찬다. 입자에 VAT 머티리얼이 제대로 입혀졌다(기본 머티리얼의 회색 덩어리나 깨진 메시가 없고 시즈·소형의 색이 실제 미니언과 같다). 입자마다 걷기 자세가 다르고 넘어진 자세가 없어 걷는 무리로 읽힌다.
- **안쪽 200m**: 1:1 화면에서 실제 미니언 맨 윗줄 바로 위에 개체가 드문 밝은 띠가 약하게 보인다. 끊긴 선이 아니라 밀도가 잠깐 낮아지는 정도이고, 4배 확대하면 분명하다. 계산한 27m 빈 띠와 맞는다.
- **안쪽 173m**: 같은 자리가 메워져 실제 미니언에서 입자로 밀도가 이어진다. 확대해도 경계 줄을 찾기 어렵다.
- **카메라가 멈춘 연속 프레임**: 정지 카메라 4프레임(0.8초 간격)에서 경계에 개체가 갑자기 생기거나 사라지는 것을 찾지 못했다. 200m에서 개체가 약 8px이고 밀도가 높아 하나가 나타나는 것이 주변에 묻힌다. 다만 이 간격과 해상도로는 개별 팝을 판별할 수 없다(사람이 움직이는 화면을 본 것은 아니다).
- **톤 차이**: 입자는 같은 거리의 실제 미니언보다 약간 밝고 푸르게 보인다. 실제 미니언은 그림자가 있고(입자는 그림자 끔) 머티리얼도 다르다(실제는 ISKM 머티리얼, 입자는 VAT 머티리얼의 자식). 카메라가 도는 프레임에서는 입자가 실제 미니언보다 더 번져 보인다(정지 프레임에서는 비슷하다). 입자의 모션 벡터 출력 여부는 확인하지 않았다.

판단: **안쪽 200m는 약하게 튄다(빈 띠). 안쪽을 실제 미니언이 나타나는 자리(172.8m)로 옮기면 밀도로는 튀지 않는다.** 그래서 기본값을 옮겼다(`FLabConfig::CrowdFxInnerCm`: Lerp(80m, 그리는 끝, 0.9)를 높이 9m로 수평 거리로 바꾸고 오브 뒤 15m를 뺀다). 입자 수는 16,000 → 16,544(+3.4%)다. 페이드는 여전히 없다. 남는 단차는 밀도가 아니라 톤(그림자·머티리얼)이다.

- 고른 것: P1 카메라 기하에 맞춘 고정 반경. 되돌리려면 `-LabCrowdFxInnerM=200`이나 함수 한 줄이다.
- 버린 대안: (1) 200m 그대로(빈 띠가 남는다). (2) 카메라 위치를 매 프레임 넘겨 입자 소멸을 카메라 거리로 하기(시스템 모듈을 고쳐야 해서 에셋을 고치지 않는 이 단위 범위 밖). (3) 겹치기·크기 줄이기(두 배 밀도 띠나 작아지는 띠가 생긴다, 1단위 (나)).
- 남는 한계: P1 화면 가장자리(정면에서 45도)는 카메라 거리와 오브 거리 차가 15m가 아니라 약 10.6m라 입자와 실제 미니언이 약 4m 겹친다. 확대 화면에서 눈에 띄지 않았다. P2는 입자가 화면에 없어 같은 값을 쓴다(프리셋에 따라 입자 수가 바뀌지 않게).

### 확인한 것

선행 조사를 코드와 엔진 소스로 확인했다. 맞은 것은 그대로 썼고 틀린 곳 하나(MinCameraDistance)와 정할 곳 하나(피격·사망)는 아래에 적었다.

- 자리와 쿼리: Representation 그룹, `VisualizationProcessing` 뒤(엔진 ISKM 프로세서와 같은 자리, `MassUpdateSkinnedMeshProcessor.cpp:21-23`). Niagara 컴포넌트를 고치므로 게임 스레드다. `FLabMinionTag` 있음, `FLabPooledTag` 없음, `CurrentRepresentation == None`, 표현 상태 Walk. `FMassOffLODTag`로 거르지 않는다. 1만 P1에서 원소 약 6,200 중 Off 태그가 약 5,980이고 나머지 약 220이 카메라 188\~200m 띠(Simulation LOD Medium)다.
- `FLabOffMoveFragment`는 Off 아키타입에만 있는 것이 아니라 M5 단계의 모든 미니언에 붙는다(`LabMassTraits.cpp:22-25`). M3·M4 단계에는 없어서 Optional로 둔다.
- T0: Off 태그 아키타입이고 `LastMoveTime > 0`이면 `LastMoveTime`, 아니면 지금(엔진 이동이 매 프레임 옮긴다, engine-notes 5절). 1만 P1에서 "지금 − T0" 최대 1.10\~1.17초(Off 틱 1.0초 ± 10% + 한 프레임)다.
- 위상: 걷기의 `StateStartTime = −LabWalkPhase(Serial)`(`LabCrowdSubsystem.cpp:251,290`)이라 W = `−StateStartTime` = 위상(0\~102.7초)이다. 재생 시각 = 지금 − `StateStartTime` = 지금 + W.
- 외삽: `ULabOffMoveProcessor`는 오브 방향 × 속도 × 흐른 시간으로 곧게 옮기고 남은 거리에서 자른다(`LabMassProcessors.cpp:263-274`). 이 거리(오브 170m 밖)에서는 자를 일이 없어 에셋 식에 상한이 필요 없다.
- 피격·사망: 넣지 않는다. 피격·사망 개체는 멈추고(`StopMoving`, Off 이동 쿼리가 피격·사망 태그를 뺀다, `LabMassProcessors.cpp:222-223`) 입자는 걷기 클립과 진행 방향 정렬뿐이라 넣으면 제자리에서 걷는다. 그려지지 않는 거리의 피격·사망은 저격 바깥 구간(오브 80\~200m) 끝에서만 생기고 1만 P1에서 프레임 평균 1.5\~3.7개다(`lab_crowdrecs hitdead`). 저격당한 자리의 입자는 사라진다. 상태는 태그가 아니라 `FLabAnimStateFragment::State`로 거른다(사망 상태가 태그보다 먼저 바뀐다).
- **바로잡은 것(MinCameraDistance)**: 표현 LOD의 Off → Low 진입 거리는 188m지만, Off(`CulledByDistance`) 청크는 표현 LOD 계산과 표현 갱신을 `NotVisibleUpdateRate`(기본 0.5초 ± 10%)마다만 한다(engine-notes 21절). 1만 P1에서 그려지지 않은 걷는 엔티티의 카메라 3D 거리 최솟값이 5초 창마다 183.9\~185.0m였다(`lab_crowdrecs min_cam_m`). 메시 렌더러 `MinCameraDistance`를 18,800cm로 두면 엔티티가 184\~188m에 있는 동안 입자는 꺼지고 메시는 아직 없다. 원소는 None 엔티티뿐이라 입자와 메시가 겹치지 않으므로 `MinCameraDistance`는 안전망이다. 17,500cm를 권한다. 0.5초 간격만으로는 1.7m(0.55초 × 3m/s)라 나머지 약 2m의 원인은 가르지 못했다.
- Niagara 쪽: `UNiagaraDataInterfaceArrayFunctionLibrary::SetNiagaraArrayVector4`에 `TConstArrayView<FVector4f>` 판이 있다. 없는 이름이면 부를 때마다 Niagara 경고를 남겨서(engine-notes 21절) 활성화 전에 이름을 한 번 보고 없는 값은 넣지 않는다. 지금 에셋에는 네 변수가 모두 없어 `lab_crowdfx_param missing=…` 경고 네 줄이 나오고 실행은 정상이다.

### 500m 경계의 밀도

엔티티는 맵 반경 500m 안에만 있다. 처음 배치는 반지름 [8m, 500m] 균등이고 재생성은 링 [490m, 500m] 균등이다(`LabCrowdSpawner.cpp:118,241`). 바깥 독립 입자는 1,000m에서 생겨 500m에서 사라진다.

- 반지름 방향 밀도(1m당 개수)로 이어진다. 입자 = 스폰율 ÷ 속도 = (N / R × v) ÷ v = N / R = 1만에서 20개/m. 엔티티 = 흐름 ÷ 속도이고 흐름(재생성)은 45초에 2,607 = 57.9개/초라 19.3개/m다. 실행에서 오브 480\~490m 원소가 149\~220개(대부분 205\~220개, 20.5\~22개/m)였다.
- 490\~500m는 엷다. 재생성 링이 [490m, 500m] 균등이라 엔티티 밀도가 500m의 0에서 490m의 전부까지 선형으로 오른다. 실행에서 116\~146개(12\~15개/m, 평균의 약 70%)였다. 10m 띠이고 카메라에서 약 490\~515m라 화면에서는 작다. 메우려면 독립 입자의 안쪽 반경을 495m로 두면 [490m, 500m]의 평균이 맞는다(이번에는 코디네이터 결정 500m를 따랐다).
- 엔티티가 죽어 재생성되면 맵 가장자리 링의 다른 자리에 새 원소가 생긴다. 독립 입자가 500m에서 사라지는 것과 짝이지만 같은 자리가 아니다. 카메라 490m 밖의 일이다.

### 인자·기록

- `-LabCrowdFxEntity=0/1`(기본 1). 1: 엔티티 구동 + 독립 입자 안쪽 500m. 0: 3단위 옛 방식(안쪽 172.8m, 수명 275.74초, 프로세서 등록 안 함, 실행 로그로 확인). 옛 방식은 에셋 구조와 무관하게 재현된다. 독립 이미터의 안쪽 반경은 수명(`User.Lifetime`)이 정하고, 엔티티 구동 이미터는 배열이 비어 있으면 그리지 않는다(에셋 단위가 지켜야 할 조건). `-LabCrowdFx=1`일 때 0을 주면 `LabOverrides`에 `crowdfx_entity=0`이 붙는다. 변형 기본값(1)이면 붙지 않아 `full-conditions.json`의 기대값(`LabOverrides` "-")은 그대로다.
- 프로세서 등록 조건: `-LabCrowdFx=1`이고 `-LabCrowdFxEntity=1`이고 M1 이상 단계(`HordeOptLab.cpp`). 그 밖에는 등록하지 않아 M0\~M5와 다른 변형의 프로세서 구성이 그대로다. 등록되면 `lab_ism_processor` 끝에 `crowdfx_entity=1`이 붙는다(m5bounds·M4 실행에는 없음을 확인).
- 새 CSV 스탯: `Lab/CrowdRecs`(원소 합), `Lab/CrowdRecsSmall`, `Lab/CrowdRecsLarge`, `Lab/CrowdRecsHitDead`(그려지지 않은 피격·사망, 넣지 않은 수), 시간 `Lab/CrowdFxGather`(모으기 + Niagara에 넣기, ms).
- 새 CSV 메타데이터: `LabCrowdFxEntity`(1 엔티티 구동, 0 옛 방식, - 배경 무리 끔). 기존 열 이름은 그대로다. 뜻이 바뀐 열 하나: `LabCrowdFxParticles`는 이제 독립 입자만이다(1만에서 엔티티 구동이면 10,000, 옛 방식이면 16,544).
- 로그: `lab_config`에 `crowdfx_entity=`(배경 무리를 켰을 때만), `lab_crowdfx`에 `entity=`와 변수 확인(`small_recs= large_recs= now= orb_pos=`), 개발 빌드 `lab_crowdrecs`(5초마다), `lab_crowdfx_count`에 `recs=`.
- 사다리 7·8단계(`q2crowd`·`q4final`)의 뜻이 바뀐다. 예행 묶음 Reh1과 그 전 묶음의 7·8단계 수치는 옛 방식이다.

### 에셋 단위에 넘길 것

에셋(`/Game/Lab/FX/NS_LabCrowd`)에 이미터 둘(엔티티 구동 소형·대형)을 더하고 지금의 두 이미터는 바깥 독립 이미터로 둔다.

| 사용자 변수 | 형 | 코드가 넣는 때 | 값 |
| --- | --- | --- | --- |
| `User.LabSmallRecs` | Niagara Array Float4(`UNiagaraDataInterfaceArrayFloat4`, "Vector 4 Array") | 매 프레임 | 소형 원소 |
| `User.LabLargeRecs` | 같음 | 매 프레임 | 대형 원소(1종 실행이면 빈 배열) |
| `User.LabNow` | float | 매 프레임 | 월드 초(`UWorld::GetTimeSeconds`) |
| `User.LabOrbPos` | Vector(Position이어도 된다) | 활성화 전 한 번 | 오브 월드 위치(지금 (0, 0, 0)). 비슷한 기존 변수는 없었다 |
| `User.Speed`(기존) | float | 활성화 전 | 300(cm/s). 엔티티 구동 이미터도 이것을 쓴다 |
| `User.SmallRate`·`LargeRate`·`OuterRadius`·`Lifetime`(기존) | float | 활성화 전 | 바깥 독립 이미터용. `Lifetime`은 이제 166.67초 = (100,000 − 50,000) / 300 |

1. 원소 `(X, Y, T0, W)`: X·Y = 엔티티 월드 위치(cm, Z는 땅 0), T0 = 그 위치에 있던 월드 시각(초), W = 걷기 위상(초).
2. 외삽: `Dir = normalize(LabOrbPos.xy − (X, Y))`(오브 쪽), `P.xy = (X, Y) + Dir × Speed × max(LabNow − T0, 0)`, `P.z = 0`. 진행 방향은 `Dir`이다(속도 기반 정렬이면 속도 = `Dir × Speed`). `LabNow`는 컴포넌트가 다음 틱에 반영하는 값이라 배열과 한 프레임 어긋날 수 있어 0 아래를 자른다(차이는 5cm 정도). 엔티티 구동 이미터는 월드 공간(Local Space 끔)을 권한다. 시스템이 오브 위치(원점)에 있어 지금은 로컬로 둬도 같다.
3. 걷기 위상: AnimToTexture 자동 재생 프레임 = `StartFrame + fmod((Time + TimeOffset) × Playrate × SampleRate, 길이)`(engine-notes 17절). 실제 엔티티의 재생 시각이 지금 + W라서 Dynamic Material Parameter 1번의 **TimeOffset = W**(부호 그대로, 빼지 않는다), Playrate 1, StartFrame·EndFrame은 지금 값(소형 0..61, 대형 0..40)이다. 머티리얼 `Time`이 월드 시각과 같은 원점인지는 확인하지 못했다. 경계(입자 → ISKM)에서 발이 이어지는지 화면으로 본다.
4. 원소와 입자 대응: 원소 순서는 프레임마다 바뀐다(청크 순회 순서이고 태그가 바뀌면 엔티티가 청크를 옮긴다). 입자 ID에 원소를 묶지 말고 매 프레임 배열 길이만큼 다시 그린다(예: 매 프레임 배열 길이만큼 스폰하고 그 프레임에 죽이기, 또는 입자 수를 배열 길이에 맞추고 실행 인덱스로 매 프레임 원소를 다시 읽기). 모션 벡터가 튀지 않게 이전 위치를 현재 위치로 둔다. 배열이 비면 아무것도 그리지 않아야 옛 방식(`-LabCrowdFxEntity=0`)이 재현된다.
5. 입자 수: 1만 P1에서 소형 약 5,600, 대형 약 620(개발 실행). 2만은 약 두 배로 본다. 사전 할당·최대 수는 2만 기준으로 잡는다.
6. 메시 렌더러 거리 컬링(엔티티 구동 이미터): 카메라 거리 컬링 켬, **`MinCameraDistance` = 17,500cm**(엔진 진입 거리 18,800cm가 아니다, 위 "바로잡은 것"), 최대 거리는 끄거나 맵을 덮는 값. 바깥 독립 이미터에는 거리 컬링이 필요 없다(카메라 485m 밖).
7. 바깥 독립 이미터: 안쪽 반경 500m(50,000cm), 바깥 1,000m(사용자 확정값) 그대로. 수명은 `User.Lifetime`(166.67초)을 그대로 읽으면 안쪽 반경이 500m가 된다. 스폰율은 그대로(1만에서 소형 54, 대형 6). 정상 상태 1만 개(전 16,544). 워밍업 268초는 새 수명을 덮으므로 그대로 둬도 된다(옛 방식 275.74초를 덮지 못하는 것은 3단위부터 남은 일이다).
8. 그림자: 엔티티 구동 이미터 둘의 메시 렌더러만 `bCastShadows` 켬, 바깥 독립 이미터는 끔. 시스템의 `bOverrideCastShadow`가 켜져 있으면 컴포넌트가 시스템 값을 쓰므로(engine-notes 17절) 이미터 렌더러 값으로 가르려면 시스템 덮어쓰기를 끈다.
9. 바운드: 엔티티 구동 이미터도 GPU라 고정 바운드다. 시스템 고정 바운드(±1,050m)가 맵(500m)을 덮는다.

### 확인하지 못한 것

- 입자가 엔티티 자리에 그려지는 것과 경계에서 입자 → 메시가 이어지는 것. 에셋이 아직 새 변수를 갖지 않는다.
- Test 패키지의 모으기 비용과 GPU 비용(엔티티 구동 입자 약 6,200개에 그림자). 패키징하지 않았다.
- 카메라 거리 최소 184m의 원인 중 0.5초 청크 간격으로 설명되지 않는 약 2m.
- P2와 2만 실행.
