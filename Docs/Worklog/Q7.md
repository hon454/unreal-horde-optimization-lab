# Q7 애니메이션 예산 값과 총괄 묶음 Full3 작업 기록

사용자가 2026-11-13에 정한 일이다. Animation Budget Allocator의 예산 값을 측정으로 다시 정하고, 오브 `SnipeView` 경합을 고치고, 전 조건을 새 총괄 묶음 `Full3`으로 다시 잰다. 지난 항목은 고치지 않는다.

## 2026-11-13 코드

작업 세션 `budget-code`가 새 Test 패키지에 들어갈 코드 수정과 할당기 조사를 했다.

### 진행

- 조사 끝(성공). 할당기 소스, Mass 처리 단계 틱, 기존 프레임 CSV를 읽었다. 경합 수정 방법이 둘 이상이라 코디네이터에게 물었다. 다음은 구현.
- 구현 끝(부분 성공). 경합을 뺀 항목(1, 3\~6, 카운터 원자화)을 넣었다. 경합 수정은 코디네이터 답을 기다린다. 다음은 빌드.
- 빌드 끝(성공). `Scripts/build.ps1`, 경고는 기존 것뿐이다. 다음은 제외한 두 수정의 영향 실행.
- 결정 받음. 코디네이터가 경합 수정 A안을 전했다(사용자 답 "A안으로 진행"). 다음은 A안 구현.
- 구현 끝(성공). 경합 수정 A안을 넣고 code-tour.md를 맞췄다. 다음은 빌드와 실행.
- 실행 끝(성공). 제외한 두 수정의 영향 실행 16회가 모두 종료 코드 0이다(아래 "제외한 두 수정의 영향 크기"). 임시 패치는 되돌리고 다시 빌드했다. 다음은 단계별 작은 실행.
- 실행 끝(실패 하나 발견). 틀린 `-LabVariant` 실행이 `lab_variant_unknown`을 남기고도 종료 코드 0으로 끝났다. `StartPlay`(프레임 0)에서 부른 `RequestExitWithStatus(false, 2)`의 코드가 사라졌다. 종료 요청을 게임 모드 첫 틱으로 미뤘다(아래 "종료 코드"). 다음은 다시 빌드하고 단계별 작은 실행.
- 실행 끝(실패 하나 더). 첫 틱으로 미뤄도 종료 코드가 0이었다. Windows의 비강제 종료 코드는 프로세스 종료 코드에 닿지 않는다(아래 "종료 코드"). 설정·에셋 오류는 강제 종료로 바꿨다. 다음은 다시 빌드하고 확인.
- 실행 끝(성공). 단계별 작은 실행, 예산 인자 실행, 틀린 변형·단계 실행이 기대대로 끝났다(아래 "단계별 작은 실행"). 다음은 커밋.
- 커밋 끝(성공). `Source/`와 이 세션의 문서를 한 커밋으로 묶었다(해시는 git log의 `feat(budget): ...`). 푸시하지 않았다. 다음은 측정 세션의 `Budget1`.
- 기본값 4ms 끝(성공). 코디네이터가 ADR-0016 반영을 맡겼다. 상수를 4로 바꾸고 commands.md를 맞췄다. 빌드와 작은 실행 넷이 종료 코드 0이다(아래 "기본값 4ms"). 다음은 커밋.
- 변형 `full` 거부 수정 끝(성공). 기본값 4ms는 53f1dfb로 커밋했다. `Full3` L1이 종료 코드 2로 멈춰 `full`을 다시 매핑했다. 21개 조건 작은 실행이 모두 통과했다(아래 "변형 `full` 거부 수정"). 다음은 커밋.

### 측정 세션이 `Scripts/`에서 고칠 것

이 세션은 `Scripts/`를 고치지 않았다.

1. `summarize.py` `types_fields`(143\~151줄)는 `large_skip_ratio` = Skips ÷ Frames다. 보간이 들어 있다. 새 메타데이터 다섯 키(`lablargeactorinterps`, `labsmallactorframes`, `labsmallactorskips`, `labsmallactorinterps`, `labbudgetms`)를 읽어 종류별 건너뜀·보간 비율 열을 더해야 `Budget1`의 선택 기준을 계산할 수 있다. 기존 열은 Full2와 견주려면 그대로 두는 것이 낫다.
2. `ablation-check.py`와 `full-conditions.json`은 기대 키만 견준다. 새 키는 검사를 깨지 않는다. 인자를 주지 않은 실행의 `LabOverrides`는 그대로다.
3. `Budget1` 조건의 기대 메타데이터: `-LabBudgetMs=<x>`(x ≠ 2)는 `LabOverrides`가 `budget_ms=<x>`, `LabBudgetMs`가 `<x>`다. 예산 끔을 `-LabBudgetMs=0`으로 고르면 `LabOverrides` `budget_ms=0`, `LabBudget` 0, `LabTechAnimBudget` 0, `LabBudgetMs` `-`다. `-LabScreenSigBudget=0`으로 고르면 `A8-budget`과 같은 메타데이터다.
4. 종료 코드: 모르는 `-LabVariant`·`-LabStage`는 2, VAT·ISKM 에셋 없음은 3이다(강제 종료). 벤치 끝의 종료 코드는 `LabOk`와 무관하게 늘 0이다(아래 "종료 코드"). 실패 판정은 `LabOk`와 CSV 유무로 한다.

### 경합 수정

- 사실: Mass PrePhysics 틱 함수는 게임 스레드에서 워커 작업을 띄우고 바로 돌아온다(`MassProcessingPhaseManager.cpp:95-110`, `DontCompleteUntil`). 그동안 같은 `TG_PrePhysics`의 오브 틱이 게임 스레드에서 돈다. 둘 사이에 선후 선언이 없다(engine-notes.md 27절). 오브 틱이 `SnipeView`(구조체)를 쓰는 동안 워커의 저격·VAT·ISKM·ActorSync·CrowdFx 프로세서가 읽을 수 있었다.
- 카메라: `PlayerCameraManager`의 캐시는 `TG_PostPhysics` 뒤 `UpdateCameraManager`에서만 바뀐다(`Engine/Source/Runtime/Engine/Private/LevelTick.cpp:1847`). PrePhysics 안에서 읽는 카메라는 늘 직전 프레임에 그린 카메라다.
- 고친 뒤의 동작: 모든 프로세서가 같은 프레임에 같은 값, 곧 직전 프레임에 그린 카메라를 본다. 저격 요청은 늘 올린 그 프레임의 저격 프로세서가 가져간다.
- 고치기 전에 프로세서가 실제로 어느 프레임의 카메라를 봤는지는 확인하지 않았다. 오브 틱보다 먼저 읽으면 두 프레임 전 카메라를, 나중에 읽으면 직전 카메라(또는 반쯤 쓴 값)를 봤을 것이다. 저격 요청도 오브 틱이 저격 프로세서보다 늦으면 다음 프레임에 처리됐을 수 있다.
- 버린 대안: 이중 버퍼(B안)는 늘 두 프레임 전 카메라를 본다. 오브 틱을 Mass 단계 틱의 선행 틱으로 거는 것(C안)은 A안과 같은 카메라지만 엔진 틱 그래프와 높은 우선순위 처리(`mass.MakePrePhysicsTickFunctionHighPriority`)에 얽힌다.
- Development 실행으로 본 크기(측정값 아님, 1280×720, 호드 1만, 60초): 오브 시점 사망 수는 고치기 전 3,736·3,737·3,734, 고친 뒤 3,734·3,736이다. 탑뷰는 3,663·3,659와 3,664·3,678이다. 실행은 아래 표의 `Q7dev2-base-*`, `Q7fix-base-*`다.
- `Scripts/plot-code-tour.py` 73줄의 그림 글자 "ALabOrb: 저격 요청과 이펙트"는 이제 틀리다. 저격 요청은 단계 시작 대리자가 올린다. `Scripts/`는 측정 세션의 경로라 고치지 않았다.

### 종료 코드

- 증상: 틀린 `-LabVariant=q4fianl` 실행이 로그에 `lab_variant_unknown`과 `RequestExitWithStatus(0, 2, LabVariant)`를 남기고 종료 코드 0으로 끝났다(`Saved/Logs/LabDev-badvariant.log`, git 밖). 요청을 게임 모드 첫 틱으로 미뤄도 0이었다(`LabDev-badvariant2.log`).
- 원인: Windows의 비강제 종료는 `PostQuitMessage(코드)`뿐이다(`Engine/Source/Runtime/Core/Private/Windows/WindowsPlatformMisc.cpp:1517-1520`). `GuardedMain`은 틱 루프가 끝나면 초기화 때의 `ErrorLevel`을 돌려주고(`Engine/Source/Runtime/Launch/Private/Launch.cpp:188-204`), 실행 경로에서 `WM_QUIT`의 코드를 읽는 곳이 없다. 그래서 비강제 종료의 코드는 늘 0이 된다. 강제 종료는 로그를 비운 뒤 `TerminateProcess(코드)`다(`:1493-1515`, `WindowsPlatform.RaiseExceptionOnFaultTermination` 기본 거짓 `:140-144`).
- 고친 것: `LabRequestExit(코드, 위치)`가 코드를 기억하고 `ALabGameMode::Tick`의 첫머리가 강제 종료 `RequestExitWithStatus(true, 코드)`를 낸다. 이때 CSV 캡처는 아직 열리지 않았다.
- 확인: 틀린 변형(`-LabVariant=q4fianl`)과 틀린 단계(`-LabStage=M9`)가 모두 종료 코드 2로 끝났다(`LabDev-badvariant3.log`, `LabDev-badstage3.log`).
- 측정 세션이 알 것: 벤치 끝의 `RequestExitWithStatus(false, BenchExitCode)`(`LabGameMode.cpp` `TickBench` Flush 단계)도 같은 이유로 늘 0이다. `LabOk` 0인 실행도 종료 코드 0으로 끝난다. 러너의 `ExitCode -ne 0` 검사(`run-bench.ps1:146`, `run-full.ps1:251`)는 실패를 잡지 못하고, 실패는 `LabOk` 메타데이터와 CSV 유무로만 잡힌다. 벤치 끝은 CSV 파일을 닫는 시간을 두고 나가므로 강제 종료로 바꾸지 않았다. 바꿀지는 코디네이터가 정한다.
- 이번 커밋 전의 단계 오류(종료 코드 2)도 실제로는 0으로 끝났을 것이다. 지난 실행으로는 확인하지 않았다.

### 건너뜀 지표

- 엔진: 할당기는 보간 메시에 갱신하지 않는 프레임에도 틱을 켜고 `EnableExternalUpdate(false)`를 준다(`AnimationBudgetAllocator.cpp:465-482`). `ShouldTickAnimation()`은 외부 틱 제어 중이면 `bExternalUpdate`를 돌려준다(`SkeletalMeshComponent.cpp:1918-1923`). 그래서 옛 지표 `IsUsingExternalTickRateControl() && !ShouldTickAnimation()`는 보간 프레임을 건너뜀으로 셌다.
- 새 지표: 갱신하지 않은 액터 중 `IsUsingExternalInterpolation()`이 참이고 틱 함수가 켜진 것을 보간으로 따로 센다. 할당기는 `OnWorldPreActorTick`(`LevelTick.cpp:1675`)에서 결정하고 Mass PrePhysics는 그 뒤라, 지표는 그 프레임의 결정이다. 옛 주석의 "한 프레임 어긋날 수 있다"는 틀렸다.
- Development 실행 넷(`Q7fix-base-*`)에서 보간 수는 소형·대형 모두 0이었다. Development는 메시 하나의 게임 스레드 시간이 길어 넘은 몫이 커서 보간 몫이 0이 된다(engine-notes.md 29절 "보간 몫"). 같은 실행의 갱신하지 않은 비율은 대형 0.59, 소형 0.81이다(`Q7fix-base-P1-r1`, Development라 Test와 견주지 않는다).

### 9. BudgetedAnimation 1.96ms와 대형 건너뜀 1.29%

설명된다. 1만에서 예산은 다 쓰이고 있다. 대형 액터가 거의 건너뛰지 않는 것은 정렬 순서 때문이다.

1. 엔진 통계 `AnimationBudget/BudgetedAnimation`과 할당기의 작업 단위는 같은 두 구간(컴포넌트 틱, 병렬 평가 완료)의 게임 스레드 시간이다. 워커의 애니메이션 평가는 들어가지 않는다(engine-notes.md 29절). Full2 4단계 1만 P1의 `AnimationBudget/AverageWorkUnitTimeMs` 실행별 중앙값은 0.008\~0.009ms다.
2. 그래서 예산 2ms는 프레임당 약 2 ÷ 0.008 = 250 작업 단위다. Full2 4단계의 엔진 스탯 `Ticks/SkeletalMeshComponentBudgeted` 중앙값은 250·250·237이다. 할당기가 예산만큼 틱을 채운다. 이것이 BudgetedAnimation이 2ms에 붙는 이유다.
3. 수요는 최근 1초 안에 그려진 메시다. 같은 실행의 `Lab/ViewActors`(화면 안 보이는 액터) 중앙값은 279다. 동기화한 액터 373 가운데 나머지는 화면 밖이라 틱하지 않는다.
4. 계산(엔진 식, engine-notes.md 29절): 수요 약 280에 예산 250이면 넘은 몫 약 30이다. 매 프레임 갱신 = 250 − 30 × 0.8 = 약 226이다. 남은 예산 약 24에서 보간 = 24 − 30 × 0.4 = 약 12다. 나머지 약 40은 간격 2 이상으로 건너뛴다.
5. 정렬은 중요도가 큰 순이고 중요도는 화면 크기(바운드 반경 ÷ 카메라 거리)다. 대형은 반경이 커서 대부분 매 프레임 갱신 몫에 든다. 그래서 대형 건너뜀은 1.29%(옛 지표, 보간 포함)다. 갱신하지 않는 약 50개는 대부분 소형이고, 소형 약 240개의 약 20%다. 이 소형 비율은 계산값이고 Full2 CSV에는 소형 지표가 없다.
6. 같은 구조로 8단계의 대형 건너뜀 0.207도 설명된다. 8단계 1만은 화면 안 액터가 365다(`Full2-L8-q4final-N10000-P1-r1`). 예산 250에 넘은 몫 약 115라 매 프레임 갱신이 약 158로 줄고 대형도 밀린다. Full1(0.003)과 Full2의 차이 자체는 확인하지 않았다.
7. 글 04·08의 "1만에서 예산이 거의 쉰다"는 틀리다. 예산은 다 쓰이고, 건너뜀은 소형에 몰린다.
8. 선택 기준에 주는 뜻: 1만에서 액터 구간 건너뜀이 예산 끔과 구별되지 않으려면 예산이 수요 × 작업 단위만큼 있어야 한다. 8단계는 365 × 0.008 = 약 2.9ms다. 이것은 계산이고 `Budget1`이 잰다.

### 기본값 4ms

[ADR-0016](../Decisions/0016-animation-budget-value.md)에 따라 애니메이션 예산 기본값을 2ms에서 4ms로 바꿨다. 범위 피해 시간값과 `-FixedSeed`는 넣지 않았다(사용자 결정).

- 기본값은 `FLabScenario::BudgetMs`(`LabConfig.h`) 한 곳이다. `FLabConfig::BudgetMs`의 초기값, `-LabBudgetMs=` 비교(`LabOverrides`·HUD의 `budget_ms=<값>`), 0 이하를 받은 변형의 대체값이 모두 이 상수를 쓴다.

- `Docs/Guides/commands.md`의 `-LabBudgetMs=` 행을 4로 고쳤다. `code-tour.md`와 `measurement.md`에는 예산 값이 적힌 곳이 없었다(grep `2ms`, `2 ms`, `BudgetMs`, `예산`).

기준 2: 호드 2만에서 프레임 p95의 중앙값이 16.7ms 안이다.

**추천 값은 4ms다.** 두 기준을 모두 만족하는 값은 4ms 하나다. 사용자의 기준문은 개체 종류를 가르지 않아 대형·소형 둘 다 보았다. 대형만 보면 3ms가 기준 1을 만족하고 3ms도 기준 2를 만족하므로 추천이 3ms가 된다. 3ms는 소형 건너뜀이 0.065라 끔과 구별된다.

- 4ms의 호드 2만 p95는 16.47ms로 기준 16.7ms와의 여유가 0.23ms다. 세 실행 최댓값은 16.49ms다.

- 예산이 같아도 보간 몫이 있다. 2ms의 1만에서 대형 0.114, 소형 0.143이 보간이다. 건너뜀 비율에 보간은 들어 있지 않다.

### 글 세션에 넘길 것

사용자가 글 04의 "예산을 어떻게 정했나" 절에 더해 달라고 한 것이다.

1. 이 프로젝트는 최종 구성에서 Significance Manager를 쓰지 않는다. `ULabActorSyncProcessor`가 액터마다 바운드 반경 ÷ 카메라 거리(화면 크기)를 계산해 `SetComponentSignificance`로 할당기에 직접 넣는다(`LabActorSyncProcessor.cpp`, 줄은 글 세션이 확인한다). 이유로 적을 것: Significance Manager는 오브젝트가 등록하고 매니저가 중요도 함수를 부르는 구조다. Mass에서는 액터가 가까운 엔티티에만 붙었다 떨어져 등록과 해제가 계속 일어난다. 위치와 카메라 거리는 Mass가 이미 갖고 있고 ActorSync가 그 엔티티를 어차피 돈다. Mass의 `LODSignificance`를 변환해 넣는 방식은 같은 거리 구간에서 대형과 소형을 구별하지 못해 화면 크기 쪽을 골랐다([M3.md](M3.md), 글 세션이 근거를 직접 확인한다). Significance Manager는 1단계 하위 실험(액터 호드에 예산만 건 변형)에서만 쓴다.
2. 실무에서 우선순위에 더 고려할 수 있는 요소를 적는다. 사용자가 정한 표현은 "하지 않은 것"이 아니라 "실무에서 더 고려할 수 있는 부분"이다. 요소: 상태(피격, 사망, 공격 중), 화면 중앙과의 각도, 가려짐(엔진은 최근 1초 안에 그려졌는지만 본다), 플레이어와의 관계(표적, 공격자), 종류별 가중치, 떨림을 막는 이력. 함께 적을 사실: 4ms에서는 호드 1만의 건너뜀이 0이라 순서가 결과를 바꾸지 않는다. 순서가 일하는 것은 예산이 누르는 2만이다. 사망·피격 중인 액터가 얼마나 건너뛰는지는 재지 않았다. 엔진 소스 근거가 없는 항목은 일반적인 실무 관행이라고 밝혀 쓴다.

### 추정

- `Full3`의 2만 실행 셋이 모두 높은 것은 그 시간대(2026-11-13 17:32\~19:57)의 GPU 쪽 환경 때문일 것이다. 후보는 GPU 온도와 클럭, 백그라운드 프로그램의 GPU 사용이다. 어느 것도 기록이 없다.
- 같은 묶음의 다른 GPU 병목 조건이 오르지 않은 것은 설명하지 못한다. `L2` 2만이 문턱 근처라 눈에 띄었을 뿐 다른 조건도 비슷한 크기로 흔들렸을 수 있다. 다른 조건의 묶음 간 차는 대부분 2% 안이다("분석" 4).
- 세 묶음에서 r1 → r3로 GPU가 오르는 경향은 `AB1`에서 보이지 않는다. 원인은 모른다.

### 확인하지 못한 것

- 환경 요인 자체. GPU 클럭, 온도, 전력 한도, 다른 프로세스의 GPU 사용은 러너가 기록하지 않는다.
- df41c13 패키지로 직접 잰 `AB1` 값. 패키지가 덮어써져 28346dc로 대신했다. 두 빌드의 `L2` 경로 코드가 같다는 것은 소스 차이로만 확인했다.
- `AB1`은 조건마다 3회다. 0.1ms 크기의 차이는 가를 수 없다. 이 조사에 필요한 크기(0.6\~0.8ms)는 가른다.
