# 백로그

작업 중 떠오른 아이디어는 여기에만 적고 진행 중인 마일스톤에 넣지 않는다. 글 대기열은 마일스톤이 끝날 때 채우고, 글을 쓰면 지운다.

## 글 대기열

마일스톤 완료 시 항목을 더한다. 글은 최신 main에서 `Posts/NN-이름/`에 쓴다(수치는 가장 최근 전체 묶음, AGENTS.md "진행 방식"). 번호는 독자 순서다(마일스톤 번호와 다를 수 있다). 틀은 [posting.md](Guides/posting.md).

**글의 수치는 총괄 묶음에서 만든다(2026-11-10 사용자 결정, [ADR-0006](Decisions/0006-three-measurement-tiers.md)).** 프로젝트가 궤도에 오르면 글에 필요한 모든 점(전 단계 사다리, 하위 실험, 같은 N 비교점)을 최신 빌드 하나로 한 번에 다시 잰다. 시점은 사용자가 정한다. 그때까지 마일스톤 묶음의 값은 마일스톤의 판단에만 쓰고 글의 수치로 확정하지 않는다. M3b 묶음은 게임 창이 뒤에 있어 절댓값을 싣지 않는다.

**첫 총괄 묶음은 평지 시나리오에서 잰다(2026-11-11 사용자 결정).** 순서는 Budget 기본 채택(코드 변경과 개발 확인만, 60회 묶음은 총괄 묶음이 대신한다) → 움직이는 화면 검토 중 수치가 바뀌는 수정 → 총괄 묶음 → 글 00\~08 공개 → 장애물 + 플로우 필드 기준선이다. 장애물 기준선은 시나리오가 다른 새 기준선이므로 공개한 글 00\~08의 표를 고치지 않는다. 각 글의 측정 기록에 "평지 시나리오"라고 적는다.

글에 넣을 것(사용자 요청, 2026-11-07). 질답에서 나온 설명할 부분은 [post-material.md](post-material.md)에 모은다:
- Lumen을 끄거나 미니언을 Lumen에서 뺀 경우, Lumen이 무엇인지 짧게 설명하고 시험 중 Lumen이 프레임 저하를 일으켜 그렇게 했다는 경위를 쓴다. 근거 수치: M1 N=2000 Test 패키지 시험에서 미니언 ISM이 Lumen에 참여하면 GPU 29.0ms, 제외하면 5.3ms, Lumen 전체를 끄면 4.0ms(`Saved/Profiling/CSV/trial/`, 비교 수치가 아닌 시험 실행). 정식 수치는 그 글의 `measurements.md`에 다시 잰 값으로 둔다.
- 엔진 Mass ISM은 기본으로 그림자를 그리지 않는다(`FMassStaticMeshInstanceVisualizationMeshDesc::bCastShadows = false`). M0 액터와 맞추려고 켰다는 것.

## 미룬 마일스톤

- **비주얼 퀄리티 되사기(2026-11-09 사용자 요청).** 최적화로 아낀 예산을 화질에 다시 쓴다: 개체 수 조정, 근거리 액터 상한·하이드레이션 거리 늘리기, 사망 래그돌 예산, 거리별 VAT 품질 단계, 그림자·LOD 설정 등. 같은 프레임 예산(16.7ms)에서 N과 화질을 어떻게 맞바꾸나를 보여 주는 실험으로 짠다. 래그돌·VFX 제작 자체는 비목표라 "예산과 비용"으로만 다룬다. 이때 근거리 부위 판정과 피직스 바디(판정용 피직스 애셋, Kinematic + QueryOnly, 래그돌 예산)를 어떻게 켤지 함께 논의한다(2026-11-09 사용자 요청, M3b부터 액터 캡슐 콜리전은 끈다). 액터 배정(하이드레이션 예산)에 화면 크기 중요도를 넣는 것도 여기서 다룬다: 엔진 표현 LOD의 개수 상한은 거리 버킷별로 화면 안 먼저 채우고(`MassLODCalculator.h` `AdjustDistancesFromCountForRuntimeData`) 개체별 크기 보정이 없다. 같은 거리면 대형을 먼저 액터로 만들려면 LOD 계산기를 바꾸거나 개체별 거리값을 크기로 나눠 넣어야 한다. M3b의 E3 (3c)는 애니 예산 중요도만 잰다(2026-11-09 결정 3, M3b 범위 밖). 상한 대비 자동 링도 여기다: 액터 상한에 닿으면 화면 밖 Base 거리를 0으로 내려 링 액터가 화면 안 액터를 뺏지 않게 한다(2026-11-09 E3b 빠른 회전 캡처에서 20k·상한 500일 때 `m3vis15`가 12회 모두 회복 못 했고, 5k에서는 상한이 남아 문제가 없었다). 위치는 "장애물 + 플로우 필드" 기준선 뒤, M6 나이아가라 앞(2026-11-09 결정 7로 갱신. 처음에는 M5 뒤 첫 항목이었다): 최종 파이프라인과 최종 지형 하나에서 한 번 잰다.
- **M6 나이아가라 배경 티어 — "나이아가라로 전부 그리면 안 되나".** 맵 끝 너머 지평선에 수십만 개의 개체를 나이아가라 GPU 시뮬레이션 + VAT 메시 렌더러로 분위기용으로만 그린다. Mass 밖, 상호작용 없음. 가치 있는 실험은 "같은 VAT 메시를 Mass ISM으로 그린 M2와 개체당 GPU 비용 비교"다. 비목표(VFX 제작)와 겹쳐 M5 뒤로 미뤘다(2026-11-06).
- **M4b StateTree + Signal.** plan.md M4의 선택 항목. 글 하나 분량이 안 나오면 여기로.
- **3종째 개체(원거리 미니언).** 종류 수가 아키타입·VAT 텍스처·ISM/ISKM 컴포넌트·트랙·액터 풀을 어떻게 늘리는지. 새 기준선이 필요하다.

## 잘라낸 실험

- **넉다운 상태**(피격 → 쓰러짐 → 기상 → 다시 접근). StateTree 전이 다양성용이었지만 쓰러진 개체가 밀도 분포와 전환 빈도를 바꾸는 시나리오 변수라 뺐다. 즉사만으로 전이(접근 → 피격 → 사망)는 충분하다.
- **Niagara Examples Pack으로 오브·저격 시각화.** 5.8 호환 확인과 라이선스 관리 비용. 구체와 디버그 라인으로 충분하다. 영상 품질이 필요해지면 그때.
- E1 부록: 프로세서 하나 vs 셋, 프래그먼트 크기. E2: `AnimationMinScreenSize` 효과. E3: `BudgetMs` 1/2/3 스윕, 풀 크기. E5: 애니 수 10/50/200 메모리 곡선, N 100k+.
- 저해상 액터 티어(AnimBP 없이 시퀀스만). 액터 ↔ ISM 두 단계로 시작한다.

## 선택 심화

- **장애물 + 플로우 필드(총괄 묶음 뒤 새 기준선. 2026-11-09 결정 7 A안을 2026-11-11 사용자가 바꿨다).** 글을 먼저 공개하려고 총괄 묶음을 평지에서 먼저 잰다. 글 00\~08의 수치는 평지 시나리오의 값으로 남기고, 장애물 결과는 새 글로 낸다. 그래서 이 기준선에서 전 단계를 한 번 더 잰다. 평지에 장애물(기둥·벽)을 두고, 목표(오브)가 고정이므로 맵 전체 방향장을 한 번 계산해 모든 개체가 읽는다. 액터 기준선(M0)도 같은 방향장을 읽게 해 비교를 공정하게 둔다. 시나리오 변수라 이전 단계를 전부 다시 잰다(처음 A안은 이 재측정을 총괄 글 08의 묶음과 합치는 것이었다). 회피와의 관계는 M4 (c) 결과를 보고 정한다. 호드 고유 재료다(Shabel ISM 11만 개 플로우 필드 데모, talk-notes.md 31:39). 버린 대안: 퀄리티 뒤(퀄리티 수치가 평지 전용이 되어 재측정 한 번 더), M3b에 포함(M3b가 길어지고 실패 원인을 가르기 어렵다), 선택 항목 유지(호드 재료가 빠진다).
- **현실성 검증(위 장애물 기준선에 묶음).** 경사가 있는 지형에서 M0 `full`과 최종 단계를 앵커 N {1k, 5k}로 한 번씩 재서 평지 결과와의 차이를 "참고"로 적는다. 평지는 액터(CharacterMovement 바닥·스텝 처리)와 Mass(높이 샘플링·장애물 회피) 양쪽을 조금씩 유리하게 본다(2026-11-07 사용자 승인).
- **ISKM 이전 변환 엇갈림(모션 블러 줄무늬).** 개발 빌드 20k P1에서 일부 ISKM 인스턴스가 37\~66초에 한 프레임씩 잘못된 세로 모션 벡터를 받는다. Lab의 `PrevTransform`은 정상이다. 엔진의 `MassVisualizationComponent.cpp:716-838`(`SetInstancePrevTransform`, `RemoveInstances`)이나 GPU Scene 인스턴스 추가·삭제 경로를 확인한다. 고칠 때까지 모션 블러는 기본값으로 둔다([ADR-0007](Decisions/0007-keep-default-motion-blur.md), Worklog/M5.md "미니언 깜빡임 진단").
- **ISKM 바운드 일반화.** ISKM 바운드를 카메라 추종 상자로 일반화하고, 오브가 움직이는 장면에서 격자 칸 분할과 비교한다(2026-11-11 `m5bounds` 결정 때 사용자 지적).
- 공간 격자 기반 저격 대상 선택(지금은 결정적 해시). 범위 피해·저격·ActorSync가 매 프레임 전 N을 순회한다(2026-11-09 점검). M4 뒤 실험.
- Lab 프로세서 그룹을 게임 스레드 밖으로(`OffGameThreadGroupNames`, City Sample `DefaultMass.ini:7`). M3b에서 그룹을 선언한 뒤 M4에서 시험.
- `m3visoff`: 화면 밖은 80m부터 안 그리기(Base Off 80m). E3b (8) 뒤 후보.
- 바닥 밴드 표시(결정 6 확정, 2026-11-09): 개발 빌드 인자 `-LabBandFloor`가 있으면 Floor의 머티리얼을 `Content/Lab/Materials/M_LabBandFloor`로 바꾼다. 띠는 **오브 중심** 30/80/200m(저격 구간 `FLabSnipeBands`와 같다). 중심은 머티리얼 파라미터로 한 번 넣는다(오브는 맵 중앙 고정). 표현 LOD는 카메라 기준이라 P1에서 XY 최대 15m 어긋난다(카메라가 오브 뒤 15m, `MassLODSubsystem.cpp:376-377`). 글에 그 한 줄을 적는다. P2(탑뷰)는 끈다(3D 거리라 200m 경계가 XY 173m). 측정 빌드는 기본 바닥. 에디터에서 만들고 순서를 `Scripts/create-band-floor.md`에 적는다. 버린 대안: 카메라 중심(띠가 1rpm으로 돈다), `DrawDebugCircle`(가늘고 Test에서 안 나온다), 링 메시(테두리만).
- LOD 기준점을 오브로 옮기기: `UMassLODSubsystem`의 `bUsePlayerPawnLocationInsteadOfCamera`(`MassLODSubsystem.cpp:367-370`)로 뷰어 위치를 폰(오브)으로 둘 수 있다. 거리 밴드의 기준이 바뀌는 시나리오 변수라 M0 고정을 깬다. 새 기준선을 또 세울 때만 검토(2026-11-09 결정 6 대안 D).
- "통합 Mass"(액터 없는 근거리) 프로토타입과 하이드레이션 비교.
- 거리별 VAT 품질 단계: 가까운 쪽은 상세 메시 + 본 영향 4, 먼 쪽은 간략 메시 + 본 영향 1로 따로 굽는다(2026-11-08 M2 결정 1의 D안, 변수 둘이라 M2에서 뺐다).
- 근거리 부위 판정 비용(2026-11-09 사용자 질문에서). 하이드레이션 액터에 판정용 피직스 애셋(뼈마다 QueryOnly 바디)을 켜고 트레이스 피격을 엔티티 사건으로 넘길 때의 비용을, E3 (6)의 캡슐 하나(20k 1.55ms)와 비교한다. 무기 전투는 비목표라 판정과 비용만 다룬다. 원본 피직스 애셋은 Simulated라 Kinematic·QueryOnly로 바꿔야 한다(engine-notes.md 9절).
- 근거리 사망 래그돌 예산(2026-11-09 사용자 질문에서). 래그돌 동시 상한, 멈춘 뒤 정지 포즈로 굳히기·정리 규칙이 하이드레이션 액터 상한(500)과 어떻게 다투는지. 원거리 사망은 VAT 그대로.
- Replication LOD 개념 — DS 실험실과의 접점. 구현하지 않는다.
- 소스 빌드가 필요한 엔진 패치(ISKM 트랙 해제 경로) — 엔티티 풀링 우회가 안 될 때만.
- **M4에서 나온 후보 셋(2026-11-10, 순서는 M4 수치를 본 뒤 정한다).** (a) Simulation LOD 개체 수 상한(`LODMaxCount`) 실험. M4는 무제한이다. (b) `UE::Mass::FExecutionLimiter`로 프레임당 개체 수 예산을 거는 실험. 엔진 가변 틱은 엔티티가 드나든 청크를 바로 돌려 설정 간격이 실제 주기에 닿지 않았다(Worklog/M4.md). 예산 방식과 비교한다(동작은 engine-notes.md 5절). (c) 먼 무리를 개체가 아니라 덩어리로 돌리기. 시나리오에 닿으므로 새 기준선 마일스톤이 된다. (d) `Config/DefaultMass.ini`로 엔진 이동 프로세서 둘(`MassApplyMovementProcessor`, `MassSmoothOrientationProcessor`)을 LOD 그룹 뒤로 보내는 실험. 탑뷰 병렬에서 LOD 프로세서가 이동 프로세서가 끝날 때까지 기다린다는 추정(청크 충돌)을 확인하는 길이다. ini는 조건이 없어 M0\~M4 모든 단계에 적용되므로 채택하면 전 단계를 다시 잰다. 프레임 이득은 기대하지 않는다(탑뷰는 GPU 병목). 설정 문장은 engine-notes.md, 근거는 Worklog/M4.md "표현 LOD 대기: 가르는 트레이스". (e) 가까운 개체만 비켜 가기(`m4avoid`)가 프레임 +10.6ms인데 세 스레드 p50 어느 것보다 프레임이 10ms 길다. 어디서 기다리는지 가르지 않았다. (f) `m4offmove`에서 남긴 것: `m4mass`와 밴드 경계를 맞춘 비교(188m 대 200m), 병렬 실행에서 `Lab/AllWorkers/OffMove`가 0.4\~1.3ms로 찍히는 이유(직렬은 0.02ms), 움직이는 화면의 200m 경계.
- **200m 밖을 싼 표현으로 채우기(2026-11-11).** 낮은 카메라에서 무리 끝과 수평선 사이가 비어 보인다. VAT 인스턴스를 그대로 멀리 그리면 `m4offmove` P1 20k에서 프레임 p50이 300m +3.11ms, 500m +8.35ms다(Worklog/M4.md "측정 세션: 그리는 거리 묶음"). 늘어난 몫의 대부분이 그리는 비용이므로(Off 경계를 200m에 두어도 되찾는 것은 0.46 / 1.23ms로 추정) 거리를 늘리기보다 개체당 비용이 낮은 원거리 표현(임포스터, Niagara, 덩어리)을 본다. 시나리오 고정값(그리는 끝 200m)을 바꾸므로 새 기준선 마일스톤이 된다. 재려면 Off 경계를 따로 두는 인자와, 그려지는 Off 개체를 매 프레임 옮기는 처리가 필요하다(1초에 약 3m씩 끊겨 보인다). 글 재료는 post-material.md "06".
