# 글 준비: 인사이트, 재료 선별, 사실 확인

2026-11-12에 글 재료([post-material.md](post-material.md)) 46개 항목과 Worklog·ADR을 최종 측정(`Measurements/Full1/`)과 엔진 소스에 대조한 결과다. 글을 쓰기 전에 재료를 정리하는 근거로 쓴다. 앞의 세 절은 코디네이터의 종합이고, "항목별 확인"부터는 확인 작업의 원문이다. 글을 다 쓰면 이 문서는 지운다.

## 핵심 인사이트

최종 측정이 직접 받치는 것만 적었다. 값은 호드 총수 1만, 오브 시점(P1), 세 회차 중앙값이다.

1. **액터 군중의 벽은 애니메이션이 아니라 이동 컴포넌트다.** 액터 1만의 게임 스레드 446ms 가운데 `UCharacterMovementComponent`의 틱이 323ms(72%)다. Animation Budget Allocator와 URO를 덧대도 프레임은 401ms, 422ms다(441ms에서). 개체당 Game 시간은 500\~2천에서 17µs로 평평하다가 1만에서 43µs로 뛴다(프레임이 길어지면 하위 스텝이 는다).
2. **로직을 Mass로 옮기면 게임 스레드가 427ms에서 6.1ms가 된다.** 60fps를 지키는 최대 개체 수는 797에서 20,250으로 25배다.
3. **병목은 단계마다 옮겨 다니고, 프레임 시간만 보면 기법의 값을 놓친다.** 2·3단계는 GPU, 4\~6단계는 Game, 7·8단계는 다시 GPU가 병목이다. 최종 구성에서 기법을 하나씩 빼면 다섯 행은 프레임이 ±0.1ms 안인데 Game에서는 갈린다(하이드레이션 −4.07ms, 애니메이션 예산 +0.82ms, Simulation LOD +0.64ms).
4. **Simulation LOD는 틱 간격이 아니라 프로세서를 건너뛰어야 프레임이 준다.** 4 → 5단계의 프레임 p50이 1만 / 2만 / 3만에서 −0.56 / −1.43 / −2.19ms다. 틱 간격을 0.5초로 적어도 실제 주기는 0.11초였다(2만).
5. **ISKM의 이점은 GPU 프레임 시간이고, 전환 품질이 아니었다.** VAT로 되돌리면 +1.28ms다(디스턴스 필드 비용이 1.38ms에서 0.04ms로 사라진 것이 크다). 전환이 티 나는 정도는 4.63 대 5.22로 시드 사이 흔들림 안이다. 앞선 1회 측정의 우위(4.31 대 6.04)는 다시 나오지 않았다.
6. **200m 밖을 입자로 그리는 것은 싸지 않았다.** 입자를 빼면 −3.66ms다. 입자 대신 ISKM으로 그리면 프레임은 비슷한데(11.82 대 11.12) 병목이 Game으로 옮겨 간다. 고른 것은 "더 싼 쪽"이 아니라 "남는 쪽 예산을 쓰는 쪽"이다.
7. **번 시간을 품질에 쓰는 데도 상한이 있다.** 80m 밖 그림자를 꺼서 1.40ms를 벌고 액터를 40m·상한 1,000으로 올렸다. 그런데 2만부터는 예산에 눌려 대형 액터의 애니메이션 건너뜀 비율이 0.64가 된다(1만은 0.003).
8. **전환 대책은 프레임으로는 0이고 화면으로만 보인다.** 끄면 눈에 띄는 전환이 3\~5%에서 9\~11%가 된다.
9. **이점이 보이지 않은 기법도 있다.** 엔티티 풀은 프레임, Game, 전환 어느 지표에서도 갈리지 않았다. 남긴 이유는 ISKM 트랙 누수 우회인데 60초 측정에서는 그것도 보이지 않는다.
10. **측정 자체가 흔들린 사례가 재료다.** 2단계 2만은 실행마다 렌더 스레드의 `PrepareDistanceFieldScene`이 8.6ms와 15.2ms로 갈렸다. 환경(다른 프로그램)이 수치를 흔든 사례, 실험 설계가 틀렸던 사례(사망 0 / 초당 1천)도 기록이 있다.

## 사실 확인에서 나온 문제

**구조적 문제 하나.** 글 재료의 측정값은 거의 전부 옛 묶음 값이다. 그리고 경위의 핵심 비교 여럿은 최종 측정에 대응 조건이 없다: 애니 없는 액터·폰 변형, 액터 5천, 직렬 실행, VAT만 바꾼 단계, 틱 간격만 바꾼 변형, 그리는 거리 300·500m, 비켜 가기. 지금 규칙([ADR-0006](Decisions/0006-three-measurement-tiers.md))으로는 이 값들을 글의 수치로 쓸 수 없다.

**틀렸거나 받쳐지지 않는 문장(고칠 것).**

- "30m 경계가 실제로는 27m": 액터 전환 경계에는 히스테리시스가 없다(`MassLODCalculator.h:868-886`).
- "거리 필드는 스플라인도 있다": 틀렸다(`SplineMeshSceneProxy.cpp:119,496`). engine-notes 11절도 같은 오류다.
- ISKM 블렌딩 인용 파일: `AnimSequenceTransformProviderData.h`가 맞다. engine-notes 44행도 틀렸다.
- `MassZoneGraphAnnotationFragments.cpp`는 City Sample이 아니라 엔진 플러그인 `MassAIBehavior`의 파일이다. engine-notes 5절도 같다.
- 표현 종류는 넷이 아니라 다섯이다(`MassRepresentationTypes.h:36-43`).
- "VAT의 커스텀 데이터 쓰기가 Game을 늘렸다": 뒤 항목이 뒤집었다(약 2ms는 `WaitForQueryResources` 대기).
- "2,000명 약 38ms, 5,000명 약 150ms"는 프레임이 아니라 Game p50이다.
- 병렬 처리 "차이가 없었다": 5만에서는 직렬이 범위 밖으로 빠르다.
- "E3 (6) 20k 1.55ms": 기록값은 1.46ms다(M5.md가 정정).
- "엔티티 재활용은 기본": 측정이 받치지 않는다.
- "눈에 띈 전환 0%": 최종 구성에서는 3\~5%다.
- Simulation LOD를 매기는 주체는 Trait이 아니라 `UMassSimulationLODProcessor`다.
- 줄 번호가 밀린 인용 넷(`LabMinion.cpp:194`, `LabVatProcessor.cpp:39`, `LabMassProcessors.cpp:234`, `MassActorSpawnerSubsystem.cpp:328`).
- 출처를 찾지 못한 값: 813, 1,128, 24.6ms, 14.5ms와 6.7ms, "PrePhysics의 48%", CharacterMovement 1k 8.6ms.

**확인하지 못한 것.** 옛 묶음 값은 Worklog 문장과만 대조했다(`summary.csv` 행은 일부만). 트레이스 원본과 `Saved/`의 프레임 CSV는 열지 않았다. 건너뜀 비율이 조건마다 갈리는 이유(`A8-crowdfx` 0.134 대 L8 0.003). `A8-farcull`의 Game +3.78ms가 어느 프로세서인지. ISKM의 애니메이션 갱신 주기.

먼저 알아 둘 구조 차이
- Full1에는 "틱만 줄인" 변형(`m4mass`)과 "간격 0"(`m4off`)이 없다. Simulation LOD는 L5에서 자체 이동(offmove)과 풀과 함께 한 번에 들어간다. 그래서 06 절의 핵심 대비("틱만 줄이면 그대로, 프로세서를 빼면 준다")는 Full1 안에서 재현되지 않는다. 옛 M4 묶음 값으로만 성립한다.
- Full1의 로직 밴드는 `80/200m tick=0/0.50/1.00 offmove=1`이다. 200m 밖은 Low가 아니라 Off 밴드(자체 이동)다(`sim_band_low` 0, `sim_band_off` 1만 5,992 / 2만 11,885\~11,894).
- Full1의 P2는 1만뿐이다. 2만 P2 값은 대응이 없다.
