# v2 사양 문서

- 상태: 잠정 확정(2026-11-15). 사용자가 자리를 비운 동안 코디네이터가 추천안으로 정했다. 사용자 검토를 기다린다.
- 결정의 근거, 대안, 득실은 [autonomous-decisions.md](Worklog/autonomous-decisions.md)의 D33부터에 있다. 방향은 [ADR-0017](Decisions/0017-roaming-orb-and-equal-function-ladder.md)이 정했다.
- 이 문서는 "무엇을 만들고 무엇으로 재는가"를 정한다. 순서와 작업 단위는 [v2-plan.md](v2-plan.md)에 있다.
- 근거 수치는 시험 실행 묶음 `Spike1`, `Spike2`의 값이다([Worklog/V2.md](Worklog/V2.md)). 설계 근거로만 쓰고 공개 문서에는 쓰지 않는다.

## 1. 목표

- 목표 사양은 호드 총수 1만, 60fps다. 판정은 이동 시나리오에서 프레임 p95가 16.7ms 안인 것이다.
- 주 지표는 목표 총수에서의 프레임 시간(p50, p95)이다. 60fps를 지키는 최대 N은 보조다.
- 최종 구성의 모든 기법은 총괄 묶음에서 이점이 보여야 한다. 이점은 프레임 시간, 같은 프레임에서의 품질, 화면 가운데 하나다([plan.md](plan.md) "이점의 원칙"을 잇는다).

## 2. 시나리오

바뀌지 않는 값(맵 반경, 2종과 비율, 체력 60\~240, 저격 구간, 시드, 초기 배치의 분포)은 [measurement.md](Guides/measurement.md) "확정값" 그대로다.

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 장면 | 평지. 장애물과 경로 탐색 없음 | ADR-0017 결정 4 |
| 오브의 궤도 | 원. 반지름 57.3m, 높이 6m. 원의 중심은 맵의 중심(원점)이다 | `Spike1` 후보 A, D34 |
| 초기 배치와 재생성 링 | 맵의 중심 둘레다. 오브를 따라가지 않는다 | D34 |
| 궤도 속도(이동 시나리오) | 2m/s. 한 바퀴 180초 | `Spike2`, D34 |
| 궤도 속도(정지 조건) | 0 | ADR-0017 결정 7 |
| 미니언 속도 | 3m/s | `FLabScenario::MoveSpeed` |
| 카메라 | 오브를 따라간다. 배치와 회전(1rpm)은 옛 P1과 같다. 탑뷰도 오브를 따라간다 | 시험 실행의 P3 |
| 워밍업과 측정 구간 | 워밍업 60초 + 측정 180초. 측정 구간은 궤도 한 바퀴다 | D34 |
| 오브 위치 | 월드 시각의 함수 하나. 오브, 카메라, 스포너, 입자가 같은 함수를 쓴다 | 시험 실행의 `FLabOrbit::LocationAt` |

- `Spike2`에서 2m/s는 액터 상한에 닿지 않았고(최대 782) 값이 궤도 위의 위치를 따라 오르내렸다. 시험 실행의 궤도는 중심이 (0, 57.3m)로 치우쳐 있었다. 중심을 맵의 중심에 두면 장면이 회전 대칭이라 값이 일정해질 것으로 본다. W1이 두 바퀴를 돌려 첫 바퀴와 둘째 바퀴의 평균이 5% 안에서 같은지 확인한다. 다르면 워밍업을 한 바퀴로 늘린다.
- 2.5m/s는 액터 상한에 닿고, 3m/s 이상은 호드가 오브 둘레에 끝없이 쌓인다(`Spike2`). 그래서 사다리 속도로 쓰지 않는다.
- 궤도, 속도, 구간의 값은 `FLabScenario`의 상수로 둔다. 인자는 탐색과 정지 조건용으로만 남긴다.
- 궤도 값과 구간은 `v2`의 첫 총괄 묶음 직전에 동결한다([ADR-0002](Decisions/0002-freeze-measurement-infra.md)를 다시 건다).

## 3. 모든 단계가 하는 기능

사다리의 모든 단계는 아래 넷을 한다. 단계는 같은 일을 더 싸게 하는 것만 바꾼다.

1. 움직이는 오브를 쫓는다. 목표는 오브의 지금 위치다.
2. 서로 겹치지 않는다. 가까운 이웃과 몸통 반지름의 합보다 가까워지지 않게 민다.
3. 가까운 개체는 캡슐 콜리전을 가진다. 범위는 액터로 그리는 개체다. 액터 기준선은 전 개체다.
4. 피해를 받고 죽는다. 범위 피해, 저격, 사망, 재생성은 지금과 같다.

판정 방법:

- 겹침: 프레임마다 "몸통이 겹친 쌍의 수"를 표본으로 세어 CSV에 남긴다. 단계 사이의 동등성 검사에 넣는다. 허용 범위는 구현 작업 단위에서 재서 정한다.
- 캡슐: 오브의 저격이 액터 구간의 대상에는 캡슐 라인 트레이스로 맞는지 확인한다. 트레이스 수를 CSV에 남긴다.
- 기능을 거리로 줄이는 것(먼 개체의 겹침 방지를 드물게 하기)은 "같은 일을 더 싸게"가 아니라 Simulation LOD 단계의 내용으로 적고, 그 단계의 이점과 함께 겹친 쌍의 수를 보고한다.

## 4. 표현과 거리 구간

- 출발값은 [ADR-0010](Decisions/0010-final-representation-bands.md)과 [ADR-0011](Decisions/0011-entity-driven-crowd-particles.md) 그대로다: 액터 0\~40m(상한 1,000), ISKM 40\~80m 그림자 켬, ISKM 80\~200m 그림자 끔, 200\~500m 엔티티 구동 입자, 500\~1,000m 독립 입자.
- 기능(겹침 방지, 캡슐)이 들어간 뒤 목표 사양을 넘으면 액터 상한과 전환 거리를 조정한다. 조정은 "품질 올리기" 작업 단위에서 재서 정하고 ADR 초안으로 남긴다.

### 4.1 전환(사용자 요구)

- 전환은 양방향이다. 오브와 카메라가 움직여 개체가 구간을 안팎으로 넘는다.
- 지표: 방향별 초당 전환 수, 2초 안에 같은 경계를 되넘는 왕복 수. Test 패키지의 CSV에 남긴다(시험 실행의 `ULabRepSwitchCountProcessor`를 잇는다).
- 규칙:
  - 경계마다 히스테리시스를 둔다(지금 10%).
  - 한 번 바뀐 개체는 최소 유지 시간 동안 다시 바뀌지 않는다. 값은 재서 정한다.
  - 액터 상한에 닿으면 가까운 순으로 액터를 준다. 상한에서 액터와 인스턴스 사이를 오가지 않게 한다. `Spike1`의 3m/s에서 왕복이 초당 34건이었다.
- 목표: 이동 시나리오의 왕복 수가 정지 조건의 두 배 안이다. 값은 구현 뒤에 재서 다시 본다.

### 4.2 움직이는 오브에 맞게 다시 만드는 기법(사용자 요구)

| 기법 | 지금의 전제 | v2 |
| --- | --- | --- |
| 200m 밖 자체 이동 | 고정 목표로 등속 직진 | 틱마다 오브의 지금 위치로 방향을 다시 잡는다. 틱 사이의 오차를 재서 적는다 |
| 엔티티 구동 입자의 외삽 | 처음 넣은 오브 위치를 향한다 | 오브 위치를 매 프레임 넣는다. 입자의 방향과 엔티티의 방향이 전환 순간에 같다 |
| 맵 밖 독립 입자 | 원점 둘레의 고리 | 그대로 둔다. 재생성 링이 맵의 중심 둘레라 어긋나지 않는다 |
| ISKM 고정 바운드 | 카메라가 원점 둘레 상자 안에 있다 | 상자가 카메라를 따라간다. 옮기는 간격은 재서 정한다 |

- 사용자가 본 증상(입자에서 바뀌어 보여야 할 개체가 안 보인다)을 영상 비교로 재현하고 원인을 확정한다. 고친 뒤 같은 영상으로 확인한다.

### 4.3 ISKM 번쩍임(사용자 요구)

- ISKM 구간의 개체가 번쩍이지 않는다. 사용자가 떠다니는 오브 장면에서도 보았다(2026-11-15).
- 원인 후보는 일부 인스턴스의 잘못된 이전 프레임 변환이다([Worklog/M5.md](Worklog/M5.md) "미니언 깜빡임 진단").
- 모션 블러를 끄는 우회는 쓰지 않는다([ADR-0007](Decisions/0007-keep-default-motion-blur.md)). 엔진 경로에서 원인을 찾아 Lab 코드에서 막는다. 막을 수 없으면 대체 ADR 초안을 쓰고 사용자에게 알린다.

## 5. 구현의 원칙

- 첫 Mass 단계는 엔진 프로세서를 그대로 쓴다(이동, 회피, 표현). 직접 짠 구현은 트레이스로 병목을 보인 뒤의 별도 단계다(ADR-0017 결정 6).
- Lab 프로세서는 서브시스템을 `AddSubsystemRequirement`로 선언하고 실행 컨텍스트에서 받는다. `World->GetSubsystem`과 `FScopeLock`으로 공유 상태를 만지지 않는다.
- 저격 대상은 틱마다 달라져야 한다. 해시를 고치고, 뽑힌 일련번호의 분포를 작은 실행으로 확인한다.
- 단계는 한 빌드 안의 실행 모드다([ADR-0004](Decisions/0004-stages-as-run-modes.md)). 사다리에 없는 옛 변형과 고정 목표 전용 코드는 지운다.
- 군중 최적화와 무관한 기능은 만들지 않는다([AGENTS.md](../AGENTS.md) "구현").

## 6. 화면의 장치

- 화면 우상단에 오브 HUD(위치 X·Y, 속도)와 그 아래 카메라 HUD(회전 속도, 한 바퀴 시간)를 둔다. 화살표는 없다.
- 양식은 좌상단 성능 HUD와 같다. 측정 실행에서는 성능 HUD와 함께 끈다. 촬영 실행에서 켠다.
- 기둥과 흔적은 쓰지 않는다.

## 7. 측정

- 장치(러너, CSV 스키마, 요약, 그림, 사이트)는 그대로 쓴다. 더하는 열: 궤도 메타데이터, 방향별 전환 수, 왕복 수, 겹친 쌍의 수, 캡슐 트레이스 수.
- 정지 조건은 최종 구성과 그 빼 보기에만 붙인다. 사다리는 이동 시나리오로만 잰다.
- 실행 간 편차: `Spike1`에서 이동 장면의 5회 범위는 프레임 p50 0.08\~0.21ms였다. 조건마다 3회를 기본으로 하고, 0.5ms 아래의 차이를 주장하는 비교는 5회로 잰다.
- 측정 구간이 240초(워밍업 포함)로 늘어 조건 수를 줄여야 한다. 조건 표는 [v2-plan.md](v2-plan.md)에서 정한다.
- `v1`의 수치와 잇지 않는다. 총괄 묶음 이름은 `Full4`다.

## 8. 하지 않는 것

- 장애물, 경로 탐색, 방향장, 부위 판정, 래그돌.
- 미니언끼리의 물리 충돌 해소(캡슐끼리 밀기). 겹침 방지는 조향으로 한다.
- main 병합, `gh-pages` 배포. 사용자 승인 뒤에 한다.
