# ADR-0018 ISKM 번쩍임은 트랙 풀을 미리 늘려 막고, 모션 블러는 엔진 기본값(켬)으로 둔다

- 상태: 승인됨(2026-11-15 채팅에서 사용자가 승인. W9 작업 세션 초안. ADR-0007을 대체한다)
- 날짜: 2026-11-15

ADR-0007은 ISKM 개체가 한 프레임씩 길게 끌리는 번쩍임을 고치지 않고 모션 블러를 켠 채 재기로 했고, 원인을 찾으면 그 ADR을 대체한다고 적었다. W9에서 원인을 엔진 소스로 확정했다. ISKM 컴포넌트의 트랙 수가 늘 때마다 렌더러가 뼈대 버퍼를 다시 할당하면서 겹친 자리로 이전 슬롯을 병렬 복사해, 그 프레임에 컴포넌트 전체가 틀린 속도를 받는다. 그래서 모션 블러는 엔진 기본값 그대로 두고, Lab 코드가 컴포넌트마다 트랙 풀을 미리 늘려 트랙 수가 바뀌지 않게 한다. 엔진을 고치는 안과 모션 블러를 끄는 안은 버렸다. 측정 조건은 바뀌지 않고, 프레임 시간 차이는 세 실행 범위 안이다.

## 결정

- 모션 블러는 엔진 기본값(켬)이다. ADR-0007의 측정 조건을 그대로 이어 간다.
- `ULabIskmProcessor`가 ISKM 컴포넌트마다 처음 개체가 들어오는 프레임에 트랙 풀의 끝 번호를 종류의 개체 수 × 1.1 + 64로 늘린다(할당한 뒤 모두 해제). 기본 켬이고 `-LabIskmTrackReserve=0`이 W8까지의 동작이다. 메타데이터 `LabIskmTrackReserve`다.
- 엔진 소스는 고치지 않는다. 엔진 쪽 수정 방법은 engine-notes.md 42절에 적었다.

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| A. 엔진 `AllocSpaceForPrimitive`를 할당 뒤 해제로 고치거나, 겹칠 때 스테이징 버퍼로 복사한다 | 근본 수정이지만 이 프로젝트는 엔진 소스를 고치지 않는다(작업 규칙). 소스 빌드에 패치를 들고 다녀야 한다 |
| B. 모션 블러를 끈다 | ADR-0007이 버린 안이다. 틀린 속도는 TSR도 읽으므로 원인을 가릴 뿐이다 |
| C. 개체가 컴포넌트를 떠날 때 트랙을 해제한다 | 트랙 수가 줄었다 늘었다 해 재할당이 오히려 잦아진다 |
| D. 다시 들어온 개체에게만 새 트랙을 준다 | W9 1차 시험. 트랙 수가 여전히 늘어 번쩍임이 남는다 |

## 결과

- ISKM 구간의 번쩍임이 개발 빌드 연속 캡처에서 사라진다. 글 07(ISKM)의 "원인 미확정"을 이 원인으로 고칠 수 있다.
- 컴포넌트마다 용량만큼의 뼈대 버퍼를 처음부터 잡는다. 이 장면은 측정 끝에 어차피 그만큼 트랙이 늘어 메모리 차이가 없다(GPU 메모리 p50 3,364MB와 3,374MB).
- 종류의 개체 수를 넘는 트랙이 필요한 실행(엔티티를 계속 새로 만드는 변형, 개체 수를 바꾼 실행)에서는 용량을 넘을 수 있다. 그때 트랙 수가 다시 늘어 번쩍임이 돌아올 수 있다.
- 다시 볼 조건: 엔진이 이 재할당 경로를 고쳤을 때(이 스위치가 필요 없어진다), 또는 용량을 넘는 실행이 필요해질 때.
