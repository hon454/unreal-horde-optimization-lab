# ADR-0006 측정을 세 층으로 나누고 단계마다 60fps 경계 둘레만 잰다

- 상태: 승인됨(2026-11-10 채팅에서 사용자가 승인)
- 날짜: 2026-11-10

## 맥락

M3b 묶음(2026-11-09 23:28\~11-10 06:03)은 294회에 6.5시간이 걸렸다. 한 실행은 약 81초다(워밍업 15초, 측정 60초, 기동). 그중 252회(86%)가 전 단계 사다리(M0\~M3의 모든 단계를 N 5점, 카메라 2종, 3회로 재는 것)를 1종과 2종으로 한 번씩 돈 값이다(`Measurements/M3b/batch-phases.csv`). 사용자는 측정 한 번에 6시간이 드는 것이 개발 속도를 떨어뜨린다고 보았다.

측정값에서 확인한 사실은 다음과 같다. 수치는 프레임 p95(ms)이고 출처는 `Measurements/M0/summary.csv`와 `Measurements/M3b/summary.csv`(`m3mass-t2-fin`, 게임 창이 뒤에 있던 묶음이라 상대 비교만 유효)다.

| 사실 | 값 |
| --- | --- |
| 대표 지표 N@16.7ms는 경계 양쪽 두 점의 보간이다. 경계에서 먼 점은 계산에 쓰이지 않는다 | [measurement.md](../Guides/measurement.md) "지표" |
| 액터 단계의 경계는 N 500\~2,000에 있다 | M0 full P1: 500 12.4 / 1,000 22.8. M0 static P1: 1,000 15.8 / 2,000 30.4 |
| Mass 단계의 경계는 N 5k\~20k 사이, 한 번도 재지 않은 구간에 있다 | M3b 대표 2종 P1: 5k 7.98 / 20k 20.14 / 30k 24.20 / 50k 32.92 |
| 그 구간이 4배라 보간 방식만으로 값이 16% 달라진다 | 로그 보간 13,513, 직선 보간 약 15,700(계산) |
| 곡선이 그 구간에서 꺾인다 | Game p50이 천 마리당 5k\~20k 0.78ms, 20k 이후 0.35\~0.40ms(계산) |
| Mass 단계의 5k는 GPU 병목이다 | M3b 대표 2종 5k P1: GPU 5.95, Game 5.52 |
| 액터 단계는 카메라에 따라 달라지지 않는다 | M0 full 1,000: P1 22.8 / P2 21.7. M0 static 1,000: 15.8 / 15.8 |
| 표현 LOD가 있는 단계는 카메라에 따라 달라진다 | M3b 대표 2종 20k: P1 20.1 / P2 11.3 |
| 3회 사이의 범위는 대부분 작지만 꼬리가 있다 | M3b 최종 묶음: 중앙값 0.34ms, 상위 10%는 2.5ms 초과 |
| P1은 60초에 한 바퀴다 | measurement.md "확정값" |

## 결정

측정을 세 층으로 나눈다. 러너, 시드, 카메라 프리셋, CSV 형식, 워밍업 15초, 측정 60초, 조건당 3회는 바꾸지 않는다([ADR-0002](0002-freeze-measurement-infra.md)). 바꾸는 것은 어느 조건을 언제 재는가다.

| 층 | 언제 | 조건 | 쓰임 |
| --- | --- | --- | --- |
| 개발 확인 | 구현 중 수시로 | N=20k, P1, 1\~3회 | 방향 확인. 글·표·`summary.csv`의 비교에 쓰지 않는다 |
| 마일스톤 묶음 | 마일스톤 끝 | 새 단계의 대표 설정과 기준점(직전 마일스톤의 대표 설정)을 같은 묶음에서 잰다. N과 프리셋은 그 마일스톤의 [plan.md](../plan.md) "측정 조건"이 정한다. 하위 실험은 N=20k P1 3회. 묶음 앞뒤 A/A, 스파이크 검사, 앞 창 검사는 그대로다 | 마일스톤의 판단. STATUS.md와 Worklog에 적는다 |
| 총괄 묶음 | 프로젝트가 궤도에 오른 뒤 사용자가 정할 때 | 최신 빌드 하나로 한 날 잰다. 전 단계 사다리(아래)에 글이 쓰는 모든 점(하위 실험, 같은 N 비교점, 병목 이동을 보이는 점)을 그때의 글 목록에서 뽑아 더한다 | 글과 README의 수치 |

N을 고르는 규칙:

1. **경계 규칙.** 설정마다 60fps 경계(프레임 p95 16.7ms)의 위와 아래에 측정점이 하나씩 있어야 한다. 없으면 그 설정만 한 점을 더 잰다(Mass 단계는 아래로 5k, 위로 50k. 액터 단계는 아래로 250, 위로 5k).
2. **Mass 단계의 기본 점은 P1 N {10k, 20k, 30k}, P2 N 20k 한 점이다.** 액터 단계는 P1 N {500, 1k, 2k}이고 P2는 재지 않는다. 1종은 다시 재지 않는다(M4부터 2종이 기본).
3. **중간점은 결과를 보고 더한다.** 두 설정의 N@16.7ms 차이가 보간 오차(구간 2배에서 최대 약 6%) 안이면 경계가 낀 구간의 중간점(15k 또는 25k)을 그 설정들만 3회 더 잰다.
4. **GPU나 렌더링이 주제인 마일스톤은 plan.md에서 5k를 더한다**(measurement.md "5k는 GPU가 주제인 실험에만 쓴다").

전 단계 사다리는 규칙 2로 29조건(액터 3단계 × 3점 + Mass 5단계 × 4점), 3회씩 87회에 A/A 6회와 버리는 첫 실행 1회를 더해 약 94회, 2.1시간이다(계산, 한 실행 81초).

## 고려한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 마일스톤마다 전 단계 사다리를 잰다(M3b 방식) | 6.5시간이 든다. 사다리의 값은 다음 묶음에서 다시 덮인다 |
| 모든 단계를 같은 N 8점, 카메라 2종으로 잰다 | 8단계 384회, 약 8.6시간(계산). 경계에서 먼 점은 N@16.7ms에 쓰이지 않는다 |
| 측정 창을 60초에서 30초로 줄인다 | P1이 반 바퀴만 돈다. M0에서 고정한 시나리오가 바뀐다 |
| 3회를 2회로 줄인다 | 이상치 하나를 거르지 못한다. 3회 범위의 상위 10%가 2.5ms를 넘는다 |
| 15k를 고정 점으로 둔다 | 새 단계가 경계를 20k 위로 올리면 쓰이지 않는다. 필요한 중간점은 결과를 봐야 안다 |
| Mass 단계의 마일스톤 묶음에 1k·5k를 둔다 | GPU 병목이라 로직 변화가 프레임에 보이지 않는다 |
| 50k를 고정 점으로 둔다 | M3b의 모든 Mass 단계가 30k에서 이미 경계 위다. 경계 규칙이 필요할 때만 부른다 |

## 결과

- M4 마일스톤 묶음은 약 48회, 1.1시간으로 예상한다(대표 설정 2 × 4조건 × 3회 24, 하위 실험 15, A/A 6, 트레이스 2, 첫 실행 1).
- N=10k는 아직 잰 적이 없다. 10k가 경계 아래라는 것은 추정이다. M4 묶음 전에 개발 확인으로 한 번 돌린다.
- 이전 묶음에는 10k가 없다. 새 점으로 구한 N@16.7ms는 이전 묶음의 값과 직접 비교하지 않는다. 같은 묶음에서 잰 기준점과 비교한다.
- 병목이 자원 사이를 옮기는 모습(M1 2종 50k는 렌더 스레드 병목)은 마일스톤 묶음에 나타나지 않는다. 글에 필요하면 총괄 묶음에 그 점을 넣는다.
- 글 01\~04가 쓰는 하위 실험 값은 옛 묶음의 것이고, 그 묶음에서 게임 창이 앞에 있었는지는 기록이 없다. 총괄 묶음에서 다시 잰다.
